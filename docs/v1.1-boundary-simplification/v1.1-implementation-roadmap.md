# v1.1 Implementation Roadmap (Strangler + Fitness-Driven)

Date: 2026-03-18  
Last Updated: 2026-03-21  
Status: active (execution + stabilization)  
Scope: execution plan and live rollout status

## 1) Purpose

Ez a dokumentum az aktiv vegrehajtasi terv a v1.1 boundary simplificationhoz.
A discovery fazis lezarult; innen nem elvi iranyok, hanem konkret, merheto migration lepesek kovetkeznek.

## 1.1) Current Execution Snapshot (2026-03-21)

1. Command migration map allapot:
   - minden jelenleg kezelt command `v11` allapotban van a `tests/contracts/v11/migration-map.ts` alapjan.
2. Fitness gate allapot:
   - a policy `M3` milestone mellett fut,
   - a check-ek hard-fail modban vannak,
   - aktualis `fitness:report` futas zold.
3. Local CI allapot:
   - `ci:local` futas zold (lint + typecheck + unit/contract + UI integration + fitness gate).
4. Aktualis fokusz:
   - nem uj command migration, hanem stabilizacio/hardening:
   - parity/contract coverage melyites,
   - fitness zajcsokkentes false positive nelkul,
   - dokumentacio/policy/runtime allapot folyamatos szinkronja.

## 2) Success Criteria

1. Nincs big-bang rewrite; commandonkenti strangler migracio tortenik.
2. Minden migralt commandhoz van stabil contract tesztkeszlet.
3. A 6 architectural fitness check dokumentalt, merheto, CI-be kotott.
4. A v1.1 celarchitektura szabalyai legalabb a migralt scope-on hard-gate modban ervenyesulnek.

## 3) Non-Goals

1. Nem cel egyszerre az osszes legacy command kivaltasa.
2. Nem cel a teljes kodbazis azonnali hard-fail gate ala vitele.
3. Nem cel uj product feature szallitasa ebben a roadmapben.

## 4) Operating Model

## 4.1 Migration Pattern (Strangler)

1. Uj implementacios zona: `src/v11/**`.
2. Legacy zona: `src/core/**` (fagyasztott, csak kritikus fix engedett).
3. Commandonkenti atallas `legacy -> parity -> v11` allapotokon.

### 4.1.1 `src/v11` Layer Mapping (explicit)

1. `src/v11/domain/**`
   - Pure policy/dontes/invariant logika (I/O nelkul).
2. `src/v11/application/**`
   - Use-case orchestration + command flow koordinacio.
3. `src/v11/ports/**`
   - Repository/Delivery/Metrics/Clock/Id interface-ek.
4. `src/v11/infrastructure/**`
   - Port implementaciok (fs/tmux/runtime/artifact/state/transcript adapterek).
5. `src/v11/legacy-compat/**`
   - Legacy input/state normalizalas, compatibility bridge.
6. `src/v11/shared/**`
   - Kozos tipusok/utilityk, amelyek nem torik meg a reteg-hatarokat.

### 4.1.2 Import Direction Rules (`src/v11`)

1. `domain` csak `domain` + `shared` importot hasznalhat.
2. `application` importalhat `domain`, `ports`, `shared` retegeket.
3. `infrastructure` implementalhat `ports`-ot, es hasznalhat runtime I/O-t.
4. `legacy-compat` nem importalhat `domain` belso policy implementaciot kozvetlenul; csak publikus `application`/`ports` boundary-n keresztul kapcsolodhat.
5. `src/cli/**` kizarlag `application` entrypointokat hivhat; kozvetlen state/transcript mutacio tiltott.

### 4.1.3 Rule Enforcement by Migration State

1. Architekturacel:
   - a 4.1.2 import szabalyok celallapotban minden migralt commandra kotelezoek.
2. `legacy` allapot:
   - nincs hard-fail enforcement; csak migration tervezesi input.
3. `parity` allapot:
   - report-only enforcement,
   - kivetelek csak explicit migration allowlisttel engedhetok (`owner`, `reason`, `expiry milestone` kotelezo).
4. `v11` allapot:
   - hard-fail enforcement kotelezo.
5. `legacy-compat -> domain internal` tiltasa:
   - cel-invarians minden fazisban ervenyes,
   - hard gate formajaban csak `v11` allapotban kotelezo,
   - parity alatt csak ideiglenes, dokumentalt, lejaro kivetel mellett toleralhato.

## 4.2 Command Migration States

1. `legacy`: csak regi implementacio fut, v11 nincs aktivan kotve.
2. `parity`: ugyanazokra a contract case-ekre legacy es v11 is fut; diff report kotelezo.
3. `v11`: v11 az aktiv path; contract teszt hard gate.

### 4.2.1 Parity Exit Criteria (`parity -> v11`)

Egy command csak akkor lephet `parity` allapotbol `v11` allapotba, ha minden kotelezo feltetel teljesul:
1. Stabilitas:
   - minimum 10 egymast koveto parity CI futas zold ugyanarra a command scope-ra.
2. Drift:
   - nincs nem-jovahagyott viselkedesi drift,
   - blocker drift (P0/P1) tolerancia: 0.
3. Idotartam:
   - minimum 3 naptari nap parity megfigyelesi ablak.
4. Bizonyitek:
   - legalabb 1 replay/parity osszehasonlito report artifact csatolva.
5. Risk-coverage:
   - az adott command W1 DoD (risk-coverage) teljesult.
6. Dontes:
   - explicit owner sign-off (`go`) a migration mapban.

Megjegyzes:
1. "Drift nincs, vagy dokumentalt es jovahagyott" onmagaban nem elegseges; a fenti 1-6. pont a kotelezo parity-exit gate.

### 4.2.2 Parity Execution Model (runtime koltseg/stabilitas)

1. Runtime command futasban egyetlen authoritative path futhat (`legacy` vagy `v11`), nem ketto egyszerre.
2. Parity osszehasonlitas alapertelmezett modja:
   - determinisztikus contract/replay/fixture futtas (CI vagy offline harness),
   - nem live dupla agent/session futtas.
3. Agent-intenziv commandoknal (`pass`, `kickoff`) parity alatt tilos a dupla LLM-hivas.
4. Shadow parity csak side-effect-mentes modban engedett:
   - nincs state write,
   - nincs transcript append,
   - nincs tmux/delivery side effect.
5. Koltsegvedelmi szabaly:
   - parity drift mereshez elsodlegesen a determinisztikus retegeket duplazzuk (policy/evaluation),
   - runtime I/O es LLM hivas nem duplazhato.
6. Kivetel csak explicit, idoben korlatozott debug flaggel engedelyezheto, release gate-ben nem.

### 4.2.3 Critical Side-Effect Invariant Policy (shield hardening)

1. Parity ekvivalencia onmagaban nem eleg release gate a kritikus runtime side-effectekre.
2. Minden commandhoz, amely runtime handoffot/deliveryt var el, kotelezo legalabb 1 explicit semantic invariant:
   - sikeres command -> elvart side-effect adapter hivas megtortenik, vagy
   - explicit delivery-failure eredmeny mezoben megjelenik (nem csendes kieses).
3. Ezeket az invariantokat deterministic contract/integration tesztben kell verifikalni (nem live LLM lane-ben).
4. `parity -> v11` atlepesi gate csak akkor teljesult, ha a commandhoz tartozik legalabb 1 zold critical side-effect invariant teszt.

## 5) Workstreams

## W1 - Contract Test Harness

### Goal

Minden migralt command viselkedese stabilan bizonyithato legyen `input -> expected state/envelope/output` szinten.

### Deliverables

1. `tests/contracts/v11/schema.ts` (case schema + validation).
2. `tests/contracts/v11/runner.ts` (shared scenario runner).
3. `tests/contracts/v11/migration-map.ts` (command state map: legacy/parity/v11).
4. `tests/contracts/v11/cases/<command>/*.case.json`.
5. `tests/contracts/v11/<command>.contract.test.ts`.
6. `tests/contracts/v11/corpus/README.md` (corpus forras, szelekcios szabalyok, redaction policy, ownership).
7. `tests/contracts/v11/corpus/manifest.json` (determinista corpus osszetetel command-szintu mappinggel).
8. `tests/contracts/v11/corpus/build-corpus.ts` (corpus eloallitas/normalizalas script).

### Rules

1. Case assertion subset-alapu legyen (ne timestamp/id/fingerprint full equality).
2. Kotelezo ellenorzes: result status/reason code, state kulcsmezok, appended envelope tipusa + payload subset.
3. Egy command migration csak akkor lephet tovabb, ha contract suite stabil.
4. A teszt darabszam nem acceptance kriterium; a release gate alapja a risk-coverage.
5. A darabszam-tartomanyok orientacios iranymutatok, nem hard release gate kuszobok.
6. Replay/parity corpus forrasa kotelezoen deklaralt es reprodukalhato legyen (`corpus/README.md` + `manifest.json`).
7. `Good enough` stop-gate kotelezo:
   - commandonkent minimum: `1 happy-path triad + 2 guard/error triad + 1 invariant triad`,
   - baseline utan uj case csak admission policy alapjan (uj reason code / uj risk class / valos regresszio).
8. A reszletes baseline es admission policy forras: `docs/architecture-fitness-checks.md` (`Contract Case "Good Enough" Baseline`, `Contract Case Admission Policy`).

### Risk-Coverage Definition (Command DoD)

1. Canonical contract suite: stabil, reprezentativ core flow halmaz.
2. Risk/regression suite: nyitott vegu, minden javitott bughoz kotelezo uj regresszio eset.
3. Legacy parity suite: reprezentativ input korpuszon legacy vs v11 viselkedes-egyezes.
4. Quality gate: kritikus policy-agak hit-je + parity drift szabaly + flaky budget szabaly.
5. Critical side-effect suite: command-specifikus runtime side-effect invariantok explicit ellenorzese (pl. kickoff implementer delivery).

### Test Taxonomy (Deterministic vs Live-LLM)

1. Contract tests (PR hard gate, determinisztikus):
   - Nem hivnak live LLM-et.
   - Fixture/structured input alapon ellenoriznek `input -> state/envelope/output` szinten.
2. Agent adapter tests (determinista robustsag):
   - Mock/fake agent outputokra futnak (jo, hibas, hianyos, keso, duplikalt esetek).
   - Celfokusz: parser/normalizer/policy agak stabilitasa.
3. Parity/replay tests (determinista regressziofogas):
   - Valos transcript/snapshot korpusz replay legacy vs v11 osszevetessel.
   - Celfokusz: policy/viselkedes drift gyors detektalasa.
4. Live-LLM E2E tests (nem PR-blocker):
   - Korlatozott, koltseges, flake-erzekeny smoke/canary lane.
   - Futasi mod: nightly vagy kulon release gate, nem minden commitnal.

Policy:
1. Merge gate alapja a determinisztikus 1-3. kategoriak.
2. Live-LLM E2E eredmeny release confidence input, de nem kotelezo merge blocker alap.

### Done Criteria

1. `pass` command DoD:
   - canonical contract suite cel tartomany (orientacios, nem hard gate): 20-30 eset,
   - risk/regression suite aktiv (nyitott vegu),
   - legacy parity suite aktiv reprezentativ korpuszon,
   - quality gate pass (kritikus policy-ag hit + elfogadott parity drift szabaly + flaky budget).
2. `converged` command DoD:
   - canonical contract suite cel tartomany (orientacios, nem hard gate): 16-24 eset,
   - ugyanaz a 4-pilleres risk-coverage gate ervenyes.
3. Legalabb 1 parity mode command fut CI-ben.

### Side Note - W1/W4 Bootstrap Sequence (Chicken-Egg kezeles)

1. Lepes A - W1 partial (M0):
   - Contract harness skeleton (`schema`, `runner`, `migration-map`) + kezdo `pass` canonical seed case-ek.
   - Cel: legyen mivel merni a parity kulonbsegeket.
2. Lepes B - W4 partial (`pass` parity):
   - `pass` command parity modba kotese (`legacy + v11` futtatasi/diff report utvonal).
   - Cel: valos parity visszacsatolas megteremtese anelkul, hogy v11 mar authoritative lenne.
3. Lepes C - W1 full (`pass` DoD):
   - `pass` contract suite kibovitese teljes risk-coverage DoD-re (canonical + regression + parity + quality gate).
4. Lepes D - W4 full (`pass` v11):
   - `pass` csak akkor lephet `v11` allapotba, ha a W1 full DoD zold.
5. Generalis szabaly:
   - Kovetkezo command W4 migracioja csak akkor indulhat, ha az adott commandhoz legalabb W1 partial harness mar letezik.

## W2 - Architecture Fitness Spec + CI

### Goal

A 6 fitness check executable formaban legyen definialva es futtathato legyen CI-ben.

### Deliverables

1. `docs/architecture-fitness-checks.md` (single source of truth).
2. `tools/fitness/policy.json` (machine-readable thresholds/scope/mode).
3. `tools/fitness/run-report.ts`.
4. `tools/fitness/run-check.ts`.
5. `package.json` script-ek:
   - `fitness:report`
   - `fitness:check`

### Rollout Modes

1. `report-only`: metrics/report mindig keszul, de nem blokkol.
2. `soft-fail`: warning es PR summary, merge meg engedett.
3. `hard-fail`: CI fail merge elott.

### Mandatory Coverage

1. Boundary fitness.
2. Mutation fitness (dual-gate).
3. Transition fitness (dual-gate).
4. Error fitness (`code + context`).
5. Complexity fitness (threshold + top offender report).
6. Dependency fitness (cycle tilt).

Cross-cutting overlay:

1. Critical side-effect invariant report kotelezo command-szinten.
2. Rollout: M2-tol soft-fail, M3-tol hard-fail a `v11` allapotu commandokra.

### Done Criteria

1. `docs/architecture-fitness-checks.md` kesz, minden checkhez: metric/scope/pass-fail/exceptions/report/owner.
2. Legalabb 2 check hard-fail modban (`boundary`, `transition`) migralt scope-ra.
3. A tobbi check minimum report-only modban fut.

### W2 Hardening Loop (how the fitness infra evolves)

1. Kiindulas:
   - kezdetben egyszeru, gyors checker logika is elfogadhato, ha koran ad hasznos signal-t.
2. Elso fazis:
   - `report-only` modban baseline gyujtes (zaj + valos talalatok kulonvalasztasa).
3. Triage minden finding clusterre:
   - `refactor` (ha valos architekturaris/runtime hiba),
   - `checker/policy refinement` (ha reprodukalhato false positive),
   - `temporary exception` (csak idokorlattal, owner+reason+expiry mezokkel).
4. Hardening:
   - ahol szukseges, regex-jellegu detektalasrol AST-segitett analizisre valtunk,
   - semantikai kulonbsegeket explicitte tesszuk (pl. lifecycle transition vs metadata-only persist).
5. Promotion:
   - csak alacsony zajszintu check lephet `soft-fail` majd `hard-fail` modba.
6. Tanulsag beemeles:
   - ha parity mellett is atcsuszhat kritikus regresszio (pl. side-effect kieses), uj cross-cutting fitness overlayt vezetunk be.

## W3 - Orchestrator Boundary Enforcement

### Goal

Az orchestrator szerep explicit legyen, de ne monolit orchestrator class keletkezzen.

### Deliverables

1. Kozos orchestrator contract one-pager (kesz):
   - `docs/v1.1-boundary-simplification/component-one-pagers/m0-11-use-case-orchestrator.md`
2. Command-level orchestration matrix (annex):
   - `docs/v1.1-boundary-simplification/orchestration-matrix-annex.md`
   - command -> ownership -> required call order -> budget.
3. Guard rule: orchestrator pathon tiltott direct state/transcript write.

### Side Note - Matrix Execution Guide

1. A matrix celja nem dokumentacios disz, hanem migration gate: command csak akkor lephet `parity -> v11` allapotba, ha a sajat sor teljes es ellenorzott.
2. Minden commandhoz kotelezo oszlopok:
   - `command`
   - `ownership` (ki validal, ki ir state-et, ki csak koordinal)
   - `required_call_order` (kotelezo lepesek sorrendje, pl. `load -> gate -> transition validate -> persist -> envelope -> side effect`)
   - `budget` (max komponens-szam, max state write, max kulso I/O, max side effect)
3. Kitoltesi szabaly:
   - eloszor a jelenlegi legacy flow-bol keszul baseline sor,
   - utana a v11 target sor,
   - parity fazisban a ket sor diff-je kotelezoen dokumentalt.
4. Enforcement:
   - fitness reportben commandonkent jelenjen meg budget-tullepes/top offender jelzes,
   - hard-fail csak a `v11` allapotu commandokra legyen bekapcsolva.
5. Ownership lock:
   - STS/BMR boundaryt minden sorban explicit rogziteni kell (`STS validates`, `BMR persists`, `orchestrator coordinates only`),
   - ahol ez hianyzik, a matrix sor `incomplete` statuszu es nem release-kesz.

### Done Criteria

1. Command matrix sorok baseline + v11 target formaban kitoltve (`pass`, `converged`, `approval`, `kickoff`, `gate`, `reconcile`).
2. Legalabb a `pass` command matrix sora legacy flow alapjan validalva (call-order + ownership + budget ellenorzessel, evidence riporttal).
3. Guard rule bekerul fitness check specbe.

4. Shadow/parity drift csak nem-blocker (P2/P3) lehet, dokumentalt es jovahagyott; P0/P1 drift tolerancia 0 a 4.2.1 szerint.

### Side Note - Pilot-to-Milestone Mapping (Architecture Context 4.0)

Forras:
1. `docs/v1.1-boundary-simplification/v1.1 architecture context.md` 4.0 szekcio, "Migracios pilot order".

Mapping:
1. M0 (foundation):
   - Pilot-elokeszites: contract harness + fitness + orchestration matrix.
   - Kotelezo minimum output: `pass` command baseline matrix sor kitoltve es review-zva.
   - Cel: Pilot #1/#2/#3 vegrehajtasahoz meresi es gate infrastruktura.

   - Pilot #1 (`ConvergencePolicy` extraction) alkalmazasa a `pass` command scope-ban.

   - Ez a milestone tudatosan a Pilot #1 + #2 kombinacioja.
3. M2 (`kickoff` + `converged`):
   - Pilot #1/#2 mintak kiterjesztese handoff commandokra.
   - Pilot #3 (gate pipeline) elso aktiv szelete a `converged` gate dontesi lancban.

   - Pilot #3 fo rollout szakasz (gate pipeline + adapter boundary szelesebb alkalmazas).

5. M4-M6:
   - Pilot eredmenyek rendszer-szintu kiterjesztese (`reconcile`, interaction/runtime, close-out commandok),
