L3 Human decision Ask — approval gate

L2 / L2a / L2b gated and communicated machine policy. L3 introduces the human as decision-maker: a human_gate step parks the instance in WAITING(human_decision), records a DECISION_REQUEST for the bound operator, and the operator’s decision routes the workflow. The gate's decisions map is generic — approve | request_rework are just this anchor's keys; the kernel knows no decision names. The narrowest Ask — not a general human platform.

The human is a different mover. A decision is not an actor envelope through HANDLE’s ACTIVE path; it is an operator-intent on a WAITING(human_decision) state — a sibling of KICKOFF. So ACTIVE stays honest ("an agent is working") and WAITING means "blocked on a human." The v1 reality check shows "human" is at least three contracts; L3 takes only the approval gate (the agent-initiated ask-human/help reply is L5).

Scope note (bare wait + its resume). L3 introduces the minimal type: wait shape for the post-approval anchor (commit_pending) and the minimal resume that closes it: arrival parks WAITING(step.wait.kind) (no actor output), and RESUME_WAIT moves forward on a matching event via the step's on_resume route. This is the bare-wait dual of the human_gate decision wait — the missing other half of the WAITING axis, surfaced now because commit_pending would otherwise dead-end. What remains later: result payloads, the resume action (e.g. actually running git commit), child-event resume sources (L4), and timeouts / external-or-fuzzy correlation (L9). It is not a special seam: enough WAITING-kind shapes already exist (kickoff_pending as the first specialized resume, the human_decision decision wait) that a one-off bare wait/resume would just reprise the finalization mistake.

Shape How the L3 pieces fit (L3-specific aid)

L3's pseudocode reads as a list of handlers, but the structure converges: three entry handlers — each with its own guards and its own commit — share the same post-commit target-entry pattern. apply_target_entry_effects fans out by the target's type, and post_commit_output derives the outbound effect. (1) is the code shape, (2) the per-target outcome, (3) the lifecycle it produces.

(1) THREE entry handlers, each its own guards + COMMIT, sharing one target-entry spine
──────────────────────────────────────────────────────────────────────────────────────
   actor envelope      ─▶  HANDLE           ─▶ own guards ─▶ COMMIT  ┐
   operator decision   ─▶  SUBMIT_DECISION  ─▶ own guards ─▶ COMMIT  ├──▶  apply_target_entry_effects(target)
   resume event        ─▶  RESUME_WAIT      ─▶ own guards ─▶ COMMIT  ┘            ─▶ post_commit_output

(2) apply_target_entry_effects applies target-entry effects; the target type decides the resulting lifecycle status; post_commit_output then derives the output
──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
   target = agent step  ─▶  ACTIVE                                       →  DispatchIntent
   target = human_gate  ─▶  WAITING(human_decision) + DECISION_REQUEST   →  HumanDecisionRequest
   target = type: wait  ─▶  WAITING(step.wait.kind)                      →  none  (awaits a resume event)
   target = terminal    ─▶  TERMINAL(done)                               →  none

(3) the lifecycle this produces (the anchor run)
─────────────────────────────────────────────────
   CREATED ─START/KICKOFF─▶ ACTIVE  ⇄  (implement ⇄ review loop)
                              │  reviewer emits CONVERGED   (L2 gates allow)
                              ▼
                   WAITING(human_decision)    ←  operator is asked (DECISION_REQUEST / HumanDecisionRequest)
                      │
            approve   │   request_rework ─▶ back to ACTIVE  (new round, → implement)
                      ▼
                   WAITING(commit_pending)
                      │  operator runs commit ─▶ COMMIT event ─▶ RESUME_WAIT
                      ▼
                   TERMINAL(done)
The same target-entry pattern carries every level: L0a–L2b all enter through HANDLE and end at the commit; L3 only adds the other two entry handlers (SUBMIT_DECISION, RESUME_WAIT) and the target-type fan-out. apply_target_entry_effects applies the target-entry effects; post_commit_output reads the resulting status to decide what to deliver.

Runtime A concrete trace

The reviewer converges at round 2; the result routes to the human_approval gate instead of straight to done:

1
the reviewer emits CONVERGED at round 2 (expected_version=N)
L2 converge gates allow → commit routes review → human_approval; the kernel parks WAITING(human_decision) and records DECISION_REQUEST { recommendation: approve, recommendation_source: { from_step: review, event_type: CONVERGED } } as one visible transition; the output is a HumanDecisionRequest to the operator — no agent is dispatched, round not advanced
2
the operator submits SUBMIT_DECISION(approve)
guards pass (wait.kind ✓ · request_ref correlates ✓ · operator authorized ✓ · version ✓); approve = the recommended decision, so no override is needed (an override here would be override_not_applicable) → append DECISION_MADE(approve) → apply_target_entry_effects routes to decisions[approve].target = commit_pending (a type: wait step) → park WAITING(commit_pending), awaiting the operator's COMMIT. The decision didn’t decide this — the target type did; a different target (agent step, another gate, done) would continue or park differently
3
the operator runs the commit; a COMMIT event arrives for the parked instance
RESUME_WAIT: guards pass (WAITING ✓ · COMMIT ∈ resume_events ✓ · version ✓ · op_id fresh) → append WAIT_RESUMED(COMMIT) → apply_target_entry_effects resolves on_resume[COMMIT] = done → TERMINAL(done). This is the resume contract; the actual git commit, merge, and teardown are later runtime slices
4
(an alternate run, at step 2) the operator submits SUBMIT_DECISION(request_rework, override, payload: { instruction: "fix the failing auth test; leave the public API untouched" })
the required instruction is non-empty ✓, and override flags going against the recommended approve ✓ → append DECISION_MADE(request_rework, override:true, payload) → route decisions[request_rework].target = human_approval → implement; the target advances_round, so a new round opens and the stale review/decision context is cleared → ACTIVE; the implementer is dispatched with the instruction as its handoff (exactly what to fix)
The override case: the converge route recommends: approve, so the agreeing approve needs none. Going the other way — request_rework — is a decision against the recommendation: without override it is Rejected(override_required), and with override: true it records DECISION_MADE(request_rework, override: true) — a human deciding against the machine, on the record. (A warn-sensitive recommendation — one that would instead flag approve as the off-recommendation choice — is the deferred dynamic recommendation.) A wrong operator, a stale version, or a replayed op_id are all rejected on this path.

Pseudocode The rule behind the trace

A new operator-intent handler SUBMIT_DECISION (a KICKOFF sibling), an atomic park_for_human_decision inside the arrival commit, and a post_commit_output that delivers either a dispatch or the Ask. HANDLE is otherwise unchanged:

Entering a human_gate parks inside the same atomic commit that moves the step, so the wait state and the DECISION_REQUEST are one visible transition (no half-entered gate). The decision resumes on a dedicated path guarded by wait.kind + request correlation + operator authority + op_id + CAS — deliberately not HANDLE’s actor gate. The override guard is the only place the machine’s recommendation and the human’s verdict meet. This level is a double birth in the kernel-primitives rebaseline (wave 4): the second keyed routing map (decisions joins transitions) names the ChoicePoint — a declared key set, an authorized selector, guards, and one shared arrival — with its selector-authority dimension (principal-committed / kernel-classified / proposed, the last reserved for L9); and the second outbound ask (HumanDecisionRequest joins DispatchIntent) names the Directive family of projected, deliverable ask objects. The Admission ladder also gains its load-first companion here — admit_input, announced at L0d — and the two operator ops fold their guard heads into it (the rungs were already in canonical order); a malformed intent with no expected_version now gets the ladder's missing_version entry guard instead of comparing absent-vs-current to Stale (recorded as F-W4-2). Behavior is otherwise unchanged.

Config The template — converge routes to a human approval gate

An operator role is added, and the review CONVERGED transition now targets a human_approval human_gate (the L2 converge gates still guard the transition); approve routes to a commit_pending wait step, request_rework returns to implement:

A decision carries no lifecycle meaning: approve routes to decisions[approve].target and the target decides. There is no privileged "finalization" phase — after approval the workflow just has more steps. Here approve targets commit_pending, a generic type: wait step (v1-faithful: approval waits for the operator's COMMIT, which does not fire on its own), so arrival parks WAITING(commit_pending) (a wait.kind on the L0d WAITING axis, NOT a terminal disposition; the closed set done | failed | cancelled is untouched). A different workflow could target another human_gate, an agent step (even a newly-added LLM step), or done. You could interleave a merge_pending wait or an automated performance_test_pending wait — all ordinary steps. The COMMIT resume contract is realized here; the actual git-commit action, the MERGE action, and teardown (v1: APPROVED_FOR_COMMIT → COMMITTED → DONE, then a separate post-DONE merge + teardown) are later slices. The operator is bound exactly like the agent roles, so the existing "binding covers every reachable role" invariant already requires a human to be assigned.
