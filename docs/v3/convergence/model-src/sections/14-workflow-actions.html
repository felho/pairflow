LC3a Workflow actions — commit / merge

A type: action step — the automated sibling of human_gate: a declared operation runs (via a runner), produces a structured outcome, and the outcome selects a route from an outcomes map. It closes the L3-deferred “resume action” hole (the anchor’s commit_pending type: wait step grows up into a type: action). LC3 Workflow Actions is the general capability; LC3a is the realized cut: trigger: operator_intent, anchored on COMMIT + MERGE. The auto trigger (run on arrival, e.g. a perf-test) is the same contract, later. Kernel-touching — the pseudocode diffs against LC2.

Action vs gate. A gate (L2) sits before an already-chosen transition and says allow | warn | block — it never picks a target. An action runs as a step, produces an outcome_key, and outcomes[outcome_key].target picks the next transition. Same runner family (L2a), different graph-role: a gate filters, an action selects.

Scope note (a v3 semantic shift, stated). The anchor routes approve → commit_action → merge_action → done, so workflow-done lands after merge. v1’s DONE was a commit-complete state with merge a separate post-DONE command. We accept the cleaner v3 model (merge is a normal pre-terminal action step, the worktree lives through it, release fires at merge_completed) — the alternative (keep v1’s DONE-before-merge) would need a post-terminal action shape, which we deliberately avoid here.

Shape action ⟷ human_gate (workflow-actions aid)

Both are keyed routing maps over apply_target_entry_effects; only the selector differs — a human picks a decision key, a runner’s result picks an outcome key. The kernel knows neither key’s meaning (de-vocabularized, as at L3).

the operator approves; apply_target_entry_effects arrives at commit_action
it is a type: action step (trigger: operator_intent) → park_for_action sets WAITING(action_pending); the output is an ActionRequest { action_key: COMMIT, runner: pairflow.git_commit, required_payload: { message } } — the operator-facing surface (no agent dispatched)
2
operator runs RUN_ACTION(expected_version, COMMIT, payload: { message: "feat: add X" })
guards pass (action_pending ✓ · trigger correlates ✓ · version current ✓ · op_id fresh ✓ · operator authorized ✓); trigger-validation (payload only): message present ✓ → CAS-claim: action_pending → action_running(request_id) + ACTION_RUNNING (a concurrent RUN_ACTION with a different op_id loses ⇒ not_awaiting_action; same op_id ⇒ Duplicate) → the runner runs git commit in the worktree → classify → committed (commit_sha) → CAS-result: append ACTION_RESULT { op_id, outcome: committed, commit_sha } → route outcomes[committed].target = merge_action → re-park WAITING(action_pending) for MERGE
3
operator runs RUN_ACTION(MERGE)
runner runs git merge --no-ff into base → merged (merge_sha) → append ACTION_RESULT → route outcomes[merged].target = done and emits: merge_completed → apply_target_entry_effects(done) = TERMINAL(done). Post-commit, boundary_events_of = [merge_completed, terminal]; the template declares release.boundaries: [merge_completed] → initiate_release(merge_completed) releases the worktree (LC2); terminal no-ops (not declared)
4
(alternate, at step 3) the merge conflicts
the runner auto-aborts (git merge --abort) → classify → conflict → append ACTION_RESULT { outcome: conflict } → route outcomes[conflict].target = merge_action (self) → re-park action_pending; the operator resolves the conflict and re-triggers MERGE. A bad/empty commit message at step 2 instead is Rejected(missing_required_field) — the action never runs
The split trigger-validation vs action-outcome is the load-bearing line: the trigger validates only the payload (the commit message) — a missing one is rejected before anything runs; workspace reality (nothing staged, merge conflict) is an action business_failure that stays parked for a retry; a crashed runner (git unavailable) is infra_error, also a parked retry.

  • Scenario coverage: approve → commit action (message-validated) → merge action (emits merge_completed → LC2 release) → done; a conflict or nothing-staged stays parked for a retry; a bad message is rejected before any git runs.
  • Invariant coverage: outcome selects not the kernel ✓; trigger validates payload only ✓; self-route stays parked ✓; ACTION_RESULT evidence ✓; outcome emits the LC2 boundary ✓; action-is-select vs gate-is-filter ✓ — and all L0a–L3 + LC1 + LC2 invariants still hold.
  • Accepted tradeoff: a v3 semantic shift (workflow-done after merge, vs v1’s DONE-before-merge) — stated and accepted to keep merge a normal pre-terminal action; the auto trigger and a packaged action library are out.
  • Known gaps (intended): auto trigger (later), rich outcome predicates (later), packaged actions (LC3b), operator delete + purge (LC4), exactly-once / retry (L9), remote action proofs (L8/L10). Each is in Absent.
  • Rebaseline (wave 3): the LC3a step is labeled as two chained Errand instances — the ask (open at the park; derived directive) whose completion opens the run (the first inline-form instance, bracketed by the two CAS commits); trigger-validation is a pre-open guard, not part of the run's claim. See the kernel-primitives memo (§6/§9); behavior unchanged.
  • Rebaseline (wave 4): the outcomes route is labeled a ChoicePoint (kernel-classified — the runner's classified result) and ActionRequest a Directive member; behavior unchanged.
  • Hardening (F-W1-2 ingress touch): RUN_ACTION's head folded into admit_input — the load gained its unknown_instance guard and the authority REQUIRE its name (operator_not_authorized, both branches declared); deliberate, ratified behavior deltas (memo §9).
  • Decision: accepted as the LC3a baseline (light evidence per playbook §2.1); LC3b generalizes the action library, L4 inherits action steps per child.
