③a Workflow actions — commit / merge

A type: action step — the automated sibling of human_gate: a declared operation runs (via a runner), produces a structured outcome, and the outcome selects a route from an outcomes map. It closes the L3-deferred “resume action” hole (the anchor’s commit_pending type: wait step grows up into a type: action). ③ Workflow Actions is the general capability; ③a is the realized cut: trigger: operator_intent, anchored on COMMIT + MERGE. The auto trigger (run on arrival, e.g. a perf-test) is the same contract, later. Kernel-touching — the pseudocode diffs against ②.

Action vs gate. A gate (L2) sits before an already-chosen transition and says allow | warn | block — it never picks a target. An action runs as a step, produces an outcome_key, and outcomes[outcome_key].target picks the next transition. Same runner family (L2a), different graph-role: a gate filters, an action selects.

Scope note (a v3 semantic shift, stated). The anchor routes approve → commit_action → merge_action → done, so workflow-done lands after merge. v1’s DONE was a commit-complete state with merge a separate post-DONE command. We accept the cleaner v3 model (merge is a normal pre-terminal action step, the worktree lives through it, release fires at merge_completed) — the alternative (keep v1’s DONE-before-merge) would need a post-terminal action shape, which we deliberately avoid here.

Shape action ⟷ human_gate (workflow-actions aid)

Both are keyed routing maps over apply_target_entry_effects; only the selector differs — a human picks a decision key, a runner’s result picks an outcome key. The kernel knows neither key’s meaning (de-vocabularized, as at L3).

                      └─ infra_error / undeclared → re-park action_pending (audited), operator retries

the operator approves; apply_target_entry_effects arrives at commit_action

2
operator runs RUN_ACTION(expected_version, COMMIT, payload: { message: "feat: add X" })
guards pass (action_pending ✓ · trigger correlates ✓ · version current ✓ · op_id fresh ✓ · operator authorized ✓); trigger-validation (payload only): message present ✓ → CAS-claim: action_pending → action_running(request_id) + ACTION_RUNNING (a concurrent RUN_ACTION with a different op_id loses ⇒ not_awaiting_action; same op_id ⇒ Duplicate) → the runner runs git commit in the worktree → classify → committed (commit_sha) → CAS-result: append ACTION_RESULT { op_id, outcome: committed, commit_sha } → route outcomes[committed].target = merge_action → re-park WAITING(action_pending) for MERGE
3
operator runs RUN_ACTION(MERGE)
runner runs git merge --no-ff into base → merged (merge_sha) → append ACTION_RESULT → route outcomes[merged].target = done and emits: merge_completed → apply_target_entry_effects(done) = TERMINAL(done). Post-commit, boundary_events_of = [merge_completed, terminal]; the template declares release.boundaries: [merge_completed] → initiate_release(merge_completed) releases the worktree (②); terminal no-ops (not declared)
4
(alternate, at step 3) the merge conflicts
the runner auto-aborts (git merge --abort) → classify → conflict → append ACTION_RESULT { outcome: conflict } → route outcomes[conflict].target = merge_action (self) → re-park action_pending; the operator resolves the conflict and re-triggers MERGE. A bad/empty commit message at step 2 instead is Rejected(missing_required_field) — the action never runs
The split trigger-validation vs action-outcome is the load-bearing line: the trigger validates only the payload (the commit message) — a missing one is rejected before anything runs; workspace reality (nothing staged, merge conflict) is an action business_failure that stays parked for a retry; a crashed runner (git unavailable) is infra_error, also a parked retry.

Invariant New at ③a

Added rules
single-winner action claim (CAS, marker-first)
because the runner mutates git, the action is claimed before it runs: a CAS commit takes action_pending → action_running(request_id) + ACTION_RUNNING; only the winner reaches the runner (a concurrent RUN_ACTION with a different op_id sees action_running ⇒ not_awaiting_action; the winner replayed is Duplicate). The trigger is version-checked (Stale) and op_id-idempotent (Duplicate) before the claim — like SUBMIT_DECISION / RESUME_WAIT. The same marker-first shape as ② release
the outcome selects, the kernel does not
an action routes to outcomes[outcome_key].target; the kernel knows no outcome meanings (de-vocabularized, like decisions). Targets resolve at load (validate_action_steps); an outcome not in the map (or infra_error) re-parks action_pending + audits the ACTION_RESULT — never a post-side-effect reject (the side effect already ran)
trigger validates payload; action examines the workspace
the RUN_ACTION trigger validates only the payload (required fields, e.g. the commit message) — missing ⇒ missing_required_field, no run. Workspace reality (nothing staged, conflict) is an action business_failure, surfaced as an outcome_key, never a trigger reject
a self-routing outcome stays parked
a business_failure (or any outcome) whose target is the action step itself re-parks WAITING(action_pending) — the operator fixes the workspace (resolve conflict, stage files) and re-triggers; an infra_error with no declared route stays parked + audited (retry is L9)
the action result is recorded with evidence
every run appends an ACTION_RESULT (outcome + outputs + evidence_refs) before routing — the outcome inline in T1, logs in T3 (① INV-3); a parked instance carries no agent dispatch (honest WAITING)
an outcome may emit a release boundary
an outcome’s emits adds a boundary event to the committed outcome; boundary_events_of carries it to ② (merged ⇒ merge_completed ⇒ worktree release). The action does not release — it only emits the boundary; ② owns the release
action is select, gate is filter
a type: action step produces the routing key; a gate (L2) only allow|warn|blocks a key an actor already chose. Same runner family, disjoint graph-roles — an action is never a gate and vice versa

Config The template — commit / merge as action steps

The L3 commit_pending type: wait step becomes a commit_action; a merge_action follows; the release boundary moves to merge_completed (the ② deferral, now realized). Diffs against ②:

committed → merge_action and merged → done (emits merge_completed) are ordinary outcome routes; nothing_staged / conflict route to the same step (stay + retry). The commented perf_test shows the same contract with trigger: auto and a regression → implement route — a mid-flow automated decision point, not built here.

Absent Still not here

No auto trigger — an action that runs on arrival (e.g. a perf-test) is the same contract but a later trigger mode, with its own lifecycle questions (when it runs, retry, does it block dispatch, a WAITING(action_pending) self-loop) → later
No rich outcome-condition language — classify_action_result is exit-code / structured-JSON (L2a-style); a general predicate DSL over outputs is later → later
No packaged action library — only the anchor runners (pairflow.git_commit / pairflow.git_merge); a general catalog (publish, notify, perf-test) is later → ③b
No operator delete — delete_requested is an explicit operator storage/lifecycle intent (a CANCEL sibling) that drives force_release in ④ (② release minus the declared-boundary gate) — not an emitted boundary and not a workflow action; it + the record purge are → ④
No action_running recovery / exactly-once — the side effect runs after the CAS claim and before the result commit; a crash in that window leaves a durable action_running (no double-run, since the claim is single-winner), but reconciling a stuck action_running (re-claim, idempotent re-run, watchdog) is later — the same crash-window class as ② release → L9
No remote / distributed action proofs — a remote action with verifiable completion (the merge-as-distribution concern) is later → L8 / L10

  • Scenario coverage: approve → commit action (message-validated) → merge action (emits merge_completed → ② release) → done; a conflict or nothing-staged stays parked for a retry; a bad message is rejected before any git runs.
  • Invariant coverage: outcome selects not the kernel ✓; trigger validates payload only ✓; self-route stays parked ✓; ACTION_RESULT evidence ✓; outcome emits the ② boundary ✓; action-is-select vs gate-is-filter ✓ — and all L0a–L3 + ① + ② invariants still hold.
  • Accepted tradeoff: a v3 semantic shift (workflow-done after merge, vs v1’s DONE-before-merge) — stated and accepted to keep merge a normal pre-terminal action; the auto trigger and a packaged action library are out.
  • Known gaps (intended): auto trigger (later), rich outcome predicates (later), packaged actions (③b), operator delete + purge (④), exactly-once / retry (L9), remote action proofs (L8/L10). Each is in Absent.
  • Decision: accepted as the ③a baseline (light evidence per playbook §2.1); ③b generalizes the action library, L4 inherits action steps per child.
