L0e Runtime context spec / provider contract

A workflow may declare the runtime context it needs; if it does, a named provider fulfils it and the kernel exposes an actor-facing projection in the packet. A context-free workflow declares none and activates without provisioning. The third instance of the L0c pattern — portable intent → named fulfiller → packet projection.

L0d gave the runtime-context a lifecycle slot (none | requested | ready) and a readiness gate, but left what is requested and who fulfils it abstract. L0e adds a RuntimeContextRequirement (none | required(spec)) on the template, the RuntimeContextProvider contract the kernel resolves at START when one is required, and the project_for_actor view that re-enters the packet. The kernel owns the spec and the contract; provider internals (the git mechanics) are implementation. It is not v1's L8 — the provider is core-adjacent and MVP-critical, the same family as ActorAdapter (runtime refs) and ContextAssembly (prompt refs).

Runtime A concrete trace

An immediate run whose worktree provider fulfils the declared context:

1
operator CREATE_INSTANCE { mode: immediate, task }
the template's runtime_context = required({ kind: worktree, provider: pairflow.worktree, config }) → kernel_status: CREATED, instance-state runtime_context: none
2
operator START
provider ← providerRegistry.resolve("pairflow.worktree") ✓ → provider.provision(instance.id, r1, spec) (async; provider internals run git branch + git worktree add); runtime_context ← requested(r1)
2b
(variant) the spec names a provider the registry doesn't know
provider is none → Rejected(runtime_context_provider_unavailable); no provisioning, no state change
3
kernel event RUNTIME_CONTEXT_READY(r1, ref{ kind: worktree, locator: { repo, worktree_path, branch, base_branch } })
correlation r1 ✓ · ref.kind = spec.kind (worktree) ✓ → runtime_context ← ready(ref); mode immediate → activate → first DispatchIntent
4
the packet carries the actor-facing projection
provider.project_for_actor(ref) → runtime_context: { workspace: { path, branch, repo } } — the kernel-internal ref fields stay out
The provider resolves the abstract request_runtime_context of L0d into a concrete provision call, and the actor finally sees where to work. Provider name-resolution failure is a contract error (rejected at START); a provider that accepts the name but fails to provision surfaces later as a kernel FAIL event (L0d). Deeper provider health/availability and retry are deferred.

Pseudocode The rule behind the trace

The provider contract, a concrete START (resolve + provision), a kind-boundary check on readiness, and the packet projection L0d deferred — diffed against the L0d kernel:

START stops being a placeholder: it reads the pinned RuntimeContextRequirement. If none, the run is trivially ready(∅) and goes straight to activate_or_hold — no provider, no provisioning. If required(spec), it resolves the named provider (rejecting an unknown one) and hands off to provision — async, correlated by request_id. activate_or_hold shares the immediate-vs-hold decision between the provisioned and context-free paths. RUNTIME_CONTEXT_READY gains a kind-boundary check; the kernel validates only the kind and the correlation, never the provider-defined locator. dispatch_intent projects via the same pinned-template provider's project_for_actor, or emits runtime_context: none for a context-free workflow — the actor sees the projection or an explicit none, never the raw ref.

This is the third member of the resolver family — AgentConfig→ActorAdapter, prompt_concern_refs→ContextAssembly, RuntimeContextSpec→RuntimeContextProvider. All share one shape: a portable intent in the definition, a named fulfiller, and a projection into the packet — none of them L8. Naming: template.runtime_context is the declared requirement (none | required(spec)); instance.runtime_context is the L0d lifecycle state (none | requested | ready) — same name, different aggregate (definition vs run).

Invariant New at L0e

Added rules
[[@invariants l0e 0]]

Config The template — declares the runtime context

runtime_context is the RuntimeContextRequirement: a spec block (required) declares what environment the actor needs and which provider builds it; a planning/decision workflow that needs none declares runtime_context: none. The kernel never hard-codes worktrees. work_mode: worktree | clone stays inside config as a provider-internal variant (one kind), exactly as v11 treats WorkspaceKind = WorkMode.

Absent Still not here

[[@absent l0e]]

Evidence Why we accept L0e for now

  • Scenario coverage: a workflow declares its worktree context; START resolves the pairflow.worktree provider and provisions; on RUNTIME_CONTEXT_READY the kind is checked and the actor's packet finally carries a workspace projection. An unknown provider is rejected before provisioning. A context-free workflow declares none and activates with no provider and a runtime_context: none packet.
  • The contract is real, not invented (v11 verified): v1 already has a swappable worktree bootstrap port — BootstrapWorktreeWorkspacePort = (WorktreeBootstrapInput) → WorktreeBootstrapResult (src/v11/ports/worktreeWorkspace.ts), injected via deps.bootstrap in …/start/internal/runtime/startCommandFlows.ts. v3 generalizes it (kind-discriminated, async/event), it does not invent it.
  • Config & mechanics grounded: repo_path, base_branch, bubble_branch (pattern bubble/<id>), work_mode worktree|clone (bubbleConfigTypes.ts, createBubblePreparation.ts); worktree path <repo-parent>/.pairflow-worktrees/<repo>/<id> (bubblePaths.ts); ops git branch + git worktree add/clone (worktreeManager.ts). Projection grounded in RuntimeSessionRecord { worktreePath, workspacePath, workspaceKind } (runtimeSessions.ts); teardown in cleanupWorktreeWorkspace.
  • Normalization: v1's port is synchronous + worktree-only; v3 makes it async (fire → RUNTIME_CONTEXT_READY) and kind-discriminated. work_mode is the first taste of provider-internal variation within one kind.
  • Known gaps (intended): no provider internals, teardown, health, run-override cascade, provisioning-failure handling, conditional/per-step context (each later); no durable delivery (L8) / launch / grant (L7); no full ContextAssembly (L2b). All captured in Absent.
  • Decision: accepted as the L0e baseline (light evidence per playbook §2.1).
