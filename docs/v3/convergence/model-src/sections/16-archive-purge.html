LC4 Archive / export / purge

The storage-lifecycle ops on durable run records — not correctness, not a preservation path. v1's archive existed only because keep-worthy data lived in a delete-sensitive folder; under LC1 the canonical record (T1) and evidence (T3) are already durable, so LC4 is just the explicit operator operations: delete from active scope, optional archive / export snapshot, and a safe hard purge. Only one kernel-adjacent piece — the DELETE_REQUESTED operator intent (a CANCEL sibling) that drives the chain and invokes LC2 force_release (it does not emit a release boundary); purge / archive are storage ops, not kernel handlers. A standalone contract (empty baseline), like LC1.

The LC1-payoff. v1 delete dropped the per-bubble dir and rescued only 5 files — evidence artifacts were lost and transcript refs dangled (the evidence-loss bug). Because LC1 made evidence durable + ref-disciplined (INV-3), a v3 purge is complete and closure-scoped: it removes the full T1 run record and exactly the T3 blobs the run's canonical ref-closure owns — no dangling refs, the v1 bug is impossible. And archive is demoted to optional: the system never reads it back for audit.

Shape The delete → cancel → release → purge chain (LC4 aid)

The destructive precondition is on the purge commit, not the delete intent — so a delete on a live run drives the lifecycle first, and the hard purge only fires once the run is wound down:

  operator DELETE_REQUESTED (force if live)
      ├─ live run?   → CANCEL / terminalize         (lifecycle, unbundled from purge)
      ├─ force_release  → LC2 release WITHOUT the declared-boundary gate   (operator delete is the authority)
      └─ purge_state ← purge_pending
                  ↓   (ops reconciler, once wound down)
         hard_purge  — precond: terminal && release discharged && closure purge-ready
            hard_purge → write-ahead run_index tombstone, then remove closure-owned evidence + record   (ordering / crash-safety: see the table)
                                                          GLOBAL metrics/audit stream SURVIVES

  archive / export (optional, read-only, any time): a cold copy of the durable record — NOT preservation.

  three independent axes:  delete-intent (lifecycle)  ·  release (LC2)  ·  storage (archive / purge)

3
(alternate) delete --force on a RUNNING run
force ✓ → the commit terminalizes first (TERMINAL(cancelled)) + purge_pending; force_release releases the still-held worktree (LC2 release minus the declared-boundary gate — the operator delete is the authority, even though no declared boundary fired); hard_purge waits until that release discharges, then removes the record. Cancel → release → purge, as one operator-initiated chain
4
(alternate) the operator runs archive / export before deleting
read-only w.r.t. the run record & runtime (it writes only catalog metadata): a cold copy of the durable record + closure-owned evidence to a sink → an ArchiveRef + a run_index entry (status: archived). It mutates no canonical run state and is never read back for audit; the durable record stays the authority until purge

Closure rule & run_index — the why behind the tables. A purge is closure-scoped: it removes exactly the T3 blobs the run’s canonical ref-closure owns (MVP: run-owned; a blob shared with another owning run is purged only once all owners release it), never a blanket “delete this run’s evidence”. run_index is itself T1-family canonical storage — T1 carries the run record (the purge target) and the run_index catalog / tombstone (the minimum surviving T1 metadata + idempotency authority), a purge-induced refinement of LC1’s monolithic T1. The per-operation, per-state, and ordering authority is the three tables above; force_release is the contract row where the delete chain diverges from a declared-boundary LC2 release.

Hard-purge ordering — write-ahead & crash-safe (a different kind of truth: not "what the op is" but "in what order it is safe")
#ActionWhy this order (crash-safety)

2remove the closure-owned T3 evidence blobsdriven from the tombstone’s manifest (captured at step 1 while the record was readable), not re-enumerated from the record — so it survives the record removal in step 3
3remove the full T1 run recordlast — it was the source for the manifest at step 1; the run_index tombstone (with its manifest) survives it as the authority + re-drive source
Re-drive: hard_purge(run_id) is keyed by run_id, not the instance, so it survives the record it removes. On re-drive it reads the run_index tombstone first: if purged, it finishes cleanup from the tombstone’s manifest (every step idempotent — already-removed blobs / already-gone record are no-ops); if not yet purged, the full record is still the authority for the preconditions. So the safe residue is always "tombstone + manifest + a not-yet-finished removal", never "removed record + no tombstone". Full crash-consistent reconciliation is L9.

  • Scenario coverage: delete a terminal run → release (no-op if already released) → purge → tombstone; delete --force a live run → cancel → force-release → purge; archive/export is an optional cold copy — read-only w.r.t. the run record/runtime, but it writes a run_index catalog entry.
  • Invariant coverage: archive not preservation ✓; purge complete + closure-scoped ✓; precondition on the purge not the intent ✓; tombstone + surviving global audit ✓; delete is an operator intent not a workflow action ✓ — and all L0a–L3 + LC1–LC3 invariants still hold.
  • Accepted tradeoff: retention / auto-purge, a query CLI, restore, and a multi-owner blob store are out — LC4 is the explicit operator ops + the safe purge contract.
  • Known gaps (intended): retention / scheduled auto-purge policy (L9/ops), archive query (ops), restore (later), shared-evidence ownership (later), export formats (ops), federation purge (L11+). Each is in Absent.
  • Rebaseline (wave 3): the delete chain is labeled — behind the one operator intent sits a force-opened release Errand (the same LC2 instance), while hard_purge is deliberately NOT an errand (a preconditioned storage re-drive with no request/reply or completion event). See the kernel-primitives memo (§6/§9); behavior unchanged.
  • Hardening (F-W1-2 ingress touch): DELETE_REQUESTED gained its none-instance path — the tombstone answers already_purged (keyed by the intent's id), no tombstone answers unknown_instance; the existing-instance path keeps authority BEFORE the purge_pending no-op, and its old tombstone re-check drops as unreachable (purged ⇒ the record is gone ⇒ load returns none); deliberate, ratified behavior deltas (memo §9).
  • Decision: accepted as the LC4 baseline (light evidence per playbook §2.1). This closes the lifecycle-close topic (LC1–LC4); L4 (child workflows) inherits all four per child runtime_context / record.
