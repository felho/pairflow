L4 Child workflow instances + internal lifecycle events

A workflow instance can spawn and link another full workflow instance, wait on it, and route on the child's lifecycle — delivered as an internal kernel event, not a poll. The child is a complete first-class instance (its own record, runtime_context, and ①②③④ lifecycle), not an embedded subflow. This is the WF-7 unlock (plan execution / pairflow self-hosting). The kernel core is narrow: five primitives — everything else (plan review, task split, approve/refine routing) is parent-template authoring on the primitives already built.

The boundary. L4 = the parent↔child instance link + the internal-lifecycle-event resume. ③ = process / LLM action routing inside the child (a failed merge can route to an agent step that resolves the conflict, then back). L3 = human / decision gates inside the child. So a child template can run all the way to done on its own — close, commit, merge, and recovery live in the child, not in the parent. v1's ExecutePairflowPlan + plan watch is the grounding anchor, but it is not the v3 child boundary: v1 stopped the programmed workflow at READY_FOR_HUMAN_APPROVAL and let an LLM orchestrate the rest; v3 pulls that into the child template.

Shape Spawn → wait → internal event → route

  PARENT instance                                              CHILD instance (a FULL instance: own record / runtime_context / ①②③④)
  ───────────────                                              ──────────────────────────────────────────────────────────────────
  arrive(type: child_workflow step)
    ├─ ChildWorkflowLink { child_key } ──────── idempotent ── (≤ 1 ACTIVE link; a crash-replay reuses it — a terminal link ⇒ a fresh retry attempt, never a double-spawn)
    ├─ WAITING(child_event)   (parks on the DECLARED wait_for lifecycle keys)
    └─ SpawnIntent  (produce-not-perform) ─────────────────►  CREATE_INSTANCE(child_template_ref, …, parent_ref)
                                                                  START → implement / review / … / merge_action → done
         (asleep — no polling)                                          │
                                                                  child terminal commit
  CHILD_LIFECYCLE { child_id, lifecycle } ◄────────────────── emit_child_lifecycle  (POST-COMMIT, correlated by parent_ref / child_id — the internal channel)
    └─ RESUME → arrive(wait_for[lifecycle].target)
         done → next_task   ·   failed / cancelled → recover

  MVP: sequential — one child link per parent step, no fan-out.   Mechanism: subscription is transition-based; the anchor subscribes only terminal (done | failed | cancelled).

the child has a parent_ref, so the kernel delivers an internal event to the parent (the RUNTIME_CONTEXT_RELEASED / ACTION_RESULT sibling). CHILD_LIFECYCLE handler: correlation ✓ (link_id + child_id) · parent is WAITING(child_event) on this link ✓ · done ∈ wait_for ✓ → arrive(wait_for[done].target = next_task)
4b
(orphan trap) the child is deleted out-of-band — an operator DELETE_REQUESTED (④)
delete drives cancel → ② force_release → purge; the cancel is a terminal commit ⇒ emit_child_lifecycle{ cancelled } fires BEFORE the record winds down → the parent receives CHILD_LIFECYCLE{ cancelled } → arrive(recover). The parent never waits forever. (A child purged before the parent consumes the event — a lost-event race — is L9 reconciliation via the surviving link + parent_ref)

Pseudocode The child-workflow handlers (diff vs ③b)

L4 adds two helpers, a spawn/park, a post-commit emission, and one kernel-event handler — reusing apply_target_entry_effects (arrive), the produce-not-perform intent, the marker-first idempotent claim, and the post-commit hook. Every other line is the ③b kernel:

The spawn is produce-not-perform: park_for_child only records the (idempotent) link and parks; the child CREATE_INSTANCE runs post-commit as a SpawnIntent (the ActionIntent / DispatchIntent analog). emit_child_lifecycle runs post-commit beside initiate_release — a child's terminal commit delivers a CHILD_LIFECYCLE to its parent. The handler is the ACTION_RESULT sibling: correlate by parent_ref / child_id, then the SAME arrive() routes per the parent template. The kernel knows no lifecycle meanings — done / failed / cancelled are just the parent's wait_for keys.

Invariant New at L4

Added rules
a child is a full instance, not a subflow
the child is created by the ordinary CREATE_INSTANCE with its own L0f resolution, runtime_context, record, and ①②③④ lifecycle. L4 adds linkage + an event, not a new embedded execution model
idempotent spawn (child_key) — on the ACTIVE link
the same (parent instance, child step, child_key) yields at most one ACTIVE link (status spawning | active): a crash-replay re-entry reuses it and never double-spawns. A terminal link (a finished / failed / cancelled attempt) does not block — a recovery re-entry with the same child_key spawns a fresh attempt (new link_id). So retry is not a deadlock, and the idempotency is on the live link
spawn write-back is correlated + CAS'd
the child's child_id lands in the parent link via a CHILD_SPAWNED kernel event (the RUNTIME_CONTEXT_READY analog), CAS'd + transcript-backed (spawning ⇒ active) — never an inline shorthand that could be lost. A lost CHILD_SPAWNED self-heals on the first CHILD_LIFECYCLE (the link binds the id then); the crash window (link durably spawning) is reconciled at L9
the parent owns the link; the child carries the back-ref
the canonical ChildWorkflowLink lives in the parent record; the child carries a parent_ref. (v1 had only a child id in plan metadata — no reverse link, so no reconciliation)
CHILD_LIFECYCLE is transition-based; the anchor is terminal
the event is produced by a child's subscribable lifecycle transition commit; the mechanism is general, but the MVP anchor subscribes only terminal transitions (done | failed | cancelled). Intermediate subscription (e.g. ready_for_human_approval) is a valid extension on the same channel
routing is fail-closed on the subscription
the parent resumes only on a lifecycle in its wait_for, on the matching link, while parked — else Rejected. The kernel knows no lifecycle meanings; wait_for keys route via the shared arrive()
round is instance-local
the parent's round (a delivered-task cycle) and the child's round (the child's own loop) measure different things but use the same kernel mechanics — they are two independent instances, neither reads the other's round
a spawn that cannot start is a failed attempt
a static / typo'd template_ref is caught at load (child_template_ref_unresolved); a child CREATE_INSTANCE rejected past load (a dynamic binding / input invalid) emits CHILD_SPAWN_FAILED (the ② initiation-failure analog) → the parent's failed route (present by load — validate_child_steps requires a route for every terminal disposition), link terminal-failed. A transient spawn-dispatch crash (no event) leaves the link durably spawning → L9 re-drive (idempotent by request_id) — never a silent forever-wait

Config A parent template — the plan executor (WF-7)

A new template: a long-lived parent that iterates plan tasks (the task list is the plan document, read by the agent steps — not kernel state), spawning one child per task and waiting on its lifecycle. The child is the ordinary pair workflow (local-pair-v0):

Only run_task is new at L4 — a single type: child_workflow step in a loop. The plan review / split / approve logic (v1's ReviewSpec approve_task / refine_task / split_task / route_back_to_plan) is ordinary parent authoring on the existing gate / decision / agent-step primitives, working off the plan document as data — not a kernel route-taxonomy. split_task just edits the plan document to add tasks; the loop processes them one at a time. A failed / cancelled child routes to recover_task → spec_gate → run_task with the same child_key: because the prior link is terminal, find_active returns none and a fresh attempt is spawned — no deadlock.

Absent Still not here

No fan-out / fan-in — one child link per parent step, sequential (the v1 plan-watch reality and WF-7's one-task-at-a-time). N concurrent children + wait-all / wait-any + a concurrency cap are a quantitative extension once the channel exists → later
No intermediate-lifecycle subscription — the MVP anchor subscribes only terminal child transitions; ready_for_human_approval (the v1 plan-watch trigger) is a valid extension on the same channel, for a child that deliberately runs to a checkpoint, not done → extension
No lost-event / orphan reconciliation — an out-of-band cancel still emits cancelled; but a child purged before the parent consumes the event (a delivery race) is reconciled from the surviving link + parent_ref → L9
No durable / external channel — CHILD_LIFECYCLE is an in-process kernel event; cross-kernel / durable / multi-recipient delivery (the full channel abstraction, kernel federation) is → L8
No kernel-held task queue — the parent iterates the plan document (an artifact the agent steps read / write), not a typed task list in instance state; split_task edits the document → by design
No auto-recovery of a transient spawn-dispatch crash — a definitive child-create reject routes the parent's failed path (CHILD_SPAWN_FAILED), but a TRANSIENT crash before the child is created (the SpawnIntent never delivered) leaves the link durably spawning, re-driven (idempotent by request_id) at → L9
No parent-driven child control beyond spawn — the parent does not pause / step / re-parameterize a running child; it spawns and awaits a lifecycle. Steering a live child is → later

Evidence Why this cut (v1 reality-checked)

  • v1 has no kernel-level parent↔child: plan watch is an external polling loop — it reads each linked bubble's state.json every ~60s (planWatchLoop.ts, planWatchLoopInternalTypes.ts:18), correlating by ids in task frontmatter (doc_bubble_id / impl_bubble_id, linkedBubbleTriggerIndex.ts:379-380). No event, no join, no reverse link. L4 replaces the polling hack with a first-class link + an internal lifecycle event.
  • v1 is strictly sequential (planWatchLoopExecution.ts — one candidate per interval, others deferred) — so the sequential, single-child MVP is v1-faithful; fan-out is the greenfield extension.
  • v1's READY_FOR_HUMAN_APPROVAL trigger (bubbleStatusProjection.ts:16-19) is where the programmed v1 workflow stopped and an LLM took over — evidence for an intermediate subscription, but not a v3 requirement: v3 pulls close / merge / recovery into the child template, so the child runs to done and the parent waits on terminal.
  • v1 has no orphan recovery (no reconciliation sweep; a failed child stalls the plan) — L4's cancelled lifecycle + the canonical link make the orphan trap routable (recover, not wait forever); the deeper lost-event race is the explicit L9 boundary.
  • The dogfooding payoff: WF-7 moves orchestration out of the ExecutePairflowPlan prompt and into the kernel — the observed LLM non-adherence to that skill is direct evidence for "the workflow is the boss" (kernel enforcement, not advisory prompt-level).
