L2a External / process gate execution

L2 core declared the external.* gate but rejected it at run. L2a realizes the inline process path — a gate that spawns a process in the workspace, under a bounded timeout, and maps its result to allow | warn | block. The deferred path stays a later slice.

This is the v1-faithful command gate: v1's PASS validation and meta_review_approve_required run a command synchronously, blocking, in the worktree, with exit-code 0 = pass / ≠0 = block. L2a models exactly that, plus three disciplines v1 left implicit: a bounded timeout, a structured GateInvocation → GateDecision contract, and an explicit runner-error vs business-block distinction. The L2 core process guard flips from "reject" to "run"; everything else in the kernel is unchanged. Deferred execution (WAITING(gate_pending) + GATE_RESULT) and the projection_ref+SDK seam remain later.

Runtime A concrete trace

An implementer PASS gated by the repo's test command — a clean run, a failing test, and a runner error that is audited distinctly from a test failure:

1
codex emits PASS on implement { expected_role: implementer } (version=1, round=1)
authorized ✓ → gate external.process: run("pnpm test", cwd=worktree, timeout_ms) → exit 0 → on_exit["0"] = allow → commit implement → review; evidence log ref recorded on the entry
2
(a later round) codex emits PASS on implement
pnpm test → exit 1 (a test failed) → on_exit[nonzero] = block → Rejected(gate_blocked(reason=test_failed), gate: external.process); no commit, round not burned, still on implement, evidence ref returned in the outcome
3
codex emits PASS with a mis-configured command path
processRunner.run → kind=runner_error (spawn failed) → on_runner_error = block_transition → Rejected(gate_blocked(reason=runner_error), gate: external.process) — audited distinctly from test_failed; the transition is held back because the gate did not run reliably, not because the work is wrong
Same runner, different policy by config alone: on_exit { nonzero: block } is a hard gate; { nonzero: warn } turns it into a warning gate (continue, evidence retained). block_transition for a runner error / timeout still surfaces as gate_blocked, but with a runner_error / timeout reason, never conflated with a business test_failed.

Pseudocode The rule behind the trace

The L2 core process reject becomes a run branch; a ProcessGateRunner contract and a classify step turn a process result into a GateDecision. Deferred execution is still rejected:

The only kernel change is the gate-pipeline branch: a process evaluator no longer hits gate_execution_not_supported (unless it is deferred) — it runs via run_process_gate, which spawns in the workspace under a bounded timeout and feeds the result to classify_process_result. The classifier is explicit: a runner error or timeout maps to block_transition (a distinct reason), and only output.mode decides whether the verdict comes from the exit code or a parsed GateDecision JSON.

  • Scenario coverage: a clean test allows the PASS; a failing test blocks it without burning the round; a runner error blocks the transition with a distinct, auditable reason.
  • Accepted tradeoff: an inline gate blocks HANDLE up to timeout_ms — exactly as v1's synchronous PASS does. Fine for the local MVP; the deferred slice is the explicit escape hatch when blocking is unacceptable (long runs, concurrency).
  • Invariant coverage: round not burned on block ✓; gate read-only & stateless ✓; evidence persisted every run ✓; all L0a–L2 invariants still hold.
  • Known gaps (intended): deferred execution, projection_ref/SDK, fail_instance, route, trust communication (L2b). Each is in Absent.
  • Decision: accepted as the L2a baseline (light evidence per playbook §2.1).
