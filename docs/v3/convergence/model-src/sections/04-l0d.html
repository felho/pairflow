L0d Instance lifecycle + activation

Separates the instance's macro-lifecycle from its position in the step graph: a run is created, activated once its runtime context is ready, may hold in a typed WAITING state, and ends in exactly one terminal disposition. The kernel also stops pretending every input is an actor envelope.

Until now the kernel modelled only the inside of an active run (current_step) and assumed every input was an actor envelope. L0d adds kernel_status as a second stored axis next to current_step, names three input source classes (actor / operator / kernel), guards actor emits to ACTIVE, and folds v1's overloaded RUNNING / PREPARING_WORKSPACE / ideation states into kernel_status + a typed wait. Workflow "phase" stays derived, never stored. It is an L0-family concern (foundational lifecycle): it diffs against the L0c kernel, and its lifecycle guard sits ahead of the role/action checks that L1 later layers on the full L0e kernel.

Runtime A concrete trace

An ideation run — created without a task, held for an operator kickoff, then cancelled:

1
operator CREATE_INSTANCE { mode: deferred_kickoff, task: ∅ }
binding covers every role ✓ → kernel_status: CREATED, current_step: none, runtime_context: none; no dispatch — not active
2
operator START
guarded: runtime_context = none ✓ → requests provisioning, runtime_context ← requested(r1); status stays CREATED (this is v1's PREPARING_WORKSPACE)
3
kernel event RUNTIME_CONTEXT_READY(r1, ctx_ref{ kind: worktree, path, branch, repo })
correlation r1 ✓ → runtime_context ← ready(runtime_context_ref); mode is deferred → kernel_status ← WAITING, wait { kind: kickoff_pending, resume_events: [KICKOFF] }
4
an actor emits PASS now
lifecycle guard: kernel_status ≠ ACTIVE → Rejected(not_active); no transcript append, no state change
5
operator KICKOFF(task)
WAITING + kickoff_pending ✓ → task supplied, activate → kernel_status ACTIVE, current_step implement; first DispatchIntent produced (the L0b path)
6
… the L0a–L0c pair loop runs … later operator CANCEL
non-terminal ✓ → kernel_status ← TERMINAL, terminal_disposition ← cancelled; any further actor emit → Rejected(not_active)
The immediate mode skips the hold after RUNTIME_CONTEXT_READY: it goes straight to activate and the first dispatch. The ideation hold is just WAITING with kind: kickoff_pending — the same machinery later carries human_decision (L3), child_workflow (L4) and timeout (L9). Note: immediate does not mean CREATE starts the run by itself — it is a rule for what happens after an operator START requests the runtime context and RUNTIME_CONTEXT_READY arrives (activate now vs enter WAITING(kickoff_pending)). A convenience operator command may compose CREATE_INSTANCE + START.

Pseudocode The rule behind the trace

A source-routed entry, the lifecycle/activation handlers, and one guard prepended to HANDLE — the first dispatch moves out of instance creation into activate. The lifecycle handlers below omit the commit wrapper for brevity — each mutation is an atomic CAS commit under instance.version unless noted:

START_INSTANCE splits into CREATE_INSTANCE (record + binding-coverage invariant, no dispatch) and the activation path; binding resolution moves out of the kernel to the start path (a plain default-actor + override merge now, the full pre-kernel resolution at L0f), so CREATE_INSTANCE takes the binding as input and only validates coverage. The first dispatch_intent now leaves activate, so a created-but-unactivated instance never dispatches. The lifecycle guard sits right after idempotency (so a duplicate of an already-applied op is still Duplicate, not not_active) and before the stale check (role/action authorization arrives at L1, which builds on this kernel). The three terminal paths differ by origin: COMPLETE is an internal helper HANDLE calls when a transition lands on a terminal step (done is never routed), FAIL is a kernel event, CANCEL an operator intent. Every lifecycle mutation here commits atomically under instance.version just like HANDLE; a replayed actor op (same op_id) is Duplicate, and the lifecycle transitions are single-shot — a second START or a stale RUNTIME_CONTEXT_READY fails its precondition and mutates nothing (a guard rejection, not a silent no-op).

v1's flat lifecycle enum is split: kernel_status is universal (every run has it), while phase-like states (READY_FOR_HUMAN_APPROVAL, …) are derived from current_step/wait, never a second stored truth. PREPARING_WORKSPACE becomes CREATED + runtime_context: requested; the ideation bubble becomes WAITING(kickoff_pending). Naming guard: this runtime_context is the actor's workspace (where work happens) — deliberately not v1's execution_context, which is actor-authority/round state (active_role, round, handoff_id, …). In v3 the actor-authority line is the per-emit snapshot (expected_version, expected_role; round later), kept separate from this workspace ref — which is exactly why we renamed it.

Invariant New at L0d

Added rules
two-axis state
current_step is absent before first activation; after activation it stays the execution position across ACTIVE and resumable WAITING states; workflow phase is derived from current_step/wait, never stored
actor-routable execution
actor envelopes are accepted only when kernel_status = ACTIVE — guarded after idempotency, before the stale check (role/action authorization is layered on at L1)
uniform commit discipline
every lifecycle mutation commits atomically under instance.version / CAS; actor envelopes keep op_id idempotency, while lifecycle inputs are guarded by preconditions and correlation ids (request_id) where applicable — the store stays dumb, the kernel writes meaning atomically
typed waiting
WAITING always carries a wait.kind and an explicit resume_events class
terminal is a sink
TERMINAL rejects every state-mutating input (dispatch, actor emit, operator mutation); reads/status queries still allowed; terminal_disposition is written exactly once via COMPLETE / FAIL / CANCEL
readiness gates dispatch
provisioning is fulfilled by a provider (→ L0e), but activate requires runtime_context = ready — no dispatch into a non-ready context; START is single-shot (requestable only from none)

Config The template — gains an activation mode

activation configures only the birth mode — the start step and roles are already in the template, so no second source of truth. deferred_kickoff is the v1 ideation bubble normalized: a WAITING(kickoff_pending) hold released by an operator kickoff. Who may issue kickoff/cancel is dormant (operator authority comes later) — the same dormant-until-restricted pattern L1 later uses for authored capability restrictions.

Absent Still not here

No operator authority / identity — who may issue START / KICKOFF / CANCEL is dormant (the dormant-until-restricted shape L1 later reuses) → L7 / L10
No runtime-context spec / provider contract — what context the template requires and which provider fulfills it (worktree / mailbox / …); L0d consumes only RUNTIME_CONTEXT_READY and stores an opaque ref, provider internals stay implementation → L0e
No kickoff payload materialization — KICKOFF here models only task-supply + activation; v1 also writes a task artifact, flips ideation config (task_pending=false, kicked_off_at) and appends a TASK envelope — activation/input materialization (a persistence detail), not the runtime-context provider → later / impl
No post-approval resume actions — L0d owns the generic terminal disposition paths (COMPLETE / FAIL / CANCEL); v1's post-approval path is APPROVED_FOR_COMMIT → COMMITTED → DONE (the git commit precedes DONE), with the merge a separate command after DONE. The minimal resume contract for such waits is realized at L3 (RESUME_WAIT: COMMIT → done); the resume actions/mechanics (running git commit, merge, teardown) are later — not a privileged finalization phase → L3 contract / later actions
No human / child / timeout / external waits — WAITING ships with only kickoff_pending → L3 / L4 / L9
No generic wait-resume contract — KICKOFF is the first specialized WAITING resume (activation). The generic bare-wait resume (resume any WAITING from a matching event → apply_target_entry_effects) appears at L3, when commit_pending introduces the first non-activation bare wait; child-event and timeout/external resume sources reuse it later → L3 / L4 / L9
No retry / compensation / rollback on FAILED → §18
No operator-intent audit / provenance — the source class is named, its full authority model is later → L7 / L10

Evidence Why we accept L0d for now

  • Scenario coverage: the v1 ideation lifecycle shape is reproduced/normalized from config — created without a task, held in WAITING(kickoff_pending), released by an operator kickoff; an actor emit during the hold is rejected as not_active. Immediate runs skip the hold.
  • Invariant coverage: two-axis state (current_step absent before first activation, then the execution position across ACTIVE and resumable WAITING) ✓; lifecycle guard after idempotency, before stale ✓; typed WAITING + explicit resume class ✓; terminal sink with single-write disposition ✓; readiness gates first dispatch ✓; all L0a/L0b/L0c invariants still hold.
  • Reality check (v11): normalizes — not copies — src/contracts/kernel/lifecycle.ts (10 states) and the cyclic transitions in src/v11/domain/state/transitions.ts into 4 kernel_status + a disposition; round/round_role_history in …/state/snapshot/bubbleStateSnapshot.ts confirm position is already separate from lifecycle; kickoff is an operator intent with an ideation precondition (…/kickoff/kickoffCliCommand.ts, mode in …/ideation/ideationConfigTypes.ts); the actor (agent …) vs operator (bubble …) command surfaces are the two input classes.
  • v1 cross-check (verified against source): v1's execution_context (…/state/execution/executionContextTypes.ts) is actor-authority/round state (active_role, round, handoff_id, execution_id, attempt, deadline); the worktree path lives separately (runtimeSessionRecord / bubblePaths.worktreePath) — hence our workspace ref is renamed runtime_context, kept apart from the authority snapshot. Provisioning is a synchronous start pipeline (PREPARING_WORKSPACE → bootstrap → session → tmux → RUNNING; …/start/internal/runtime/startCommandFlows.ts) with no explicit event, so RUNTIME_CONTEXT_READY is a v3 abstraction and PREPARING_WORKSPACE is the in-flight marker requested generalizes. v1 ideation start is RUNNING round=0, active_role set, execution_context=null (…/state/startState.ts, guard requires round ≥ 1) — a "RUNNING-but-not-routable" shape v3 normalizes to WAITING(kickoff_pending). v1 also clears execution_context on waiting/terminal entry while round/active_role survive (…/state/machine.ts), and allows FAILED from any active / CANCELLED from any non-final (…/state/transitions.ts) — so position, actor authority and runtime ref are three separate concerns, FAIL/CANCEL stay broad, and COMPLETE is ACTIVE-only here (L3 generalizes it to a committed arrival into a terminal target, reachable from a resumed WAITING decision too).
  • Known gaps (intended): no operator authority (L7/L10); no runtime-context spec/provider (L0e); no post-approval resume actions/mechanics (the minimal COMMIT resume contract appears at L3); only kickoff_pending waits here; no retry on FAILED (§18). Each is in Absent.
  • Decision: accepted as the L0d baseline (light evidence per playbook §2.1).
