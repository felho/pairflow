LC2 Runtime resource teardown / provider close

The symmetric half of L0e: provision built the runtime_context (worktree / branch / tmux session); LC2 releases it. The kernel tracks a release obligation for every ready runtime_context and closes L0d/e's current dangling provision (we provision a worktree and never release it). A kernel-touching slice — the pseudocode diffs against L3. Conceptually this still completes L0e's runtime-context lifecycle; realized here, after LC1 (so release is pure), before L4 (children inherit the contract).

Release mirrors provision, exactly. A declared release boundary (the template's release.boundaries, e.g. [terminal] for this anchor) initiates provider.release(ref) asynchronously, correlated by request_id, completed by a RUNTIME_CONTEXT_RELEASED kernel event — the same shape as provision → RUNTIME_CONTEXT_READY. Release is orthogonal to lifecycle: it moves only the runtime_context axis (ready → releasing → released), never kernel_status / current_step / terminal_disposition.

What the kernel can promise. With no auto-retry / timeout / watchdog in this slice (that is L9), the kernel does not promise the resource is eventually released. It promises the weaker, true thing: the release obligation is tracked through failure until discharged, never dropped silently — a run is not "closed" until RUNTIME_CONTEXT_RELEASED, and any failure (initiation or provider) lands in release_failed(ref), a retriable release handle, not a usable runtime. Eventual liveness is the L9 retry slice.

Shape Provision ↔ release symmetry (teardown aid)

The release path is the provision path read backwards — same async/correlated/event shape, plus a failure state that keeps the obligation visible:

  PROVISION (L0e)                                  RELEASE (LC2, the mirror)
  ──────────────────────────────                   ──────────────────────────────
  START, required(spec)                            declared release boundary reached (e.g. terminal)
        │ provider.provision (async)                     │ release_safe ✓ , provider resolved
        ▼                                                ▼ provider.release (async)
  requested(req)                                   releasing(req, ref)
        │ RUNTIME_CONTEXT_READY                           │ RUNTIME_CONTEXT_RELEASED
        ▼                                                ▼
  ready(ref) ──────────────── carries the release obligation ──────────────▶ released  (tombstone)

  state machine (the runtime_context axis only — kernel_status is untouched):
    none ─▶ requested(req) ─▶ ready(ref) ─▶ releasing(req, ref) ─▶ released
                                  ▲                  │
                                  └── (provided)     ▼  initiation OR provider failure
                                            release_failed(ref)   ← retriable release handle, NOT a usable runtime
                                                                    (obligation retained; retry = L9)
The boundary is a declared event, not a kernel default, not the release API, and not an operator command: this anchor declares terminal in release.boundaries; a later workflow declares merge_completed / another event. An operator issues an intent: a v1 merge results in a merge_completed boundary and the kernel initiates the release after it — never conflating the boundary-causing command with the release operation. A v1 delete is instead handled by LC4 force_release (an operator storage/lifecycle intent, not a declared boundary).

Runtime A concrete trace

The local-pair-v0 run reaches done; this template declares terminal in release.boundaries (no post-completion action needs the worktree), so it is released right there:

1
the commit_pending wait resumes on COMMIT → done
COMPLETE sets TERMINAL(done) inside the atomic commit; the terminal transition emits the terminal boundary event. After the commit lands, RECEIVE's post-commit hook calls initiate_release(instance, terminal), which proceeds because terminal ∈ this template's declared release.boundaries and runtime_context = ready(ref). The provider side effect runs only post-commit, never inside the mutation; the instance is already terminal, so release runs orthogonally
2
initiate_release checks the precondition and dispatches
release_safe(instance) holds (LC1 INV-5: no canonical ref points into the worktree — the record, evidence outcomes, and durable evidence refs are all off in T1/T3) → resolve the pinned-template provider → persist the marker first in a CAS atomic commit (REQUIRE ready(ref) → releasing(req, ref) + RUNTIME_CONTEXT_RELEASING), then dispatch provider.release(ref) async post-commit — so the durable correlation target exists before the provider can fire back
3
the provider finishes; RUNTIME_CONTEXT_RELEASED(req, ok) arrives
correlation ✓ (the release we dispatched) → runtime_context ← released (tombstone), append RUNTIME_CONTEXT_RELEASED { evidence_refs }. The worktree / branch / tmux session / registry entry / locks are gone; the durable run record (T1) and evidence (T3) are untouched. The obligation is discharged
4
(an alternate run) the provider reports a partial failure — worktree removed, branch deletion failed
RUNTIME_CONTEXT_RELEASED(req, failed) → runtime_context ← release_failed(ref, reason) + RUNTIME_CONTEXT_RELEASE_FAILED with evidence. The ref is now a retriable release handle, not a usable runtime; the obligation is retained (tracked, not dropped). A retry / timeout / watchdog is L9. The instance stays TERMINAL(done) regardless — release failure cannot un-terminate it
A pre-dispatch failure (not-safe / provider unavailable) lands in release_failed(ref) before any marker. A dispatch error (the dispatch itself errors after the marker committed) is recorded by a follow-up versioned transition (releasing → release_failed, guarded by REQUIRE releasing) — not the same commit as the marker; only a crash in the persist→dispatch window leaves an orphan releasing, which L9 reconciles. A CANCEL or FAIL terminal emits the same terminal boundary event; this anchor releases its provisioned worktree because terminal is a declared boundary — a template that did not declare it would keep the obligation open.

The provider contract gains release; initiate_release runs at the boundary (guarded by release_safe); a RUNTIME_CONTEXT_RELEASED kernel-event handler mirrors RUNTIME_CONTEXT_READY; the three terminal setters emit the terminal boundary event:

The marker commit is a CAS single-winner: COMMIT atomically at expected_version with REQUIRE runtime_context = ready(ref), so two concurrent initiate_release calls race on the same version — one applies releasing(req, ref), the rest reload, see non-ready, and no-op. The marker is persisted before provider.release (so the correlation target exists before the provider can fire); a dispatch error is recorded by a follow-up versioned transition guarded by REQUIRE releasing(request_id, ref) (so a racing RUNTIME_CONTEXT_RELEASED never gets a wrong release_failed); a crash in the persist→dispatch window leaves a durable releasing the L9 watchdog reconciles. The boundary is a parameter: the hook calls initiate_release(instance, terminal), LC3a will call initiate_release(instance, merge_completed), and the guard is boundary_event ∉ release_boundaries(template) — so the deferral hook actually works later. This mirror is the birth of the Errand (kernel-primitives rebaseline, wave 3): the provider round you met at L0e literally repeats — release is the second provider-addressed full instance — so the shape gets its name as a declared contract (claim → post-commit directive → external work → correlated completion → keyed route), and the instances that already existed (kickoff, process gate, human decision, bare wait) are named retrospectively as its forms. Phase labels on the handlers, no mechanical reorganization; the claim phase opens at the marker commit — release_safe and provider resolution are pre-open guards, not errand phases. Behavior is unchanged.

The provider's release bundle (what it provisioned) is opaque to the kernel — worktree, temporary branch, tmux / runtime session, remote clone, plus engine support data (runtime-session registry entry, watchdog markers, locks). The kernel tracks only the obligation, the correlation, and the state; the mechanics are the provider's, exactly as on the provision side (the locator stays provider-defined).
Release policy — the release contract is the provision contract's declared pair
policy: required
the kernel owns the release: a release obligation exists and must be discharged at one of the declared boundaries (non-empty — else the release_boundaries_empty definition issue at admission). This is the worktree anchor: boundaries: [terminal]
policy: retained
the resource is intentionally kept past the run — an explicit ownership decision, not "cleanup later". No kernel release obligation; the kernel never auto-releases
policy: external
the resource lifecycle is owned by an external system / provider policy; the kernel is not the release-owner. No kernel release obligation
load-time rule
a teardown-managed provider (worktree = yes) MUST declare runtime_context.release — provision implies a declared release path (the release_policy_undeclared definition issue otherwise). A shared / external provider opts out. Keyed on the provider, not on runtime_context: required — so the retained / external space is preserved. Boundary coherence is enforced too: under required, boundaries must be non-empty; under retained / external they must be absent or empty (a non-empty list ⇒ release_boundaries_not_allowed) — a config that looks like release but never fires is rejected, not silently ignored
Release boundary — a declared event, distinct from the command that causes it
declared, per policy
under policy: required, release.boundaries lists the events that discharge the obligation. The anchor declares [terminal] (no post-completion action needs the worktree yet); a v1-faithful later form is [merge_completed] — operator delete is not a template boundary; it drives force_release in LC4
terminal is an event, not a default
the terminal transition emits a terminal boundary event; whether it triggers release is the template's release.policy decision (boundary_event ∉ release_boundaries(template) ⇒ no-op). The kernel never bakes in "terminal = release"
deferred (later)
a boundary past terminal — merge_completed — when a LC3a post-completion action still needs the resource (v1: the worktree survives DONE for the post-DONE merge). The hook is parameterized: LC3a will emit that boundary event and call initiate_release(instance, merge_completed); only the action emitting the event is later. Operator delete is not such a boundary — it is a separate storage/lifecycle intent that drives force_release in LC4
not the API
an operator never calls "release"; it issues an intent. A v1 merge results in a merge_completed boundary event and the kernel initiates release after it; a v1 delete is handled by LC4 force_release — an operator storage/lifecycle intent, not a boundary event
release_failed(ref) is the load-bearing refinement: a failed release (initiation or provider, possibly partial) is not a return to ready. The ref is a retriable release handle — a flagged resource leak pending retry — never a runtime that can be dispatched to an actor again.
Three meanings of "commit", kept in separate namespaces (no rename needed): Committed(...) is the kernel outcome — the kernel accepted and durably committed a state/transcript mutation (the same atomic COMMIT the release marker uses); COMMIT is an authored workflow / operator event in this anchor (the commit_pending resume); and git commit is a later LC3a action. Same word, three layers — the namespaces stay distinct, so no term is renamed.
