② Runtime resource teardown / provider close

The symmetric half of L0e: provision built the runtime_context (worktree / branch / tmux session); ② releases it. The kernel tracks a release obligation for every ready runtime_context and closes L0d/e's current dangling provision (we provision a worktree and never release it). A kernel-touching slice — the pseudocode diffs against L3. Conceptually this still completes L0e's runtime-context lifecycle; realized here, after ① (so release is pure), before L4 (children inherit the contract).

Release mirrors provision, exactly. A declared release boundary (the template's release.boundaries, e.g. [terminal] for this anchor) initiates provider.release(ref) asynchronously, correlated by request_id, completed by a RUNTIME_CONTEXT_RELEASED kernel event — the same shape as provision → RUNTIME_CONTEXT_READY. Release is orthogonal to lifecycle: it moves only the runtime_context axis (ready → releasing → released), never kernel_status / current_step / terminal_disposition.

What the kernel can promise. With no auto-retry / timeout / watchdog in this slice (that is L9), the kernel does not promise the resource is eventually released. It promises the weaker, true thing: the release obligation is tracked through failure until discharged, never dropped silently — a run is not "closed" until RUNTIME_CONTEXT_RELEASED, and any failure (initiation or provider) lands in release_failed(ref), a retriable release handle, not a usable runtime. Eventual liveness is the L9 retry slice.

Shape Provision ↔ release symmetry (teardown aid)

The release path is the provision path read backwards — same async/correlated/event shape, plus a failure state that keeps the obligation visible:

  PROVISION (L0e)                                  RELEASE (②, the mirror)
  ──────────────────────────────                   ──────────────────────────────
  START, required(spec)                            declared release boundary reached (e.g. terminal)
        │ provider.provision (async)                     │ release_safe ✓ , provider resolved
        ▼                                                ▼ provider.release (async)
  requested(req)                                   releasing(req, ref)
        │ RUNTIME_CONTEXT_READY                           │ RUNTIME_CONTEXT_RELEASED
        ▼                                                ▼
  ready(ref) ──────────────── carries the release obligation ──────────────▶ released  (tombstone)

  state machine (the runtime_context axis only — kernel_status is untouched):
    none ─▶ requested(req) ─▶ ready(ref) ─▶ releasing(req, ref) ─▶ released
                                  ▲                  │
                                  └── (provided)     ▼  initiation OR provider failure
                                            release_failed(ref)   ← retriable release handle, NOT a usable runtime
                                                                    (obligation retained; retry = L9)
The boundary is a declared event, not a kernel default, not the release API, and not an operator command: this anchor declares terminal in release.boundaries; a later workflow declares merge_completed / another event. An operator issues an intent: a v1 merge results in a merge_completed boundary and the kernel initiates the release after it — never conflating the boundary-causing command with the release operation. A v1 delete is instead handled by ④ force_release (an operator storage/lifecycle intent, not a declared boundary).

Runtime A concrete trace

The local-pair-v0 run reaches done; this template declares terminal in release.boundaries (no post-completion action needs the worktree), so it is released right there:

1
the commit_pending wait resumes on COMMIT → done
COMPLETE sets TERMINAL(done) inside the atomic commit; the terminal transition emits the terminal boundary event. After the commit lands, RECEIVE's post-commit hook calls initiate_release(instance, terminal), which proceeds because terminal ∈ this template's declared release.boundaries and runtime_context = ready(ref). The provider side effect runs only post-commit, never inside the mutation; the instance is already terminal, so release runs orthogonally
2
initiate_release checks the precondition and dispatches
release_safe(instance) holds (① INV-5: no canonical ref points into the worktree — the record, evidence outcomes, and durable evidence refs are all off in T1/T3) → resolve the pinned-template provider → persist the marker first in a CAS atomic commit (REQUIRE ready(ref) → releasing(req, ref) + RUNTIME_CONTEXT_RELEASING), then dispatch provider.release(ref) async post-commit — so the durable correlation target exists before the provider can fire back
3
the provider finishes; RUNTIME_CONTEXT_RELEASED(req, ok) arrives
correlation ✓ (the release we dispatched) → runtime_context ← released (tombstone), append RUNTIME_CONTEXT_RELEASED { evidence_refs }. The worktree / branch / tmux session / registry entry / locks are gone; the durable run record (T1) and evidence (T3) are untouched. The obligation is discharged
4
(an alternate run) the provider reports a partial failure — worktree removed, branch deletion failed
RUNTIME_CONTEXT_RELEASED(req, failed) → runtime_context ← release_failed(ref, reason) + RUNTIME_CONTEXT_RELEASE_FAILED with evidence. The ref is now a retriable release handle, not a usable runtime; the obligation is retained (tracked, not dropped). A retry / timeout / watchdog is L9. The instance stays TERMINAL(done) regardless — release failure cannot un-terminate it
A pre-dispatch failure (not-safe / provider unavailable) lands in release_failed(ref) before any marker. A dispatch error (the dispatch itself errors after the marker committed) is recorded by a follow-up versioned transition (releasing → release_failed, guarded by REQUIRE releasing) — not the same commit as the marker; only a crash in the persist→dispatch window leaves an orphan releasing, which L9 reconciles. A CANCEL or FAIL terminal emits the same terminal boundary event; this anchor releases its provisioned worktree because terminal is a declared boundary — a template that did not declare it would keep the obligation open.

The provider's release bundle (what it provisioned) is opaque to the kernel — worktree, temporary branch, tmux / runtime session, remote clone, plus engine support data (runtime-session registry entry, watchdog markers, locks). The kernel tracks only the obligation, the correlation, and the state; the mechanics are the provider's, exactly as on the provision side (the locator stays provider-defined).
Release policy — the release contract is the provision contract's declared pair
policy: required
the kernel owns the release: a release obligation exists and must be discharged at one of the declared boundaries (non-empty — else Rejected(release_boundaries_empty) at load). This is the worktree anchor: boundaries: [terminal]
policy: retained
the resource is intentionally kept past the run — an explicit ownership decision, not "cleanup later". No kernel release obligation; the kernel never auto-releases
policy: external
the resource lifecycle is owned by an external system / provider policy; the kernel is not the release-owner. No kernel release obligation
load-time rule
a teardown-managed provider (worktree = yes) MUST declare runtime_context.release — provision implies a declared release path (Rejected(release_policy_undeclared) otherwise). A shared / external provider opts out. Keyed on the provider, not on runtime_context: required — so the retained / external space is preserved. Boundary coherence is enforced too: under required, boundaries must be non-empty; under retained / external they must be absent or empty (a non-empty list ⇒ release_boundaries_not_allowed) — a config that looks like release but never fires is rejected, not silently ignored
Release boundary — a declared event, distinct from the command that causes it
declared, per policy
under policy: required, release.boundaries lists the events that discharge the obligation. The anchor declares [terminal] (no post-completion action needs the worktree yet); a v1-faithful later form is [merge_completed] — operator delete is not a template boundary; it drives force_release in ④
terminal is an event, not a default
the terminal transition emits a terminal boundary event; whether it triggers release is the template's release.policy decision (boundary_event ∉ release_boundaries(template) ⇒ no-op). The kernel never bakes in "terminal = release"
deferred (later)
a boundary past terminal — merge_completed — when a ③a post-completion action still needs the resource (v1: the worktree survives DONE for the post-DONE merge). The hook is parameterized: ③a will emit that boundary event and call initiate_release(instance, merge_completed); only the action emitting the event is later. Operator delete is not such a boundary — it is a separate storage/lifecycle intent that drives force_release in ④
not the API
an operator never calls "release"; it issues an intent. A v1 merge results in a merge_completed boundary event and the kernel initiates release after it; a v1 delete is handled by ④ force_release — an operator storage/lifecycle intent, not a boundary event
release_failed(ref) is the load-bearing refinement: a failed release (initiation or provider, possibly partial) is not a return to ready. The ref is a retriable release handle — a flagged resource leak pending retry — never a runtime that can be dispatched to an actor again.
Three meanings of "commit", kept in separate namespaces (no rename needed): Committed(...) is the kernel outcome — the kernel accepted and durably committed a state/transcript mutation (the same atomic COMMIT the release marker uses); COMMIT is an authored workflow / operator event in this anchor (the commit_pending resume); and git commit is a later ③a action. Same word, three layers — the namespaces stay distinct, so no term is renamed.

Invariant New at ②

Added rules
release obligation is never dropped silently
under release.policy: required, every ready(ref) carries a release obligation that is tracked through failure until discharged (RUNTIME_CONTEXT_RELEASED); a failed release — initiation or provider — does not close it, it is retained in release_failed(ref). This closes L0d/e's dangling provision. (retained / external carry no obligation — explicit ownership.) Not "eventually released": auto-retry / timeout / watchdog (the liveness guarantee) is L9
release_failed is a handle, not a runtime
release_failed(ref) is a retriable release handle, not a usable runtime — a terminal instance with a failed release is a flagged resource leak pending retry, never re-dispatchable as a live context. A partial release (worktree gone, branch not) lands here, not back in ready
release-safe precondition
release initiates only when release_safe(instance) holds (① INV-5: no canonical-record ref points into the resource). ① guarantees it by construction; ② asserts it fail-closed — an unsafe release becomes release_failed(precondition), never an orphaned canonical ref
release is orthogonal to lifecycle
release moves only the runtime_context axis (ready → releasing → released | release_failed); it never changes kernel_status / current_step / terminal_disposition. A terminal instance stays terminal whether release succeeds, fails, or is still in flight
release initiation is post-commit
the provider side effect is never inside an atomic commit: the transition commits first, and if that committed outcome emits a declared release boundary, RECEIVE's post-commit hook initiates the release only after the commit landed. A CAS-failed transition returns Rejected/Stale and emits no boundary; a duplicate boundary hook is a no-op via initiate_release's ready(ref) guard — whereas a duplicate or stale RUNTIME_CONTEXT_RELEASED event is rejected on the correlation REQUIRE (two distinct mechanisms)
single-winner release initiation (CAS)
every state write in initiate_release is a COMMIT atomically at expected_version with REQUIRE ready(ref) inside — the releasing(req, ref) marker and the two pre-dispatch failure transitions (not-safe, provider-unavailable) alike. So concurrent boundary events on the same ready(ref) race on one version: exactly one applies (marker or failure), the rest reload, observe non-ready, and no-op. The marker is persisted before dispatch, so the correlation target exists before the provider can fire; the dispatch-error follow-up is itself a versioned commit guarded by REQUIRE releasing(request_id, ref), so a racing RUNTIME_CONTEXT_RELEASED never gets a wrong release_failed
correlated + idempotent
the RUNTIME_CONTEXT_RELEASED event correlates by request_id against releasing(req, ref) + CAS, exactly like RUNTIME_CONTEXT_READY; a stale or duplicate release event is rejected
teardown-managed ⇒ release policy declared
a teardown-managed provider (worktree = yes) MUST declare runtime_context.release at definition load (validate_release_policy): policy: required needs non-empty boundaries, retained / external are explicit no-obligation choices, absent ⇒ Rejected(release_policy_undeclared). Keyed on the provider, not on runtime_context: required — preserving the retained / external space
boundary is declared, not hardcoded
the kernel reads the declared release.boundaries (under policy: required); it does not hardcode terminal as the release instant. The terminal transition only emits a terminal event — a possible boundary, acted on solely if declared. The boundary is an event (terminal ｜ merge_completed ｜ later), distinct from the operator command that produces it (operator delete is not a boundary — it drives force_release in ④)

Absent Still not here

No eventual-liveness guarantee — no auto-retry, backoff, timeout, or watchdog on a release_failed obligation; the kernel tracks it but does not re-drive it. The retry that turns "tracked" into "eventually discharged" is later → L9
No deferred release boundary realized — the parameterized hook is in (initiate_release(instance, boundary_event), guard boundary_event ∉ release_boundaries(template)), but no post-completion action emits a non-terminal boundary yet; the merge / commit actions that do are → ③a
No retained / external release policy exercised — the policy vocabulary and load-time rule are in, but the anchor only uses required; a long-lived (retained) or externally-owned (external) runtime_context is a later, explicit ownership choice → later
No workflow actions — the type: action steps that run git commit / merge (and emit a deferred boundary like merge_completed), perf-test, publish, notify → ③a / ③b
No archive / export / purge — the record-purge half of v1 delete is a storage-axis op, not resource teardown → ④
No provider internals — the git worktree / branch / tmux removal mechanics are the provider's, opaque to the kernel, exactly as on the provision side → impl
No remote / distributed release proofs — a remote or async release with verifiable completion (the merge-as-distribution concern) is later → L8 / L10
No child release fan-out — a child is just another runtime_context the same contract releases; L4 multiplies the count, not the contract → L4
