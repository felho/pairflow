LC1 Durable run record / storage scope

A cross-cutting placement/authority contract, not a kernel step — no new handler, no new transcript entry, no template config. It declares where each kind of run datum canonically lives and the rules that keep teardown (LC2) and archive (LC4) from re-entangling. Conceptually this completes L0e's runtime-context lifecycle on the storage side; realized here, at the forcing point before L4 (children must inherit a durable record), per the RESUME_WAIT precedent — we do not renumber L0e. The central artifact is the Canonical Home Table.

The whole topic in one line: canonical run history is written during the run, into durable storage; teardown only releases runtime resources — teardown is never the step that preserves history. Operationally checkable as: no canonical-record ref points into a resource being released. This slice guarantees that by construction; LC2 Teardown only asserts it, fail-closed.

One genuinely new rule. Most of this slice makes an existing boundary explicit — v3 already treats the transcript/instance as durable abstract stores. The single new runtime-affecting rule is the evidence-ref discipline (INV-3): a canonical record entry may reference an evidence blob only by a durable ref into the evidence store, never by a path into the ephemeral workspace. That one rule is exactly what closes the v1 evidence-loss bug.

Shape Four homes, one release cut (storage-scope aid)

The canonical truth (T1/T3) is born durable and survives teardown. The state projection (T2) is not a canonical home — it is derived: droppable and rebuildable from T1, or a sealed snapshot anchored to T1. Only the runtime workspace (T4) is released — safe precisely because nothing canonical's only copy lives there. The shape of the table below is the invariant.

The v1 "archive" is a placement symptom, not a primitive: it exists only because keep-worthy history lives in a deletable folder. Once T1 is a born-durable authority, archive becomes optional ops (LC4), never the preservation path — the same bias-removal as the L3 "finalization" seam.

Pseudocode The placement contract — three checkable predicates

A standalone contract (empty baseline — it is not a kernel handler; it constrains writes the kernel/runtime already make). The predicates are what make the invariants fail-closed:

Three predicates, three invariants: evidence_ref_ok (INV-3, the new rule), projection_authoritative (INV-4, the sealed-snapshot rule), and release_safe (INV-5, the handle LC2 grabs). The first is enforced at the write site; the last is asserted by LC2 before any release.

Sealed projection snapshot — a closed, verifiable projection, not a second truth
shape
sealed_snapshot { state, source: { record_ref, version /* range / hash */ }, sealed_at: <declared boundary> } — a materialized T2 view that may be read as authoritative without replay
constraints
made at a declared boundary (e.g. terminal); anchored to its T1 source by record_ref + version (range / hash); it never overwrites T1; on audit/replay T1 remains the deeper authority. The minimum bar: a sealed snapshot must anchor to a T1 source range/version — otherwise it is a cache only
Default reading: T2 is a cache; a consumer that needs the authoritative state either reconstructs from T1 or reads a sealed snapshot. "Snapshot-authority" is deliberately narrow — a sealed, verifiable projection, not a rival source of truth. This is the placement contract; there is no author-facing template config for it — it constrains kernel/runtime writes, not the workflow definition.

  • Scenario coverage: every datum in the Canonical Home Table maps to exactly one home; the canonical homes (T1/T3) survive runtime teardown; the T2 projection is rebuildable from T1 (or a sealed snapshot anchored to it), not canonical on its own; only T4 is released.
  • Invariant coverage: born-durable record ✓; no workspace-sole-truth ✓; evidence-ref discipline ✓; projection subordination (incl. sealed snapshot anchored to T1) ✓; release-safe by construction ✓ — and all L0a–L3 invariants still hold (this slice adds no handler).
  • Accepted tradeoff: the durable-write mechanism, storage backend, and archive/retention are out — this slice fixes placement & authority only. The genuinely new code is the one evidence-ref rule.
  • Known gaps (intended): release mechanics (LC2), workflow actions (LC3a commit/merge · LC3b general), archive/export/purge (LC4), backend choice (impl), multi-instance/central stores (L11+). Each is in Absent.
  • Decision: accepted as the LC1 baseline (light evidence per playbook §2.1); LC2 Teardown builds directly on INV-5.
