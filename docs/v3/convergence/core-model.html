V3 Core Model — built one level at a time

The convergence companion to concept-braindump.md. The braindump is the raw material (divergence); this distils a coherent, buildable core by growing it from the smallest possible kernel, one capability per level. Each level is shown through three parallel views, plus what it deliberately leaves out.

How to read this

Every level adds exactly one capability and is rendered through three views, so you can follow the model and its configuration as complexity grows — rather than absorbing it all at once:

  • Runtime  a concrete trace — what events arrive and what the kernel does, step by step.
  • Domain  the model (DDD) — entities, aggregate boundaries, and how they relate.
  • Config  the template/definition that declares the behaviour.
  • Absent  what is deliberately not here yet, and which level introduces it.
The ramp is also a coherence test. If each new capability sits cleanly on the existing model (a new entity, or a new field — not a rewrite), the core is sound. If a capability forces the structure to be torn up, that is a signal the core is wrong. Levels are greenfield kernel concepts; occasional reality checks against the v1 code (src/v11/…) keep them honest.

L0 Local pair loop

The smallest thing that is still a workflow: two roles passing work back and forth on one machine, with no gates, no permissions, no humans-in-the-loop.

One implementer and one reviewer alternate. The implementer does work and passes; the reviewer either passes back (found something to fix) or declares convergence (nothing left). That is the entire system at L0 — the loop and nothing guarding it. The reviewer's judgement, not a formal gate, ends the loop; the gate arrives at L2.

Runtime A concrete trace

A two-round run that converges on the second review:

1
START — instance created from template local-pair-v0
state: current_step=implement, round=1, status=RUNNING
2
implementer (codex) works → emits PASS
EventEnvelope { type: PASS, actor: codex, payload: { summary, ref } }
3
kernel dispatches → transition implement → review
appends envelope to transcript; state: current_step=review
4
reviewer (claude) finds issues → emits PASS
EventEnvelope { type: PASS, actor: claude, payload: { findings } }
5
kernel dispatches → transition review → implement (back)
state: current_step=implement, round=2
6
implementer fixes → emits PASS → transition implement → review
state: current_step=review
7
reviewer is satisfied → emits CONVERGED
EventEnvelope { type: CONVERGED, actor: claude }
8
kernel dispatches → transition review → done
state: status=DONE — terminal; transcript is the complete history
The kernel only ever does three things here: route the envelope to a transition, append it to the transcript, update the instance state. No decision logic of its own yet — the actors decide, the kernel records and moves.

Domain The model

Two aggregates: the template (the definition, immutable while running) and the instance (the run). The EventEnvelope is the command/event that drives the instance through the kernel.

Template aggregate — the definition (immutable at runtime)
WorkflowTemplate root
id, roles[], steps[], start
Step
id, role, transitions { on_pass, on_converged }
Role
name, actor binding
Actor
id (codex / claude)
Instance aggregate — the run (mutable, append-only history)
WorkflowInstance root
id, template_id, current_step, round, lifecycle_status
Transcript
append-only ordered EventEnvelopes
LifecycleStatus (value)
CREATED → RUNNING → DONE
Message — crosses the boundary
EventEnvelope
event_id, instance_id, type (PASS / CONVERGED), actor, payload

Relationships: a Template defines Steps bound to Roles, each filled by an Actor. A WorkflowInstance is created from a Template and owns its Transcript. An EventEnvelope targets an instance; the kernel applies it as a transition and appends it to the transcript.

Why two aggregate roots. The definition and the run have different lifecycles and consistency rules: the template is shared and immutable while instances run; the instance mutates but its transcript is append-only. This split is the seed of the braindump's lifecycle-vs-execution-position (§2.2) and immutable-artifact / append-only-transcript (§15.1) decisions — already present at L0, before any of the machinery that needs them.

Config The template

The whole of L0's behaviour is this declaration. No engine code encodes the loop — the loop is the transitions:

template:
  id: local-pair-v0
  roles:
    implementer: { actor: codex }
    reviewer:    { actor: claude }
  start: implement
  steps:
    - id: implement
      role: implementer
      on_pass: review
    - id: review
      role: reviewer
      on_pass:      implement   # found something → back
      on_converged: done
Template = configuration, not code (braindump §2.1). L0 is "just one preset"; the engine reads transitions from data. A reality check against v1: this is the review-loop the v1 code hardcodes — here it is already external data.

Absent Deliberately not here yet

The border of L0 — each of these is a later level, and seeing the border is half the point:

No capability check — anyone can emit anything → L1
No gate / policy — reviewer decides convergence directly → L2
No round limit — formalised with the round gate → L2
No human gate / approval → L3
No help subflow / Ask → L4
No trigger — manual start only → L5
No channels / task inbox — direct emit → L6
No wait condition / correlation → L7
No gatekeeper / federation → L8+
No grants, sticky labels, trust, rollback → L9+
