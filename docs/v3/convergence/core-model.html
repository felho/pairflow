V3 Core Model — built one level at a time

The convergence companion to concept-braindump.md, approach.md (the method + roadmap; source of truth for the ramp), and design-method-playbook.md (how to use DDD, pseudocode, and evidence while designing). Grows from the smallest kernel, one coherent capability per level, each shown through multiple lenses.

How to read this

Each level adds one coherent capability (a single concept, or an inseparable cluster — not a convenience bundle) and is rendered through multiple lenses, so the model and its rules can be followed as complexity grows rather than absorbed all at once:

  • Runtime  one concrete trace — what events arrive and what the kernel does, step by step.
  • Pseudocode  the general rule behind the trace, including branches the trace does not exercise (duplicate, stale, invalid, reject, no-op).
  • Domain  the model (DDD) — entities, aggregate boundaries, relationships.
  • Invariant  hard rules stated at this level, not deferred (idempotency, atomicity, store semantics).
  • Config  the template/definition that declares the behaviour.
  • Absent  what is deliberately not here yet, and which level introduces it.
Two coherence tests run as the ramp grows. Structurally: if a new capability sits cleanly on the model (a new entity or field, not a rewrite), the core is sound. Algorithmically: if it slots into the pseudocode as a small guard/branch, the abstraction holds; if the pseudocode must be torn apart, the earlier level hid a missing concept. Some primitives mature in stages (the Ask: human-decision → agent-help → general; the wait: internal-deterministic → external-fuzzy). Levels are greenfield kernel concepts; reality checks against the v1 code (src/v11/…) keep them honest.

L0a Kernel skeleton

The smallest mechanically-correct kernel: routing + state, with the foundational invariants in place — but no agent guidance yet (that is L0b).

Two roles alternate on one machine; the kernel routes their events through transitions and records everything. At L0a the kernel does only route → atomic-commit (append + update), plus enforce the invariants below. There is deliberately no notion yet of what an actor should do; an agent here would route correctly but have no task. That gap is filled at L0b, and naming it is half the point.

L0a is a reactive kernel slice: it handles envelopes that arrive (from a manual driver here) but does not dispatch work or wake actors — the trace's "emits" is an external stimulus, not the kernel activating anyone. Closing that loop (handing the next work item to the next actor — its task, the version it sees, and the protocol outputs the step exposes) is L0b's dispatch.

Why two aggregate roots. Definition and run have different lifecycles and consistency rules: the template is shared and immutable while instances run; the instance mutates but its transcript is append-only. This split is the seed of the braindump's lifecycle-vs-execution-position (§2.2) and immutable-artifact / append-only-transcript (§15.1) decisions — present at L0a, before any machinery that needs them.

L0b Actor binding + context packet

Closes the loop L0a left open: the kernel resolves who acts next and hands them a minimal context packet — so the skeleton becomes a usable system.

L0a was a reactive kernel: it processed envelopes but woke no one. L0b adds the other half of the loop. On instance start, and after every commit, the kernel produces a DispatchIntent — the next actor plus a context packet telling it: its task, the version it sees, what to do this step, what it received, and which protocol outputs exist. The full cycle: start → initial DispatchIntent → actor works → envelope → handle → next DispatchIntent. The kernel still only produces the packet; a local/manual driver delivers it (durable channels are L8).

Runtime A concrete trace

The same two-round run, now driven by dispatch — plus a stale step where an actor replies from an outdated packet:

1
START_INSTANCE(local-pair-v0, task) — binding snapshot { implementer→codex, reviewer→claude }
invariant ✓ binding covers all roles; create at implement, version=1; commit creation → derive DispatchIntent { actor: codex, packet: task, instruction "build it", version=1, available_ops=[PASS] }
2
codex works → emits PASS, expected_version=1
kernel: new op_id ✓, 1 = 1 ✓ → commit implement → review (1 → 2) → derive DispatchIntent { actor: claude, handoff: codex diff, instruction "review it", version=2, available_ops=[PASS, CONVERGED] }
3
claude reviews, finds issues → emits PASS, expected_version=2
kernel: 2 = 2 ✓ → commit review → implement (2 → 3), round=2 → DispatchIntent { codex, handoff: claude findings, version=3, available_ops=[PASS] }
4
codex replies from an old packet → emits PASS, expected_version=2
kernel: 2 ≠ 3 (instance is at 3) → Stale(3). The actor acted on an outdated view; it must refresh to the version-3 packet. (idempotency checked first — this is not a duplicate, the op_id is new)
5
codex refreshes → re-emits PASS, expected_version=3
kernel: 3 = 3 ✓ → commit implement → review (3 → 4) → DispatchIntent { claude, version=4, available_ops=[PASS, CONVERGED] }
6
claude is satisfied → emits CONVERGED, expected_version=4
kernel: 4 = 4 ✓ → commit review → done (4 → 5); status=DONE — terminal, no DispatchIntent
The loop is now closed end-to-end: every commit either produces the next DispatchIntent or, at a terminal target, produces none. Step 4 shows why the actor-visible version matters — an actor working from a stale packet is caught, not silently committed.

L0b pseudocode

What the pseudocode surfaces: the start was an implicit hole at L0a — here START_INSTANCE makes the first dispatch explicit, closing the loop at the front too. And the commit/derive split is explicit: the COMMIT writes state, the DispatchIntent is a kernel output computed after, so the store stays a dumb recorder, never a deliverer. START_INSTANCE is an abstraction: v11 separates create and start; the core model deliberately shows the persisted-initial-assignment + first-activation core as one step.

L0c Agent run configuration

Resolves how the assigned actor is run — the effective AgentConfig — so the right kind of agent does the work, not a vanilla one.

L0b decides who acts and hands them a packet, but carries agent_config raw. L0c answers how: it resolves the effective config by cascade (role default → step override → run override), puts the resolved config in the packet, and records which config the kernel issued in the transcript. This closes the v1 gap where "use sub-agent X" was implicit and merely assumed. It stays a portable run intent — actual provisioning, skill loading, and attestation are later layers.

L0d Instance lifecycle + activation

Separates the instance's macro-lifecycle from its position in the step graph: a run is created, activated once its runtime context is ready, may hold in a typed WAITING state, and ends in exactly one terminal disposition. The kernel also stops pretending every input is an actor envelope.

Until now the kernel modelled only the inside of an active run (current_step) and assumed every input was an actor envelope. L0d adds kernel_status as a second stored axis next to current_step, names three input source classes (actor / operator / kernel), guards actor emits to ACTIVE, and folds v1's overloaded RUNNING / PREPARING_WORKSPACE / ideation states into kernel_status + a typed wait. Workflow "phase" stays derived, never stored. It is an L0-family concern (foundational lifecycle): it diffs against the L0c kernel, and its lifecycle guard sits ahead of the role/action checks that L1 later layers on the full L0e kernel.

Pseudocode The rule behind the trace

A source-routed entry, the lifecycle/activation handlers, and one guard prepended to HANDLE — the first dispatch moves out of instance creation into activate. The lifecycle handlers below omit the commit wrapper for brevity — each mutation is an atomic CAS commit under instance.version unless noted:

START_INSTANCE splits into CREATE_INSTANCE (record + binding-coverage invariant, no dispatch) and the activation path; binding resolution moves out of the kernel to the start path (a plain default-actor + override merge now, the full pre-kernel resolution at L0f), so CREATE_INSTANCE takes the binding as input and only validates coverage. The first dispatch_intent now leaves activate, so a created-but-unactivated instance never dispatches. The lifecycle guard sits right after idempotency (so a duplicate of an already-applied op is still Duplicate, not not_active) and before the stale check (role/action authorization arrives at L1, which builds on this kernel). The three terminal paths differ by origin: COMPLETE is an internal helper HANDLE calls when a transition lands on a terminal step (done is never routed), FAIL is a kernel event, CANCEL an operator intent. Every lifecycle mutation here commits atomically under instance.version just like HANDLE; a replayed actor op (same op_id) is Duplicate, and the lifecycle transitions are single-shot — a second START or a stale RUNTIME_CONTEXT_READY fails its precondition and mutates nothing (a guard rejection, not a silent no-op).

L0e Runtime context spec / provider contract

A workflow may declare the runtime context it needs; if it does, a named provider fulfils it and the kernel exposes an actor-facing projection in the packet. A context-free workflow declares none and activates without provisioning. The third instance of the L0c pattern — portable intent → named fulfiller → packet projection.

L0d gave the runtime-context a lifecycle slot (none | requested | ready) and a readiness gate, but left what is requested and who fulfils it abstract. L0f Project/repository configuration & definition resolution

A repository declares which workflow templates it runs and supplies repo-scoped values for the typed slots a template declares. This is a pre-kernel resolution layer: it runs before CREATE_INSTANCE and produces its inputs — it adds no kernel handler.

L0e let a template declare a runtime-context requirement with a config block of literal values (base_branch, branch_pattern). But those belong to the repo where you deploy, not to the portable definition. The same split surfaces for v1's bootstrap / test commands — repo toolchain values the workflow references but cannot define. L0f separates the two responsibilities: (J1) definition resolution — pick and pin the template (explicit or repo default, from a source) — and (J2) slot/value resolution — fill the template's typed slots from a repo-local ProjectConfig through a cascade. The fields with a meaningful universal default may stay template defaults; the cascade resolves the rest.

Not the kernel. The kernel still knows only Template + Instance. L0f is a function RESOLVE_START(command, project_config) → ResolvedStartRequest | Rejected that runs ahead of the kernel and hands a resolved bundle to CREATE_INSTANCE; later START and provider provisioning read the applied values from the pinned resolved definition through normal template loading. No instance, transcript, or version exists during the pass — a rejection means nothing was created.

L2 Gate / policy — runtime authorization

A legitimate emit is not yet a permitted one. Before the commit, an ordered pipeline of policy gates decides whether the run's current state allows this action — and a block never burns a round.

By now the kernel has its full L0 foundation and L1 authorization. L1 decided whether an emit is structurally legitimate (role × current_step); L2 adds a runtime decision on top — even a legitimate emit may be blocked by policy given the run's state. This is the operational core of "the workflow is the boss": an early CONVERGED is rejected even though the reviewer judged it ready. The gate is a fourth filter — transition exists (L0b) → role/action authorized (L1) → policy allows now (L2) → commit. Two orthogonal axes organize the space: implementation = declarative | packaged | process and execution = inline | deferred. L2 core realizes only the inline pipeline with declarative DSL primitives and packaged pure pairflow.* policies. Inline external/process gates are L2a; deferred execution is a separate later lifecycle slice (named, not numbered); the route verdict (workflow redirection) is a later routing slice (L3).

L2a External / process gate execution

L2 core declared the external.* gate but rejected it at run. L2a realizes the inline process path — a gate that spawns a process in the workspace, under a bounded timeout, and maps its result to allow | warn | block. The deferred path stays a later slice.

L3 Human decision Ask — approval gate

L2 / L2a / L2b gated and communicated machine policy. L3 introduces the human as decision-maker: a human_gate step parks the instance in WAITING(human_decision), records a DECISION_REQUEST for the bound operator, and the operator’s decision routes the workflow. The gate's decisions map is generic — approve | request_rework are just this anchor's keys; the kernel knows no decision names. The narrowest Ask — not a general human platform.

The human is a different mover. A decision is not an actor envelope through HANDLE’s ACTIVE path; it is an operator-intent on a WAITING(human_decision) state — a sibling of KICKOFF. So ACTIVE stays honest ("an agent is working") and WAITING means "blocked on a human." The v1 reality check shows "human" is at least three contracts; L3 takes only the approval gate (the agent-initiated ask-human/help reply is L5).

Scope note (bare wait + its resume). L3 introduces the minimal type: wait shape for the post-approval anchor (commit_pending) and the minimal resume that closes it: arrival parks WAITING(step.wait.kind) (no actor output), and RESUME_WAIT moves forward on a matching event via the step's on_resume route. This is the bare-wait dual of the human_gate decision wait — the missing other half of the WAITING axis, surfaced now because commit_pending would otherwise dead-end. What remains later: result payloads, the resume action (e.g. actually running git commit), child-event resume sources (L4), and timeouts / external-or-fuzzy correlation (L9). It is not a special seam: enough WAITING-kind shapes already exist (kickoff_pending as the first specialized resume, the human_decision decision wait) that a one-off bare wait/resume would just reprise the finalization mistake.

① Durable run record / storage scope

A cross-cutting placement/authority contract, not a kernel step — no new handler, no new transcript entry, no template config. It declares where each kind of run datum canonically lives and the rules that keep teardown (②) and archive (④) from re-entangling. Conceptually this completes L0e's runtime-context lifecycle on the storage side; realized here, at the forcing point before L4 (children must inherit a durable record), per the RESUME_WAIT precedent — we do not renumber L0e. The central artifact is the Canonical Home Table.

The whole topic in one line: canonical run history is written during the run, into durable storage; teardown only releases runtime resources — teardown is never the step that preserves history. Operationally checkable as: no canonical-record ref points into a resource being released. This slice guarantees that by construction; ② Teardown only asserts it, fail-closed.

One genuinely new rule. Most of this slice makes an existing boundary explicit — v3 already treats the transcript/instance as durable abstract stores. The single new runtime-affecting rule is the evidence-ref discipline (INV-3): a canonical record entry may reference an evidence blob only by a durable ref into the evidence store, never by a path into the ephemeral workspace. That one rule is exactly what closes the v1 evidence-loss bug.

② Runtime resource teardown / provider close

The symmetric half of L0e: provision built the runtime_context (worktree / branch / tmux session); ② releases it. The kernel tracks a release obligation for every ready runtime_context and closes L0d/e's current dangling provision (we provision a worktree and never release it). A kernel-touching slice — the pseudocode diffs against L3. Conceptually this still completes L0e's runtime-context lifecycle; realized here, after ① (so release is pure), before L4 (children inherit the contract).

Release mirrors provision, exactly. A declared release boundary (the template's release.boundaries, e.g. [terminal] for this anchor) initiates provider.release(ref) asynchronously, correlated by request_id, completed by a RUNTIME_CONTEXT_RELEASED kernel event — the same shape as provision → RUNTIME_CONTEXT_READY. Release is orthogonal to lifecycle: it moves only the runtime_context axis (ready → releasing → released), never kernel_status / current_step / terminal_disposition.

What the kernel can promise. With no auto-retry / timeout / watchdog in this slice (that is L9), the kernel does not promise the resource is eventually released. It promises the weaker, true thing: the release obligation is tracked through failure until discharged, never dropped silently — a run is not "closed" until RUNTIME_CONTEXT_RELEASED, and any failure (initiation or provider) lands in release_failed(ref), a retriable release handle, not a usable runtime. Eventual liveness is the L9 retry slice.

L0f+ Run-scoped mode / variants

A single workflow can run in more than one mode (v1's code | doc) — the same step graph, but different gates and context. This is not a runtime kernel branch: a start-fixed, run-scoped mode that L0f resolution normalizes into a pinned, mode-specific ResolvedDefinition, so the kernel runs a mode-agnostic template and never sees the mode at runtime. One mechanism — the modes: membership tag — on two carriers: a gate binding and a context ref. An L0f-family extension, living entirely in the pre-kernel resolution pass.

Why two surfaces, not three. An earlier draft added a third surface — a run-level mode_profiles policy-ref map. It was dropped: in this kernel a policy is only ever applied at a gate (uses: = the policy, config: = its parameters) — there is no global run-level policy engine, so a free-floating policy map had no consumer. Mode-specific policy instead rides a gate binding: a transition point may declare a [code] binding and a [doc] binding (same uses with different config, or a different uses); resolution keeps the mode's. The consumer is the surviving gate's evaluator — visible, not a dangling map. An L0f delta kept off the L0f / ③b baselines (the lenses diff against them and leave them untouched); L2 (gates) and L2b (context) are the pure consumers.

L4 Child workflow instances + internal lifecycle events

A workflow instance can spawn and link another full workflow instance, wait on it, and route on the child's lifecycle — delivered as an internal kernel event, not a poll. The child is a complete first-class instance (its own record, runtime_context, and ①②③④ lifecycle), not an embedded subflow. This is the WF-7 unlock (plan execution / pairflow self-hosting). The kernel core is narrow: five primitives — everything else (plan review, task split, approve/refine routing) is parent-template authoring on the primitives already built.

The boundary. L4 = the parent↔child instance link + the internal-lifecycle-event resume. ③ = process / LLM action routing inside the child (a failed merge can route to an agent step that resolves the conflict, then back). L3 = human / decision gates inside the child. So a child template can run all the way to done on its own — close, commit, merge, and recovery live in the child, not in the parent. v1's ExecutePairflowPlan + plan watch is the grounding anchor, but it is not the v3 child boundary: v1 stopped the programmed workflow at READY_FOR_HUMAN_APPROVAL and let an LLM orchestrate the rest; v3 pulls that into the child template.
