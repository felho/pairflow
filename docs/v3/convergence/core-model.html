V3 Core Model — built one level at a time

The convergence companion to concept-braindump.md, approach.md (the method + roadmap; source of truth for the ramp), and design-method-playbook.md (how to use DDD, pseudocode, and evidence while designing). Grows from the smallest kernel, one coherent capability per level, each shown through multiple lenses.

How to read this

Each level adds one coherent capability (a single concept, or an inseparable cluster — not a convenience bundle) and is rendered through multiple lenses, so the model and its rules can be followed as complexity grows rather than absorbed all at once:

  • Runtime  one concrete trace — what events arrive and what the kernel does, step by step.
  • Pseudocode  the general rule behind the trace, including branches the trace does not exercise (duplicate, stale, invalid, reject, no-op).
  • Domain  the model (DDD) — entities, aggregate boundaries, relationships.
  • Invariant  hard rules stated at this level, not deferred (idempotency, atomicity, store semantics).
  • Config  the template/definition that declares the behaviour.
  • Absent  what is deliberately not here yet, and which level introduces it.
Two coherence tests run as the ramp grows. Structurally: if a new capability sits cleanly on the model (a new entity or field, not a rewrite), the core is sound. Algorithmically: if it slots into the pseudocode as a small guard/branch, the abstraction holds; if the pseudocode must be torn apart, the earlier level hid a missing concept. Some primitives mature in stages (the Ask: human-decision → agent-help → general; the wait: internal-deterministic → external-fuzzy). Levels are greenfield kernel concepts; reality checks against the v1 code (src/v11/…) keep them honest.

L0a Kernel skeleton

The smallest mechanically-correct kernel: routing + state, with the foundational invariants in place — but no agent guidance yet (that is L0b).

Two roles alternate on one machine; the kernel routes their events through transitions and records everything. At L0a the kernel does only route → atomic-commit (append + update), plus enforce the invariants below. There is deliberately no notion yet of what an actor should do; an agent here would route correctly but have no task. That gap is filled at L0b, and naming it is half the point.

L0a is a reactive kernel slice: it handles envelopes that arrive (from a manual driver here) but does not dispatch work or wake actors — the trace's "emits" is an external stimulus, not the kernel activating anyone. Closing that loop (handing the next work item to the next actor — its task, the version it sees, and the protocol outputs the step exposes) is L0b's dispatch.

Runtime A concrete trace

A two-round run that converges on the second review, including a re-delivered event to show idempotency:

1
START — instance created from template local-pair-v0
instance store write; template_ref { id, version: 1 } snapshotted; state: current_step=implement, round=1, status=RUNNING, version=1
2
the implementer role emits PASS
EventEnvelope { event_id, op_id=a1, instance_id, type: PASS, actor_id (provenance), payload: { ref } }
3
kernel: (instance_id, a1) unseen → resolve transition implement → review
atomic commit — transcript append + state update under expected_version (1 → 2); current_step=review
3′
same PASS re-delivered (retry, op_id=a1)
kernel: (instance_id, a1) already in transcript → Duplicate, no-op. No second transition entry. (idempotency; a separate duplicate-delivery audit is optional/later)
4
the reviewer role emits PASS (op_id=b2, payload: findings)
kernel: resolve review → implement; atomic commit (2 → 3); round=2, current_step=implement
5
the implementer role emits PASS (op_id=c3) → implement → review
atomic commit (3 → 4); current_step=review
6
the reviewer role emits CONVERGED (op_id=d4)
kernel: resolve review → done; atomic commit (4 → 5); status=DONE — terminal
The kernel has no decision logic of its own yet — the actors decide, the kernel routes, records, and guarantees each accepted event is applied at most once per (instance_id, op_id) — duplicate delivery is a no-op (step 3′). (Not "exactly once": delivery may repeat; idempotency makes the apply effectively-once.) Convergence here is the reviewer's bare judgement; the formal gate arrives at L2.

Pseudocode The rule behind the trace

The trace shows one happy path. The pseudocode states the general rule, including the branches the trace never exercises:

HANDLE envelope → Outcome
  IF not valid_shape(envelope)            THEN RETURN Rejected(invalid_shape)

  instance ← instanceStore.load(envelope.instance_id)
  IF instance is none                     THEN RETURN Rejected(unknown_instance)
  template ← definitionStore.load(instance.template_ref)   # separate store; pinned immutable version

  # idempotency, key scope (instance_id, op_id)
  IF instance.transcript.has(envelope.op_id) THEN RETURN Duplicate   # no-op, no 2nd entry

  step   ← template.step(instance.current_step)
  target ← step.transitions[envelope.type]   # on_pass / on_converged
  IF target is none                       THEN RETURN Rejected(no_transition)

  # one atomic commit, CAS on instance.version
  COMMIT atomically at expected_version = instance.version:
    instance.transcript.append(envelope)
    instance.current_step ← target
    IF target is terminal THEN instance.status ← DONE
    instance.version ← instance.version + 1
  # on CAS conflict: restart HANDLE from load —
  #   re-check idempotency and re-resolve the transition;
  #   never re-commit a target computed from stale state

  RETURN Committed(instance.version)
What the pseudocode surfaces that the trace hid: three reject paths (invalid shape / unknown instance / no transition for this event in this step), the Duplicate no-op, and the exact atomic-commit boundary. And a question it raises: the CAS here is the kernel's own version counter (internal consistency). An actor-supplied expected_version — "I act against the version I last saw" → a true Stale rejection — needs the actor to know the version, which arrives with the context packet at L0b+. The pseudocode found a real boundary the trace could not: a small but genuine coherence signal.

Domain The model

Two aggregates — the template (definition, immutable while running) and the instance (the run) — and the EventEnvelope that drives the instance through the kernel.

Template aggregate — the definition (immutable at runtime)
WorkflowTemplate root
id, version, roles[] (names), steps[], start
Step
id, role, transitions { on_pass, on_converged }
Role (name only)
implementer / reviewer — no actor binding yet (L0b)
Instance aggregate — the run (mutable, append-only history)
WorkflowInstance root
id, template_ref { id, version }, current_step, round, lifecycle_status, version
Transcript
append-only ordered EventEnvelopes
LifecycleStatus (value)
CREATED → RUNNING → DONE
Message — crosses the boundary
EventEnvelope
event_id, op_id, instance_id, type (PASS / CONVERGED), actor_id (provenance), payload

Relationships: a Template (id + version) defines Steps bound to Role names. A WorkflowInstance is created from a Template — snapshotting its template_ref { id, version } so the run is pinned to an immutable definition — and owns its Transcript. An EventEnvelope targets an instance and carries an actor_id as provenance (who sent it); the kernel applies it as a transition. Which concrete actor fills a role, and how the next work item is dispatched, is L0b.

Why two aggregate roots. Definition and run have different lifecycles and consistency rules: the template is shared and immutable while instances run; the instance mutates but its transcript is append-only. This split is the seed of the braindump's lifecycle-vs-execution-position (§2.2) and immutable-artifact / append-only-transcript (§15.1) decisions — present at L0a, before any machinery that needs them.

Invariant Hard rules, stated now — not deferred

The braindump insists these belong in the foundation (§2.1): every later trigger and correlation level reaches back to them, so they must exist at L0a or they look retrofitted.

Idempotency & atomic commit
op_id idempotency
key scope (instance_id, op_id); re-applying a seen key is a no-op (trace 3′). Scope matters for the later remote relay (BC-08).
atomic transition commit
transcript append + state update are one logical commit under expected_version — never append-then-CAS as separate steps, or a CAS failure would diverge transcript from state
Store semantics — dumb store, kernel-owned meaning
definition store
templates, versioned
instance store
instance state + version
transcript / event log
append-only
artifact refs
content by reference
The store only persists and returns bytes (CAS-checked); it knows nothing about workflow semantics — the kernel owns all meaning (v2 BC-06). This is what lets the store be swapped later (file → SQLite → cloud) without touching the kernel.

Config The template

The whole of L0a's behaviour is this declaration — the loop is the transitions, no engine code encodes it:

template:
  id: local-pair-v0
  version: 1
  roles: [implementer, reviewer]   # names only; actor binding is L0b
  start: implement
  steps:
    - id: implement
      role: implementer
      on_pass: review
    - id: review
      role: reviewer
      on_pass:      implement   # found something → back
      on_converged: done       # 'done' is a terminal target, not a step
Template = configuration, not code (§2.1). L0a is "just one preset"; the engine reads transitions from data. roles are bare names — binding them to concrete actors is L0b. Reality check against v1: this is the review-loop the v1 code hardcodes — here it is already external data.

Absent Deliberately not here yet

The border of L0a — each is a later level, and seeing the border is half the point:

No actor binding / work-item dispatch — roles are bare names → L0b
No agent guidance — TASK, instruction, context-packet seed → L0b
No actor-supplied stale-intent — needs the context packet → L0b+
No capability check — anyone can emit anything → L1
No gate / policy — reviewer decides convergence directly → L2
No round limit — formalised with the round gate → L2
No human gate / approval → L3
No child workflows / internal events → L4
No help subflow → L5
No triggers — manual start only → L6
No grants / credentials → L7
No channels / task inbox / general Ask → L8
No wait / correlation → L9
No gatekeeper / federation → L10

Evidence Why we accept L0a for now

  • Scenario coverage: the local pair loop runs end-to-end (runtime trace); forward-compatible with WF-7, whose child workflows build on exactly this kernel (instance + transcript + atomic transitions).
  • Invariant coverage: idempotency (instance_id, op_id) ✓; atomic transition commit under expected_version ✓; dumb-store / kernel-owned semantics ✓; template/instance boundary holds (pseudocode loads the template from the definition store via template_ref, not from the instance) ✓.
  • Known gaps (intended): no actor binding / guidance (L0b); no actor-supplied stale-intent (L0b+); no gate (L2). Each is listed in Absent.
  • Decision: accepted as the L0a baseline. Light evidence per the playbook §2.1; a full evidence gate is only needed when L0a becomes an implementation input.
