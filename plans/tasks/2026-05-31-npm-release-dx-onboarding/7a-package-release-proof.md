# Task: Package Release Proof

## L0 - Policy

### Goal

Prove that Pairflow can be built, packed, inspected, and installed from a local
npm tarball as `@pairflow/cli`, and prove that release/publish automation stays
guarded until the final release readiness decision explicitly opens the guard.

### Domain / Control Model Summary

1. Business invariant: release readiness must be based on reproducible package
   and automation evidence, not on source-checkout assumptions.
2. Control model: `package.json` owns package identity, version, bin entry, file
   allowlist, and publish metadata; the generated tarball owns installed
   package contents; GitHub workflow config owns release/publish activation
   behavior; npm/GitHub account settings remain external prerequisites.
3. Read-path rule: installed CLI version proof must come from the package
   metadata shipped inside the packed tarball and observed through the
   installed `pairflow --version` and `pairflow -v` command.
4. Forbidden fallback: do not infer release readiness from repo-local `dist`,
   git tags, npm registry state, workflow names, or successful source-checkout
   commands alone. Do not perform a real public `npm publish` in this task.
5. Allowed resolution path: a local tarball generated by `npm pack` may stand in
   for npm registry distribution when installed into an isolated prefix; missing
   external credentials may be recorded as blocked prerequisites while local
   package proof remains valid.
6. Missing-data rule: if npm org/package access, `NPM_TOKEN`,
   `RELEASE_PLEASE_TOKEN`, GitHub environment approval, repository variables,
   or package-name availability cannot be verified, record that as a guarded
   prerequisite according to the L1 per-prerequisite status contract. Ordinary
   prerequisites use `present|missing|unknown|deferred`;
   `PAIRFLOW_NPM_PUBLISH_ENABLED` uses
   `false|true|missing|unknown|deferred` because the workflow guard is
   boolean-valued. Keep publish disabled or manual-approval protected.
7. Phase boundary: this task owns package/release proof only. It must not open
   the real npm publish guard, perform public publication, prove docs Pages
   deploy, or prove installed-package skill/UI behavior beyond package-content
   prerequisites consumed by `7c` and `7d`.

### In Scope

1. Run package/release validation from the current checkout.
2. Build the root package and UI assets required by the tarball.
3. Generate a real local npm tarball with `npm pack --json`.
4. Inspect the tarball contents for required and forbidden file classes.
5. Install the tarball into an isolated prefix or temp project without relying
   on the current source checkout.
6. Run installed `pairflow --version` and `pairflow -v` from the isolated
   install context.
7. Record the path or reusable location of the generated tarball for `7c` and
   `7d`, or record the exact command needed to regenerate it deterministically.
8. Prove `release:validate` passes and the publish workflow is still guarded.
9. Record external publish prerequisites using the L1 per-prerequisite status
   contract.
10. Record a blocker/follow-up requirement when package/runtime/workflow source
    defects are discovered. Do not fix those defects in this task.

### Out of Scope

1. Real public `npm publish`.
2. Opening `PAIRFLOW_NPM_PUBLISH_ENABLED` or weakening GitHub environment
   approval.
3. Creating or editing npm/GitHub secrets from local code.
4. Proving `pairflow skills install` behavior from the installed package; owned
   by `7c`.
5. Proving `pairflow ui start|status|restart|stop` from the installed package;
   owned by `7d`.
6. Publishing GitHub Pages docs; owned by `7b` and final operational setup.
7. Changing release-history taxonomy or commit-message policy.
8. Treating local source-checkout success as a substitute for tarball install
   evidence.
9. Editing package/runtime/workflow source files to repair proof failures.

### Safety Defaults

1. Use temporary install prefixes and temp HOME values for smoke commands.
2. Do not write to global npm, global skill, or global UI service locations.
3. Do not use `npm install -g` against the real global prefix during proof.
4. Stop immediately if a command path would publish to npm or mutate GitHub
   release state.
5. Keep publish workflow guard closed unless `7e` later records a GO decision.
6. If package proof creates temporary UI or process state, clean it before task
   closure and record cleanup evidence.

## L2 - Acceptance

### Required Checks

1. Run:

   ```bash
   pnpm release:validate
   ```

2. Run:

   ```bash
   pnpm build
   ```

3. Generate a tarball:

   ```bash
   npm pack --json
   ```

4. Inspect tarball contents for required and forbidden artifact classes.
5. Install the tarball into an isolated prefix or temp project without using the
   real global npm prefix.
6. Run installed:

   ```bash
   pairflow --version
   pairflow -v
   ```

7. Verify both outputs match `package.json.version`.
8. Verify `.github/workflows/npm-publish.yml` still has guard-closed behavior
   and a separate real-publish path gated by release event, enabled var,
   protected environment, `NPM_TOKEN`, tag/version match, and duplicate
   package preflight.
9. Record external prerequisite statuses using the L1 status contract.
10. Record successor handoff evidence for `7c` and `7d`.

### Suggested Local Proof Script Shape

The implementation may use an equivalent script or manual commands, but the
proof must preserve these safety properties:

```bash
set -euo pipefail

tmp_root="$(mktemp -d)"
prefix="$tmp_root/prefix"
export HOME="$tmp_root/home"
export npm_config_cache="$tmp_root/npm-cache"
mkdir -p "$HOME" "$npm_config_cache"

pnpm release:validate
pnpm build

pack_json="$(npm pack --json --pack-destination "$tmp_root")"
tarball="$(node -e 'const input = JSON.parse(process.argv[1]); console.log(input[0].filename)' "$pack_json")"
tarball_path="$tmp_root/$tarball"

npm install --prefix "$prefix" "$tarball_path"
"$prefix/node_modules/.bin/pairflow" --version
"$prefix/node_modules/.bin/pairflow" -v
tar -tf "$tarball_path"
```

### Acceptance Criteria

1. `pnpm release:validate` passes.
2. `pnpm build` passes.
3. `npm pack --json` produces exactly one local tarball for `@pairflow/cli`.
4. Required artifact classes are present in the tarball.
5. Forbidden artifact classes are absent from the tarball.
6. Isolated install succeeds without real global npm mutation.
7. Installed `pairflow --version` and `pairflow -v` equal
   `package.json.version`.
8. Release workflow validation proves guarded release automation is still
   aligned with package metadata.
9. Publish workflow remains guard-closed for real npm publication unless later
   opened by `7e-release-go-no-go`.
10. Missing external npm/GitHub prerequisites are recorded as blockers or
    deferred values, not silently bypassed.
11. Evidence is sufficient for `7c` and `7d` to reuse or regenerate the same
    packed package context.

### Review Checklist

1. Does the task prove tarball install behavior rather than source-checkout
   behavior?
2. Are package-content findings based on actual tarball contents?
3. Does version proof run from the isolated install path?
4. Does the evidence avoid real public publish?
5. Are external prerequisites separated from repo-provided proof?
6. Does any discovered source/runtime/workflow gap require a follow-up task
   before successor tasks run?
7. Does the final evidence clearly state whether `7c` and `7d` can proceed?

   missing, this task may still close as package-proof complete while final

   guard-restoration follow-up before recording release-pilot progress.
