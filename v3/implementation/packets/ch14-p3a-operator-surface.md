### The Ask's realized shape (built at ch14-p2a — this packet's INPUT, not its work)

The derivation the floor member calls lives today in `kernel/humanDecisionRequest.ts` and moves to `domain/` at this build (F4), together with the `DecisionRequestBody` type below; its body is unchanged by the move. Its signature and its contract, restated because the floor is its
second caller and the first lives in another module:

```
humanDecisionRequest(
  instance: WorkflowInstance,
  template: WorkflowTemplate,
  request: DecisionRequestBody,
): HumanDecisionRequest
```

Its inputs are ALREADY-IN-HAND by construction — "nothing is fetched"
is the function's own stated rule — and it THROWS a kernel-integrity
error at exactly SIX sites: a parked gate with a null `currentStep`; a
`currentStep` with no step definition; a step with no `role`; a role
unbound in `instance.binding`; a step with no `instruction`; a null
`instance.task`. Its only callee, `requiredFields`, is pure and
throw-free. Every one of the six describes a state the kernel cannot
have committed. THE FLOOR DOES NOT CATCH THEM and F6 states why.

### The two kernel handlers (built at ch14-p2b — this packet's CALLEES)

`kernel.submitDecision(input: SubmitDecisionInput)` and
`kernel.resumeWait(input: ResumeWaitInput)`. THE INPUT SHAPES ARE
CARRIED IN FULL, because entity names alone under-specify a shape and
five of their properties are not entailed by any prose below — the
required `intent` discriminant literal, the two required-but-may-be-
`undefined` fields, and the two genuinely OPTIONAL keys that make V3's
absence rule expressible at all:

```
SubmitDecisionInput {
  intent: "submit-decision"
  instanceId: InstanceId
  opId: OpId
  expectedVersion: number | undefined
  requestRef: string
  verdict: string
  override?: boolean
  payload?: unknown
  by: ActorId | undefined
}

ResumeWaitInput {
  intent: "resume-wait"
  instanceId: InstanceId
  opId: OpId
  expectedVersion: number | undefined
  type: string
}
```

`expectedVersion` and `by` are REQUIRED KEYS whose value may be
`undefined` — an absent value must REACH the kernel's version and
authority rungs; `override` and `payload` are OPTIONAL KEYS whose
absence is asserted as absence. The distinction is the shape V3's
per-flag absence rule rests on.

Their outcome unions, in full, because the exit-code matrix at V6 is a
total function over them and a partial one is the defect:

```
SubmitDecisionOutcome =
  | { kind: "committed"; version: number;
      intent: DispatchIntent | HumanDecisionRequest | null }
  | { kind: "duplicate" }
  | { kind: "stale"; currentVersion: number }
  | { kind: "rejected"; reason:
        "unknown_instance" | "op_id_collision" | "not_awaiting_decision"
      | "decision_request_mismatch" | "missing_version"
      | "operator_not_authorized" | "unknown_decision"
      | "missing_required_field" | "override_required"
      | "override_not_applicable" }

ResumeWaitOutcome =
  | { kind: "committed"; version: number;
      intent: DispatchIntent | HumanDecisionRequest | null }
  | { kind: "duplicate" }
  | { kind: "stale"; currentVersion: number }
  | { kind: "rejected"; reason:
        "unknown_instance" | "op_id_collision" | "not_waiting"
      | "resume_event_mismatch" | "missing_version" | "not_bare_wait"
      | "no_resume_transition" }
```

THE FOUR KINDS ARE THE SAME FOUR the actor-envelope `Outcome` carries,
which is what makes V6's reuse of the ch6-P4a exit matrix a REUSE and
not a coincidence — and it is also why V6 takes proof-parity rather
than inheriting it silently.

## Claim

**After this packet a human being can move a parked v3 workflow from the
shipped command line, and everything that move needs is readable from
one committed-state read.**

Stated WIDE, over the two surfaces rather than over the code:

1. **The floor's detail read answers the pending-decision question on
   C21's own two-valued terms.** The member carries the whole C20 Ask
   when the instance is parked on a human decision and the floor's
   definition store yields the pinned template; it is absent otherwise.
   The floor never re-derives, re-shapes or re-keys the Ask, and never
   invents a value for a question it cannot answer.
2. **The operator is never left unable to tell "not parked" from "I
   cannot reach the template".** Both facts are in the same document and are read TOGETHER, per `contract:ch14-human-decision#C27`: `wait.kind`
   says whether the run is parked on a human decision, and — read under a
   `human_decision` `wait.kind` — the member's absence says the Ask could
   not be derived. Neither field carries the distinction alone; the pair
   does, and no key is added to state their conjunction.
3. **The two verbs are total over their kernel outcomes and add no
   semantics.** Every outcome either handler can return reaches the
   operator as a DATA document on stdout under its inherited exit class;
   no kernel-negative is re-interpreted, retried, hidden, or promoted to
   an error document. The CLI's only decisions are argument shape, the
   resolution read C23 mandates, and the `--by` default C23 declares.
4. **The correlation and CAS inputs are the operator's to supply and
   nobody's to guess.** Each verb resolves what IT needs by reading,
   once, the same surface the operator can read — `submit-decision` the
   correlation handle AND the CAS version, `resume` the CAS version
   alone; a value that has moved between
   the read and the write lands as the kernel's own `Stale` or
   `decision_request_mismatch` data outcome, never as a retry and never
   as a fabricated success.
5. **The reach is proven through the shipped entrypoint, not through a
   seam.** At least one journey drives park → decide → resume as a
   subprocess against production bindings with a deterministic actor,
   using only the two shipped verbs to move the human's side.

**WHAT THIS CLAIM DOES NOT COVER, named here so the Claim is not read
wider than the packet:** the shipped `local-pair-v0` template still
declares no gate after this packet, so nothing an operator runs BY
DEFAULT reaches a human decision. That wiring, the golden-trace re-pins
it forces, and the journey over the CANONICAL template are ch14-p3b's
(row X1).

## Dimensions (enumerated BEFORE any test row)

Dependence between dimensions is stated, never assumed independent.

1. **Park state** — C21's two-valued axis: parked
   WAITING(`human_decision`) vs everything else. "Everything else" is
   driven across its members: never-parked (ACTIVE), parked on a
   NON-decision wait kind, terminal, and unknown-instance (the read's
   own null).
2. **Derivability, given presence** — DEPENDS ON 1 and on 4: for a
   parked instance, whether the floor's dependency yields the pinned
   template. The two-valued floor member collapses "not parked" and
   "parked but underivable" into absence; dimension 3 is the axis on
   which that collapse is undone.
3. **The read verb's document under an underivable Ask** — DEPENDS ON
   1, 2 and 4: that the `detail` document is still EMITTED, whole and
   with its existing members intact, when the floor member cannot be
   derived — by a `null` load, by a rejecting load, or by an absent
   dependency.
4. **The floor's dependency state** — DEPENDS ON 6's verb class: a wired
   definition store vs the explicit `null`. `null` is reachable on the
   READ verb (no dir configured) AND on `resume`, whose floor is given
   `null` by construction (F1) even with a dir fully configured;
   `submit-decision` is the one verb whose floor always carries a store.
   An INPUT axis, not a failure axis.
5. **Correlation of the request** — DEPENDS ON 1: which
   DECISION_REQUEST row the derivation uses when the transcript carries
   more than one (the rework loop-back's second park).
6. **Verb class and identity** — the WRITE class (`submit-decision`,
   `resume`) vs the READ verb (`detail`), and within the write class the
   two verbs. Both splits carry weight: F6 routes the same failure
   differently by CLASS, while the two write verbs differ in what they resolve (dimension 7), in their flag sets, in their outcome unions, and — since C27 — in whether their floor carries a dependency at all. Every matrix below is stated per class and, where they differ,
   per verb.
7. **Resolution completeness** — DEPENDS ON 6: `submit-decision` needs
   `requestRef`, `expectedVersion` and the bound operator (V3's
   default); `resume` needs `expectedVersion` alone.
8. **Resolution failure** — DEPENDS ON 1, 2 and 6: the read returns
   null (unknown instance), or returns an instance with no pending
   decision, or the load fails to yield a template — by THROWING or by returning `null`, two shapes with one answer ON THE SUBMIT PATH; `resume` reaches (i) ALONE, and misses the other two for DIFFERENT reasons: no (iii), its floor having no dependency to load with; no (ii), because a non-parked instance is not refused at the CLI at all — it reaches the kernel and returns as its `not_waiting` DATA outcome. Three
   distinct answers, three distinct dispositions; collapsing them is the
   defect this dimension catches.
9. **Argument shape** — DEPENDS ON 6, because the flag sets are per verb
   (`resume` carries neither `--by`, `--payload` nor `--override`). Per
   flag: present-and-well-formed,
   present-and-malformed, absent. The absent column carries meaning and
   is NOT uniform: for `--by` it is the C23 default and not a usage
   error; for `--payload` and `--override` it is a genuine absence the
   kernel's own rungs must see.
10. **Outcome kind, and within `rejected`, reason token** — DEPENDS ON
    6. TOTALITY is the property: the matrix is over the unions, not
    over the outcomes a happy path produces.
11. **Channel** — DEPENDS ON 8 and 10: stdout data document vs stderr
    error document. A cell that emits on both, or on neither, is a
    violation — scoped to the pre-teardown emit point and to lanes
    where the output stream is open.
12. **Journey reach** — subprocess vs in-process; production bindings
    vs injected seams; deterministic actor vs live. R-ACTIVATION-JOURNEY
    fixes one corner as mandatory and the others as illegal for the
    journey lane.
13. **Nonce identity** — one `op_id` per logical invocation, in BOTH
    directions: a replayed `op_id` reaches `duplicate`, and two
    invocations do not collide.

## In-context notes

- The two write verbs are the first write path in the tree that reads the
  floor before writing. That is C23's design, and it is the reason V2 says ONE
  read and means it: a second read inside a verb would introduce a
  window between two views of the same instance, and the operator would
  have no way to know which one the wire carried.
- The `submit` verb (the actor-envelope writer) and `submit-decision`
  are different surfaces with deliberately different shapes — `submit`
  takes `--instance` and demands `--expected-version` and
  `--expected-role`; `submit-decision` takes a positional id and demands
  neither. Reading the older verb as the pattern to copy is the most
  likely wrong turn in this build.
- `resume` is the verb name and `resume-wait` the intent discriminant
  the input carries. The asymmetry is C23's and is kept rather than
  tidied: the operator types the short one, the input carries the
  qualified one.
