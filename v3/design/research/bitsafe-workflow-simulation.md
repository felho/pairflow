# BitSafe Workflow Simulation — Can v3 + External Tools Realize the Real Fleet?

**Status: COMPLETE — 17/17 simulations, 16-gap register, synthesis; gaps LIFTED 2026-07-06 into `../../model/core-model-future-topic.md` (12 gaps, level/seam sections) + `topics/_open-creation-identity.md` (GAP-1) + `topics/_open-kernel-floor.md` (GAP-2, GAP-11, boundary canon) — see the register's Disposition column** · Started 2026-07-06 · Companion to `bitsafe-ai-os-capture.md` (source facts) and `nanoclaw-study.md` (runtime/supervision read)

## Purpose

The v3 kernel model has so far been stress-tested from the inside (level ramp, primitives rebaseline, paper tests) and against other systems' *architectures* (the study series). This exercise tests it against a real company's *workload*: the ~17 most instructive workflows in BitSafe's AI-operations fleet, as documented in the capture. For each workflow we simulate a v3 realization — kernel coordinates, external tools perform — and record precisely what is expressible today, what needs a planned level, and what has no story at all. The running gap register is the actual deliverable.

The selection criterion was **dimensional coverage for v3**, not importance to BitSafe: every trigger type (event, cron, calendar-relative, queue), every gate shape (pre-approval, tag-conditional, multi-sign-off, tier-based auto-approve), fan-out patterns, fleet-level policy, and governance meta-loops are each represented at least once.

## Method

One orchestrator (the supervising session) + one dedicated subagent per workflow. The subagent is briefed with this document, reads the kernel corpus and its workflow's capture section, and returns a simulation section; the orchestrator verifies claims against the corpus before capturing it here, then updates the gap register (dedup across workflows happens at capture time).

Each simulation section has five parts:

1. **Facts (capture).** Trigger, actors, gates, side effects — with capture line references. No invented facts.
2. **v3 decomposition.** Template sketch: instance(s), steps, waits, which primitive carries what (P1–P5), which levels are required.
3. **External tool boundary.** What is performed by providers behind the P5 Directive boundary (Notion MCP, Slack, GitHub Actions, Fathom, BetterStack, host cron, LLM calls…) and is therefore out of kernel scope.
4. **Verdict.**
   - ✅ expressible with the built corpus (L0a–L4 + LC + L0f/L0g) plus providers;
   - 🟡 expressible with a *planned* level — names the exact level/section, and says whether that section as written actually covers the need;
   - 🔴 gap — neither built nor planned corpus has a story.
5. **Gaps.** Reusable one-liners with a concrete trigger scenario; candidates for the gap register.

A finding of "not a kernel workload — pure provider/agent territory" is a legitimate verdict, not a failure: knowing where v3's edge *should* be is as valuable as finding holes inside it.

## The v3 baseline assumed by every simulation

**Built (normative, machine-checked corpus — `../../model/`):**

- Commit-based leaderless kernel. `WorkflowInstance` + append-only transcript; `UNIQUE(instance_id, op_id)` idempotency; CAS at `expected_version`; `kernel_status` lifecycle; produce-not-perform (the kernel emits deliverable ask objects; the runtime performs); de-vocabularized routing (the kernel routes by declared keys, knows no business names).
- Level ramp: L0a–L4, with the LC lifecycle-close strand (storage scope, runtime teardown, workflow actions, archive/purge), L0f config mode, L0g.
- Ingress: operator intents `CREATE_INSTANCE / START / KICKOFF / SUBMIT_DECISION / RESUME_WAIT / CANCEL / RUN_ACTION / DELETE_REQUESTED`, plus the actor envelope `HANDLE`.
- Five kernel primitives (contracts in-corpus, memo `topics/_open-kernel-primitives.md`):
  - **P1 Errand** — five-phase async request/reply (full / inline / marker-less inline / open-door forms; opener dimension incl. reserved agent-emit for L5).
  - **P2 ChoicePoint** — declared key set + authorized selector + guards + shared arrival (principal-committed / kernel-classified; proposed reserved).
  - **P3 Admission** — the rung ladder op_id → state → correlate → version → authority (`admit_loaded` + load-first `admit_input`).
  - **P4 Warrant** — commit authority.
  - **P5 Directive** — projected deliverable ask objects: `DispatchIntent`, `HumanDecisionRequest`, `ActionRequest`, `ActionIntent`, `SpawnIntent` (+ future `CapabilityIntent` L7, `RememberIntent`/`LinkIntent` L11).
- L4 child fan-out: parent spawns children via `SpawnIntent`, parks; child completions arrive as records (record-collection or wait-slot marker homes).

**Planned (topic map only — `../../model/core-model-future-topic.md`):** L5 skill surface & portable capability packaging · L6 triggers & scheduling · L7 grants & credentials · L8 channels, task inbox & EventNormalizer · L9 wait conditions, liveness & recovery · L10 gatekeeper & private-data federation · L11 memory & durable agent identity · L12 definition PRs & metacognition · L13 trust calibration & evals · cross-level seams (identity/sandbox/session, observe seam, operational observability & cost).

**Simulation rule:** external tools are fair game as providers — anything performable behind a P5 Directive is out of scope. The simulation judges only the **coordination**: durable state, waits, gates, idempotency, dedup, fan-out, authority, recovery.

### S1. CRM Capture Agent

**Facts (capture).** A Notion-resident custom agent (one of the "custom agents living inside Notion", capture 432–434) reachable from three surfaces: the #bd-ai-crm Slack channel, the Notion AI sidebar, and standard Notion forms (436). Trigger: a human utterance per interaction — no schedule, no queue. Three sub-paths in one agent: **capture** ("New lead: Temple Digital, met at Canton Summit, interested in CBTC" → a properly filed row), **update** ("set Temple Digital partnership status to Qualified"), and **lookup** ("what's our pipeline in Commit?") (all 436). Actors: the requesting human + the agent; no in-workflow approver — gates are design-time/harness-level, not workflow steps: schema protection via closed option sets ("the agent can't introduce new states", 506), master-data ownership (may create company rows, "can't mint a new Country or Region", 508), and action tiering under which "read operations and routine writes proceed freely" while destructive actions need human approval "at the harness layer" (510) — S1's writes are the routine tier. Side effects: create/update rows in the CRM database, native to Notion where the agent lives ("CRUD on the CRM, lookups in the sidebar", 424); the operating envelope is "one entity, one verb, frozen schema" (434, 444). Note that Partnership Status is a manual-discretion field by the autofill tiering (465) — the update path is a human *instructing* a write to it, not the agent judging.

**v3 decomposition.** The honest primary finding first: as BitSafe runs it, S1 is a single-turn assistant interaction — parse, act, reply within one exchange — and that is predominantly **provider/agent territory, not a kernel workload**. There are no waits, no in-workflow gates (510 puts them at the harness/token layer), no fan-out, and the conversational surface itself (sidebar chat) is the opposite of park-and-resume. The kernel earns entry only where a **side-effecting write** needs durable dedup and audit, and the three sub-paths split exactly there:

- **Lookup** — zero durable state, zero side effects; a WorkflowInstance adds only ceremony. Pure provider Q&A. No decomposition offered, deliberately.
- **Capture (row creation)** — the one path where idempotency genuinely earns a WorkflowInstance: "new lead: Temple Digital" is *not* effect-idempotent — a redelivered Slack message means a duplicate CRM row. Template sketch: one instance per inbound write request. Ingress: a channel connector normalizes the Slack/sidebar/form utterance and issues `CREATE_INSTANCE` + `KICKOFF` (P1 open-door errand — kickoff instance per `errand.txt`; task supply = the NL utterance + envelope identity); duplicate-delivery dedup must key instance creation on the external message id — this is *cross*-instance dedup, which the built `UNIQUE(instance_id, op_id)` does not provide (see verdict). One agent step: `DispatchIntent` (P5, per `directive.txt`) to the capture actor; the actor performs parse + Notion write provider-side and emits; the emit climbs the P3 ladder via HANDLE (op_id idempotency → state → version → P4 warrant/authority) and routes through the transitions ChoicePoint (P2, principal-committed) to complete, the row ref riding the transcript as evidence. Sturdier variant: split parse (actor) from write (LC3b auto action — `ActionIntent` to a Notion-write runner, `ACTION_RESULT` with classified outcomes `created | infra_error`, durable `action_running` marker + episode retry budget per `RUN_ACTION.txt` phases) — buys crash-safety between parse and write at the cost of a runner. Levels: L0a–L0d (+ LC3b optionally + LC teardown); no L3 human_gate — 510 explicitly frees routine writes.
- **Update** — same template shape, but "set partnership status to Qualified" is an absolute-value write, effect-idempotent at the provider under replay; the kernel case here rests on the audit transcript alone (a durable record of *who instructed* a write to a human-discretion field, 465/436), which is a defensible but optional use. Run provider-native, nothing is lost but the audit line.

**External tool boundary.** Everything that makes S1 *work* is behind P5: the LLM parse of natural language into fields, entity resolution ("Temple Digital" → row), the Notion database write/read itself, schema/option-set enforcement (506) and token scoping (512, 474) at the Notion boundary, and the reply posted back to Slack/sidebar. The kernel, where engaged at all, coordinates only: instance-per-write dedup, the write errand's marker/retry, and the transcript.

**Verdict.**
- **Lookup:** ✅ — as *not a kernel workload*: pure provider territory end-to-end; nothing to coordinate, and forcing an instance would be a category error.
- **Capture (create):** 🟡 **L8 §1–§3 + §4** (`core-model-future-topic.md` "Channels, task inbox, and EventNormalizer"). The instance body is fully expressible on the built corpus (L0a–L0d, optionally LC3b), but reaching the kernel from Slack/sidebar/forms needs L8's message-source channel normalization (§1) and connector contract (§3), inbound message-id dedup needs §1's exact correlation oracle (`UNIQUE(channel_type, platform_id, instance)`, "auto-create over hijack") — and those sections **as written do cover the need**, including the reply path (§4 delivery ledger, §4a correlation-by-stored-state).
- **Update:** 🟡 **L8** (same ingress dependency if kernel-realized) — with the note that the effect-idempotent write makes "not a kernel workload, run provider-native" an equally legitimate reading; the kernel adds audit only.

**Gaps.**
- **One-shot write ceremony (cost floor):** a single-turn side-effecting request has no lighter kernel form than a full WorkflowInstance lifecycle (create → kickoff → dispatch → emit → complete → LC teardown); trigger: every "#bd-ai-crm: set Temple Digital partnership status to Qualified" message minting and tearing down an instance for one Notion property write. Neither built nor planned corpus names a sub-instance-weight audited-errand form — register whether the answer is "by design: below this line, stay provider-native." → **GAP-2**

### S2. Companies CRM Enricher

**Facts (capture).** An autofill agent operating on **existing** Companies rows, populating five metadata fields — Region, Company Size, AUM/Revenue Band, ICP Segment, BitSafe Products of Interest; it works because "the Companies schema is frozen" (438). One of the fleet's single-responsibility agents — "one entity, one verb, frozen schema" (434, 444). Autofill is applied only where values are **derivable from existing content**; judgment fields (Partnership Status, Priority) are deliberately retained for humans, deterministic transforms go to formulas (462–466). There is **no per-run human gate**: the system maintains data quality "without requiring active user attention or intervention" — "nobody sees it work" (468). Volume: the enrichment agent sits in the "reach" system whose ~80 jobs "run on schedule", and this single agent has "logged roughly 7,700 runs by itself" (1976, 1984). The capture states the schedule-driven firing for the reach system (1976, 1984) but never specifies a per-row-change trigger; the side effect per run is a metadata write onto an existing CRM row (438).

**v3 decomposition.** The per-row inner work — read row → derive values → write fields — has **zero coordination content**: no wait, no gate, no fan-out, no multi-party handoff. So the load-bearing decision is where the instance boundary sits, and instance-per-row-event is the wrong cut at this volume: 7,700 runs × full lifecycle (CREATE_INSTANCE → START → KICKOFF → action claim/result → COMPLETE → LC teardown + archive/purge) is on the order of 40–50k commits and 7,700 archived transcripts purchased for runs that never park — pure ceremony, and the LC archive becomes dominated by trivial one-step records. The right cut is **one instance per scheduled sweep**: an L6 timer fire creates a short-lived instance whose template is a single auto-action step (LC3b) — P1 Errand in inline/full form: `action_running` claim → **P5 `ActionIntent`** to the runner ("enrich all rows currently needing it") → `ACTION_RESULT` classified through the **P2 outcomes ChoicePoint** (`enriched` / `nothing_derivable` / `infra_error`, with infra_error re-parking for retry) → COMPLETE. **P3 Admission + P4 Warrant** guard every entry as usual; the ingress touch's operator `op_id` on KICKOFF/START is load-bearing here — a scheduler that retries its kickoff gets `Duplicate`, not a second run. Per-row idempotency is then keyed **provider-side on (row_id, row_version)** and is semantically safe by construction: fill-only-derivable against a frozen schema converges — a re-delivered "row changed" signal re-derives the same values, so double-enrichment is a cost problem, not a correctness problem. If instance-per-row-event is nonetheless wanted (per-row run records), exactly-once creation must be keyed on (row_id, row_version) — and the built corpus's `UNIQUE(instance_id, op_id)` idempotency is **per-instance** scope; nothing built dedupes instance *creation* against an external event identity. The watcher/trigger itself lives outside the built kernel: the scheduled shape is **L6** (durable cron rows, drift-free recurrence, CAS-claimed firing); a row-changed-webhook shape is **L8** (message-source channel + EventNormalizer + the exact correlation store). A third honest reading: if the enrichment stays Notion-native autofill (460–464), the provider does everything and v3 coordinates nothing — the kernel only enters when BitSafe wants durable run records, failure classification, and retry governance over the 7,700 runs. Levels required: built L0a–L0e + LC3b (one action-step template; no L3 gate, no L4 children) + planned L6 (or L8 for the event variant).

**External tool boundary.** Behind the P5 `ActionIntent`: the row read, the LLM derivation/classification, and the Notion field write — the entire per-row loop, including provider-side (row_id, row_version) skip-if-already-enriched bookkeeping. Notion-native autofill firing, if used, is wholly provider territory.

**Verdict.** 🟡 — the run itself is expressible today as a one-action-step instance on the built corpus, but the recurring trigger requires **L6 §§1–2** (durable look-ahead timer rows + idempotent CAS-claimed firing), which as written **do cover** the scheduled-fire-with-exactly-once-claim need (nanoclaw's `series_id` recurring-identity row model is explicitly adopted); the event-driven variant requires **L8 §1**, which as written **does cover** exact inbound dedup (store-enforced `UNIQUE` correlation, auto-create over hijack). What neither the built ingress nor L6/L8 as written spells out is the seam between them: how a claimed fire mints `CREATE_INSTANCE` idempotently (deterministic instance identity per occurrence).

**Gaps.**
- **Fire→create binding: no contract for exactly-once instance creation from an external trigger identity.** L6 CAS-claims the fire and the built ingress dedupes `op_id` *within* an instance, but nothing states how a fire or event mints `CREATE_INSTANCE` so a retry finds the existing instance instead of creating a twin — trigger scenario: the scheduler crashes after CREATE commits but before its fire row advances; the re-claimed fire re-issues CREATE and a second enricher run writes the same rows. → **GAP-1**
- **No instance-boundary guidance or lightweight run-record shape for high-volume narrow work.** The corpus prices every run at full instance lifecycle + LC archival regardless of coordination content — trigger scenario: an autofill fleet at ~7,700 runs where per-row instances would swamp the instance store and archive with trivial one-step transcripts, forcing the per-sweep batching decision onto every template author with no stated rule. → **GAP-2**

### S3. Meeting Notes Processing

**Facts (capture).** Category: an "AI-powered SOPs" agent — work that "executes according to a schedule, operating against an SOP written once" ([03] 448), under the principle "humans write the SOP once, agents run it every week" ([03] 456). The workflow itself: "Every Fathom-recorded meeting receives a post-processing pass that extracts decisions, action items, and entity mentions. Action items become Tasks. Mentioned Companies and Contacts get linked. The summary is short, structured, and actually used." ([03] 452). Actors: the SOP-running agent ([03] 448, 456); Fathom as the recording source and Notion Tasks/Companies/Contacts as the write targets ([03] 452). No human gate appears anywhere in the S3 facts — the owner-edits-the-draft step at [03] 450 belongs to Meeting Prep (S4), not this workflow. The capture does not name the trigger mechanism: the category framing is schedule-driven ([03] 448), while the per-recording shape ("every Fathom-recorded meeting receives a pass", [03] 452) is event-shaped — the register row reads it as an event pipeline. Both readings impose the same coordination need: exactly one pipeline per recording.

**v3 decomposition.** One `WorkflowInstance` per recording; task = the recording ref; no human gate, so no L3 `human_gate` step is needed at all.

- *Trigger/ingress.* Not built; both capture readings land on planned levels. Scheduled reading (the [03] 448 framing): an L6 cron sweep ("find unprocessed recordings") — L6 §1–2's durable timer rows + CAS-claimed idempotent firing carry the tick itself. Event reading (register row): a Fathom "recording ready" webhook enters through the L8 connector contract (§2–3) and EventNormalizer, and L8 §1's exact correlation oracle — a store-enforced `UNIQUE` key, auto-create over hijack — is precisely the "one instance per recording id" registry. Today the entry would be an external harness driving `CREATE_INSTANCE` + `START` per recording, and there the dedup has no kernel story: `CREATE_INSTANCE` carries no idempotency or external-event key, and the `UNIQUE(instance_id, op_id)` ledger cannot see cross-instance duplicates — two creations from a redelivered event mint two instance ids. Idempotency against redelivery is therefore owned by L8 §1's correlation store (covered as written, for channel-borne events) or by the harness; the built ingress dedups nothing at creation grain.
- *Step 1 — extract* (agent step, L0b): P5 `DispatchIntent` to the SOP actor, which fetches the Fathom transcript and performs the LLM extraction (decisions / action items / entity mentions); the actor's emit is a P2 `transitions` principal-committed selection, admitted through the P3 ladder with its P4 warrant, and the structured extraction result rides the emit payload into the handoff.
- *Step 2 — apply side effects* (the fan-out). Two shapes, both honest:
  - **Provider-side (expressible today, ✅):** a second agent step (or one LC3b auto action whose runner is an idempotent "apply extraction" script) performs all N Task creations + M entity links + the summary write behind one P5 directive. The kernel sees one errand; per-item progress, per-item idempotency, and partial-failure resume live entirely behind the P5 boundary (the runner keys each Notion create on `{recording_id, item_id}`).
  - **Kernel-grain (per-item errands):** one errand per item — L4 child per action item (`child_key = {recording_id, item_id}`, each child a one-step template whose LC3b auto action carries the Notion write via P5 `ActionIntent`; P1 spawn + child-await errands; P2 `wait_for` kernel-classified routing). This is where the built corpus stops: the step list is static and the L4 parent parks on exactly ONE link (`park_for_child` sets `wait.link_id` singular; `CHILD_LIFECYCLE` rejects `not_awaiting_this_child`), so a runtime-sized N fits only as a sequential self-target loop — and that loop has no declared "collection exhausted" route to terminate on. Concurrent fan-out is exactly the reserved non-blocking marker-home (errand.txt: a record-collection home *permits* a non-blocking form, → L5), but that dimension as written targets the help subflow, not N data-driven sibling errands.
- *Partial failure (3 of 5 Tasks created, run dies).* Split answer, and the split is the produce-not-perform boundary itself. Kernel story: with per-item errands, settled items are terminal commits (transcript entries / terminal links) and re-entry is a reload — `park_for_child` is idempotent on the live link and a terminal link never blocks a fresh attempt; the one in-flight item is a durable `action_running` marker, whose reconciliation the built pseudocode explicitly defers ("a crash here leaves a durable `action_running` the L9 watchdog reconciles" — RUN_ACTION.txt; ACTION_RESULT.txt's undeclared-outcome path likewise "recovered at L9"). Provider story: whether the crashed write actually landed in Notion before the crash — the runner must make the create idempotent (keyed on `request_id` / item id); the kernel guarantees at-most-once *routing* per completion plus durable in-flight visibility, never effect-level exactly-once. With the provider-side shape, the whole question moves behind P5.
- Completion → `COMPLETE`; LC teardown/archive closes the instance. Levels required: L0a–L2b + LC + (optionally) L4, all built, for the body; L6 or L8 (planned) for ingress; L9 (planned) for crashed-in-flight reconciliation.

**External tool boundary.** Behind P5 (`DispatchIntent` / `ActionIntent`): the Fathom transcript fetch; the LLM extraction of decisions, action items, and entity mentions; entity resolution (mention → existing Company/Contact page); Notion Task creation, relation linking, and the summary write; and the per-item effect-idempotency ledger in the provider-side shape. The Fathom webhook receipt/normalization itself is L8 connector/EventNormalizer territory — outside the kernel commit path.

**Verdict.** 🟡 — the pipeline body is fully expressible on the built corpus plus providers (one instance, an extract errand, side effects behind P5), but the workflow does not start itself: ingress needs **L6 §1–2** (scheduled-sweep reading — durable timer rows with CAS-claimed idempotent firing; covers that need as written) or **L8 §1–§3** (event reading — connector normalization plus the store-enforced exact correlation oracle with auto-create; covers both normalization and redelivery dedup as written), and recovery of a crashed in-flight write needs **L9** (named in the built pseudocode as an explicit deferral; the future-topic L9 section owns liveness/recovery but the watchdog contract is not yet written). Kernel-grain per-item fan-out tracking has no construct today (see gaps) but a legitimate provider-side fallback keeps the workflow realizable.

**Gaps.**
- **Creation-grain idempotency has no built story:** `CREATE_INSTANCE` carries no idempotency/external-event key and `UNIQUE(instance_id, op_id)` cannot see cross-instance duplicates — a Fathom "recording ready" webhook redelivered after an ack timeout mints two pipelines for one recording; L8 §1's correlation store covers the channel path as written, but the operator/API ingress path dedups nothing. → **GAP-1**
- **Data-driven fan-out (one errand per runtime-extracted item) has no kernel construct:** the template step list is static, the L4 parent parks on one link at a time, and a self-target child loop lacks a declared collection-exhausted route — a meeting yielding 5 action items where the run dies after 3 Tasks leaves the operator with no kernel-grain answer to "which two are missing" unless the per-item ledger is pushed behind P5; the reserved non-blocking marker-home (→ L5) names the mechanism but as written targets help subflows, not N sibling errands. → **GAP-3**

### S4. Meeting Prep SOP

**Facts (capture).** Category: "AI-powered SOPs" — agent work that "executes according to a schedule, operating against an SOP written once" ([03] 448). Three meeting classes — the Monday RevOps sync, the Wednesday marketing meeting, and advisory calls — "each have a Notion document SOP describing how to assemble the prep doc — which databases to pull from, which fields matter, what the agenda template looks like" ([03] 450). Trigger rule, verbatim: "An hour before each meeting, the SOP runs and produces a draft prep doc" ([03] 450) — calendar-relative, not a clock time: the two named meetings are weekly slots, advisory calls carry no stated recurrence at all. Post-delivery: "The owner edits it for ten minutes" ([03] 450) — no approval loop, no rejection route, no signal back into the workflow appears anywhere in the facts. Actors: the SOP-running agent and the meeting owner ([03] 450, 456). Side effect: one draft prep doc per meeting occurrence, assembled from Notion database pulls per the SOP. Governing principle: "humans write the SOP once, agents run it every week"; the leverage is "the SOP being good enough that the model has nothing to argue about" ([03] 456).

**v3 decomposition.** The instance body is the easy 90%: one `WorkflowInstance` per meeting occurrence, task = {occurrence ref, `sop_doc_ref`}, a single agent step — P5 `DispatchIntent` to the SOP-running actor, which reads the SOP doc, performs the database pulls, drafts against the agenda template, and writes the prep-doc page provider-side; its emit routes through the P2 `transitions` ChoicePoint (principal-committed) to COMPLETE, admitted as always through the P3 ladder under its P4 warrant; LC teardown closes it. No L3 `human_gate` anywhere (see the edit question below). Levels: L0a–L0d + LC, all built.

- *SOP-as-Notion-doc (the L0f adjacency).* Two layers, and the built corpus already draws the line correctly. The **variant selection** is exactly L0f: one generic one-step template, three targets (revops / marketing / advisory) each binding a `sop_ref` slot — `RESOLVE_START`'s `wf.targets` + slot resolution produce the pinned resolved definition per run. But the pin deliberately stops at the *ref*: the SOP **content** is mutable Notion data — "humans write the SOP once" and keep editing it ([03] 456) — read at dispatch time behind P5, never at resolve time. That mutability is the feature, not a leak: the SOP is config-as-data driving *actor* behavior (which databases, which fields), and the de-vocabularized kernel cannot and must not read it — kernel routing sees only the declared emit keys. L0f covers what it should; the rest is provider territory by design.
- *The trigger (the crux).* "An hour before each meeting" is neither cron nor interval: the fire time is a projection of an external, mutable calendar event. What **L6 as written** gives: durable deadline rows (§1 — "a long sleep should become a stored timer/deadline row"), explicit status bits including *obsolete*, CAS-claimed exactly-once firing with reload-and-discard-if-stale (§2), and the `series_id` recurring-identity model — a *materialized* fire at `meeting_start − 1h` fits the row shape perfectly (the L6 timer is even a named P1 errand mapping in the primitives memo). What it does **not** give: recurrence advances via a **cron parser** ("next occurrence computed from the schedule"), and this schedule lives in Google Calendar, not in a cron expression — advisory calls have no recurrence to parse at all; §2's discard rule reloads the *instance/work item* and checks *kernel* staleness, never re-checks the external fact at fire time; and nothing states who rewrites or obsoletes a materialized row when the meeting moves or cancels — the *obsolete* status bit is vocabulary awaiting a writer. So the faithful shape is an **L8 + L6 composition**: the calendar change feed enters as a message-source channel (L8 §1) through the connector contract (§3), correlating exactly on the calendar event/occurrence id (§1's store-enforced exact oracle); each normalized created/moved/cancelled event then *maintains* the timer row keyed on that identity — upsert the deadline on a move, mark obsolete on a cancel — and the fire claim must be arbitrated against a concurrent move/cancel (CAS claim vs obsolete write). L8 covers the ingestion as written; L6 covers the firing as written; the maintenance seam between them is written in **neither** section. Edge case the seam must own: move-after-fire — the sync moves at T−50 when the T−60 fire already claimed and a prep instance is running; the built `CANCEL` intent can kill it and the re-materialized row fires a fresh instance, but nothing declares *who* issues that CANCEL.
- *Degenerate realization expressible today (modulo GAP-1):* a plain L6 cron sweep every N minutes; the sweep instance's single step asks a provider "which meetings start within the next hour and lack a prep doc?" and drafts them — calendar-relativity, occurrence dedup (the same meeting sits in the window across consecutive ticks), and cancellation awareness all move behind P5. Given the Notion-native "executes according to a schedule" framing ([03] 448), this is plausibly what BitSafe actually runs. It buys realizability at the price of fire precision (sweep granularity) and a provider-owned per-occurrence effect ledger.
- *The owner's 10-minute edit:* deliberately out-of-band — the workflow **ends at draft delivery**. An L3 `human_gate` would park `WAITING(human_decision)` that no captured signal ever completes: there is no submit-back, no approve/reject route, no re-run on edit — the human-decision errand's completion is `SUBMIT_DECISION`, and nothing in the facts produces one. The edit is native Notion document editing on the artifact after the instance is COMPLETE. If a "prep doc ready" ping is wanted, that is an L8 §4 outbound delivery (durable delivery ledger), not a wait — the capture states no notification.

**External tool boundary.** Behind P5 (`DispatchIntent` / `ActionIntent`): the calendar read; the SOP Notion-doc read; the Notion database pulls ("which databases to pull from, which fields matter", [03] 450); the LLM drafting against the agenda template; the prep-doc page write; and, in the sweep variant, the meetings-in-window query plus the prep-doc-exists dedup check. The calendar change feed's receipt and normalization are L8 connector/EventNormalizer territory, outside the kernel commit path.

**Verdict.** 🟡 — the body is fully expressible today (L0a–L0d + L0f targets + LC; no gate), but the trigger is a two-level composition: **L6 §§1–2**, which as written cover the durable deadline row, the *obsolete* status vocabulary, and CAS-claimed exactly-once firing, but do **not** as written cover a deadline derived from external mutable state (cron-only recurrence — nothing fits an ad-hoc advisory call; no external re-check at fire; no row-maintenance contract on move/cancel); plus **L8 §§1–3**, which as written **do** cover calendar-change ingestion and exact occurrence correlation. The seam — L8 event maintains L6 row; fire-claim vs concurrent-move arbitration; cancel-after-fire authority — is written in neither. The cron-sweep degenerate form is realizable on L6-as-written with the calendar logic pushed behind P5, at the cost of precision and provider-owned dedup — and it still meets GAP-1 at instance creation.

**Gaps.**
- **Externally-derived deadlines: a timer row whose fire time is a projection of external mutable state has no maintenance contract.** L6 materializes and fires rows and even names an *obsolete* status; L8 ingests and exactly-correlates the change events; but no section states who upserts/obsoletes a materialized row on a move or cancel, nor arbitrates the CAS fire-claim against a concurrent move — trigger scenario: the Monday RevOps sync moves from 10:00 to 14:00 at 9:05; the 9:00 row must be obsoleted and a 13:00 row minted, and if the move lands mid-fire-claim, the fleet either produces a prep doc for a ghost slot or never produces the 13:00 one. → **GAP-5**
- **Fire→create binding re-surfaced:** a re-claimed fire, a redelivered calendar webhook, or consecutive sweep ticks seeing the same meeting inside the 60-minute window mint twin prep instances for one occurrence — `CREATE_INSTANCE` still carries no external-identity key to make per-occurrence creation exactly-once. → **GAP-1**

### S5. CRM Hygiene Monitor

**Facts (capture).** Four agent checks, "each housed in the Notion Skills database" (484): **Stale Stage** — an Opportunity in the same stage beyond its expected duration (486); **Dormant Account** — a partnered Company with no recent engagement (487); **Overdue Close Date** — Opportunities past their scheduled close (488); **Missing Required Fields** — rows failing locked capture-layer specifications (489). Trigger: "Each executes every weekday at 9 AM ET, with output directed to a #crm-alerts Slack channel" (491). The cross-layer split (493–498): the Notion *schema* (Architect-owned) carries the timing definitions — expected stage dwell times (495); the *skill pages* specify each check's execution methodology (496); *NanoClaw* "executes them according to schedule and publishes to Slack" (497); and human responses in the channel — "fix Temple — set close date to next Tuesday" — are processed by a **different** agent, the Notion-resident *BitSafe CRM Agent*, which translates and records them back to Notion (498). Gates: none in-workflow — "no engineer participation is required"; modifying a check means editing the skill page, adjusting a routing rule means editing the routing-rules table; "system behavior is configured entirely within Notion" (500). Side effects: Slack posts (alert side); Notion CRM writes (reply side, 498).

**v3 decomposition.** Each check's inner work — query CRM rows, judge against expectations, post findings — has zero coordination content: no gate, no mid-run wait, no handoff. The kernel questions are the three named below.

*(a) Instance topology.* Recommended cut: **four independent L6 timer series** (one per check; cron `weekdays 9:00` in America/New_York), each fire minting one single-step instance — an LC3b auto action: P1 errand (`action_running` claim + episode) → **P5 `ActionIntent`** to the check runner → `ACTION_RESULT` classified through the **P2 outcomes ChoicePoint** (`alerts_posted` / `all_clean` / `infra_error`, the infra route re-parking under the episode retry budget) → COMPLETE → LC teardown; P3 Admission + P4 Warrant on every entry as usual. Judged against **GAP-2**: unlike S2's 7,700 runs, ~20 one-step instances/week is a priced but affordable ceremony, and per-check instances buy exactly what a sweep loses — failure isolation (an `infra_error` re-park in Stale Stage never stalls Dormant Account, whereas a single 4-static-step sweep template serializes the checks, so one parked retry blocks the rest), per-check run records, and a per-check definition pin matching the capture's own unit of change (a check = a skill page, 500). The one-sweep-instance alternative (4 design-time-fixed action steps — static N, so GAP-3's data-driven fan-out is *not* triggered; in-instance concurrency is not on offer anyway, L4 awaits being one-link-at-a-time) remains the fallback if the weight floor is judged to bite; the finding is that the corpus states no rule for making this call — that *is* GAP-2. The fire→`CREATE_INSTANCE` seam is GAP-1 as recorded.

*(b) The closed loop.* **Two workflows coupled only through the world (Slack thread + Notion rows) — and that is the correct cut, not a concession.** The monitor's contract ends at the Slack post: 497 gives NanoClaw exactly "executes and publishes"; nothing in the capture has the monitor await remediation. The reply is a separate **S1-shaped ingress**: an utterance in a channel, parsed and written to the CRM by the resident agent (498) — precisely S1's Update path ("set close date to next Tuesday" is an absolute-value, effect-idempotent write), and S1's verdict transfers wholesale. The kernel-spanning alternative — one instance parking after the post for replies — has no built home: replies are 0..N, optional, unordered, arriving over days; the built wait slot is singular; thread-correlated reply routing is exactly L8 territory (§1 correlation store, §4a correlation-by-stored-state, §4c session-existence-as-subscription); and the only built cross-instance kernel coupling is the L4 parent/child pair, which does not fit two peer agents in different runtimes. Where v3 stands: coupling through the world is outside the kernel's audit horizon — legitimate, and here *convergent by design*, because the next weekday's 9 AM re-scan re-detects anything unfixed. The loop is closed by idempotent re-detection over world state, not by a kernel wait; the reply side is not the monitor's concern.

*(c) Check definitions in a Notion Skills DB.* Split the two config surfaces. The **dwell-time expectations** (495) are world data the check reads live behind P5 alongside the Opportunity rows — re-read per run is correct and no pin question arises. The **methodology pages** (496) are behavior definition, and the built discipline is unambiguous: definitions resolve and **pin before the kernel runs** (L0f `RESOLVE_START` pins the resolved view; every handler loads the pinned immutable template; the future-topic gate-config text repeats it — the kernel "should not interpret a free-floating profile at run time"). Daily instances reconcile pinning with mutable pages for free: each 9 AM fire resolves and pins *that morning's* definition, so an edit lands next weekday — exactly the "edit the skill page, no engineer" semantics of 500, plus what BitSafe itself lacks: a transcript recording which definition version produced Tuesday's alerts. What is missing is the *source*: `RESOLVE_START`'s `select_source` is "MVP: local(.pairflow/); central store is L11+" — a Notion Skills DB is not a definition source the built corpus can read. BitSafe's own S16 Skill Reconciler (Notion → disk sync) is precisely the workaround that turns the mutable page into a local source; and if the check instead runs as skill text the actor fetches at run time (the capture reality), the behavior identity escapes the pin entirely (L0c §3's issued-vs-applied attestation names the adjacent problem). → new gap below.

**External tool boundary.** Behind P5 (`ActionIntent`/`DispatchIntent`): the CRM database queries (stage ages, engagement recency, close dates, required fields), the dwell-time reads from the schema (495), the check judgment itself per the skill-page methodology (496), the Slack post to #crm-alerts (491) with provider-side message idempotency, and — on the reply side — the thread read, NL translation, and the Notion write-back (498). The Skills-DB page fetch/sync (S16's job) is definition-source territory, outside the kernel commit path.

**Verdict.**
- **Check/alert side:** 🟡 **L6 §§1–2** — the instance body is fully expressible on the built corpus (one LC3b action-step instance per check per fire), but the weekday-9-AM-ET recurrence needs L6's durable timer rows + CAS-claimed idempotent firing, which **as written cover the need**, including the timezone-correct drift-free recurrence (cron computed in the user's timezone — DST-correct 9 AM ET) and the `series_id` recurring identity. If durable Slack-post delivery accounting is wanted (crash between check and post), **L8 §4**'s delivery ledger covers that as written; otherwise it stays provider-side.
- **Reply side:** 🟡 **L8 §1–§3** (identical to S1 Update: channel ingress + correlation if kernel-realized) — with S1's note transferring: the effect-idempotent write makes "not a kernel workload, run provider-native" (the capture's actual shape — a Notion-resident agent) an equally legitimate reading; the kernel would add only the audit line.
- **Definition/config side:** the per-instance pin discipline is **built** and the daily-re-resolution semantics fall out of it as written; the Notion-resident definition *source* is a named corpus deferral (central store → L11+) with no written contract — see the new gap.

**Gaps.**
- **Fire→create binding (cite GAP-1):** each 9 AM fire must mint `CREATE_INSTANCE` exactly once — trigger: the scheduler crashes after CREATE commits but before the timer row advances; the re-claimed fire mints a twin instance and #crm-alerts gets every stale-stage alert twice. → **GAP-1**
- **Instance-boundary rule absent (cite GAP-2):** four-series-vs-one-sweep is a real design fork with no stated rule — trigger: the template author must choose between ~20 ceremony-priced one-step instances a week and a sweep template that serializes four independent checks behind one retry park. → **GAP-2**
- **External mutable definition source: no pin/provenance contract for behavior authored outside the local definition store.** The pinned-definition discipline stops at `select_source` (MVP local; central store deferred to L11+), so a check whose methodology lives in a mutable Notion page either escapes the pin entirely (the actor fetches the page at run time — behavior identity unrecorded in the transcript) or needs an unspecified snapshot/sync step to become resolvable — trigger: the Architect edits the Stale Stage skill page at 8:55 AM; the 9:00 run's transcript cannot answer which methodology text produced its alerts, and a redelivered fire may resolve a different definition than the first attempt. → **GAP-7**

### S6. Daily Health Dashboard

**Facts (capture).** Trigger: a scheduled task generated from `src/monitor.ts` publishes the dashboard daily at 09:00 UTC (1406). Work: walks 35+ checks — cron drift, container counts, scheduled-task staleness, Anthropic spend, security audit status, backup checkpoint age, dead-man heartbeat (1406); data-source freshness, search latency, vector embedding coverage, Slack sync, container health, secret-file modes, pipeline state (1699) — and posts one structured table to `#ai-projects-nanoclaw-admin` where every check returns ok / warn / fail with the next-step command inlined, so reading takes ~30 seconds (1406, 1699). "The dashboard IS the dashboards — 35+ separate background workers in some other system, here 35+ alert subscriptions in one post" (1699). Side effects mid-run: some sections auto-remediate **before posting** — root-owned cache DBs get chowned back to `nanoclaw`, stale lock files get reaped (1406). Actors: the monitor agent plus the admin (Aki), who is pinged only on judgment calls — a sync silent for three days, daily spend crossing 2× the trailing-7d average, a cron not run in 6 hours (1406); the ping is a notification, not an approval — nothing blocks on a reply. The monitor "does not loop forever; it runs once per scheduled tick and writes its findings" (1412). Three cross-cutting alert design principles (1711): **severity tiers** map alerts to delivery surfaces — info to admin channel, warning to admin DM, critical paged out-of-band through BetterStack; **cooldown + dedup** is enforced per source — `scripts/ping-aki.sh --source <name>` checks a state file before firing so a repeat condition doesn't spam; **batching** is preferred over staccato — one post per day, not 35 pings.

**v3 decomposition.** One `WorkflowInstance` per daily tick; no human gate anywhere in the body (the admin ping is fire-and-forget outbound, never a parked `human_decision` wait — the dashboard posts regardless). Ingress: an L6 timer row (09:00 UTC recurrence, drift-free advance, CAS-claimed fire per L6 §§1–2) mints `CREATE_INSTANCE` + `KICKOFF` — and the fire→create seam is GAP-1 verbatim: a re-claimed fire after a crash-between-commits mints a twin dashboard run and a duplicate Slack post.

- *(a) 35+ checks — batch vs fan-out.* GAP-3 does **not** recur for the checks themselves: the check list is design-time-fixed (authored in `src/monitor.ts`, 1406), so a STATIC 35-step template — 35 sequential LC3b auto actions, each a P1 inline/full errand with `ActionIntent` (P5) and a classified `outcomes` ChoicePoint (P2, kernel-classified: `ok | warn | fail | infra_error`) — is genuinely expressible on the built corpus today. But nobody should want it: ~35 × (claim commit + result commit) per day buys kernel-grain audit for checks with zero individual coordination content, the parent-style concurrent alternative isn't built (the L4 parent parks on one link at a time; multi-child fan-in/controls are named L4 future extensions), and the capture's own design principle argues the other way — batching over staccato, "35+ alert subscriptions in one post" (1711, 1699). GAP-2's instance/step-weight-floor reasoning recurs as exactly this boundary decision. The right cut: **one provider-side batch behind one directive** — a single LC3b auto action (`ActionIntent` to a monitor runner, `ACTION_RESULT` outcomes: `published | publish_failed | infra_error`) or a single agent step (`DispatchIntent`), with the per-check ok/warn/fail table riding the result as T1 evidence. The kernel sees one errand; the sweep is data, not steps.
- *(b) auto-remediation mid-sweep.* The chown/reap fixes (1406) are condition-*discovered* at runtime — a static template cannot pre-place them, so promoting each to a kernel-grain `ActionIntent` errand would re-surface GAP-3 (runtime-discovered N side-effecting sub-actions), and their character argues against bothering: idempotent, convergent, low-blast-radius commands (chown to a known owner; reap stale locks) fired at machine tempo. Provider-side is the honest boundary, with each remediation recorded in the posted table and the errand's evidence refs — the transcript keeps "the sweep ran and remediated X" without a commit per chown. The design threshold worth stating: a remediation that grows blast radius (restart prod, delete data) should graduate to its own declared action step — a template-design rule, not a kernel hole (GAP-2's "where is the line written?" question again).
- *(c) cooldown + dedup across runs.* This is the workflow's genuinely hard coordination fact: the suppression state is consulted-before-firing and lives **across** instances (yesterday's run fired the warning; today's fresh instance must know). Built corpus: nothing — instance state and transcript are per-run, and `UNIQUE(instance_id, op_id)` is per-instance scope. Planned corpus, two near-misses: the L2 future extension "Stateful policy plane" (`policy_state`: policy-local, namespaced durable decision memory explicitly naming budgets and **rate limits**, kernel-committed under idempotency/audit rules) is the closest shape, but as written it is gate-scoped — it rides gated transitions — and never states cross-instance scope; L8 §4's outbound delivery ledger dedupes and retries **a single logical send** against its delivery record, not a repeating *condition* across days (its states are queued/sent/acked/failed/expired/superseded — no suppressed-by-cooldown). L11 memory (`RememberIntent`) is durable and cross-run but framed as perspective-keyed agent knowledge; operational suppression counters would be a category stretch. So today the answer is **provider state by design** — and it is coherent, because the alert *firing* is also behind P5 (`ping-aki.sh` owns its own state file, 1711). The gap opens the moment delivery moves kernel-side: if L8 §4's ledger performs the sends, cooldown/dedup becomes a delivery decision the kernel is making with no kernel-readable state to make it from. See gaps.
- *(d) severity-tier routing.* Two clean readings. Provider routing (expressible today): the sweep runner posts channel/DM/page itself behind the one P5 directive — the kernel never sees the tiers. Kernel-side (the L8 reading): each judgment-call alert becomes an addressed outbound directive; L8 §2's envelope identity (platform, channel, recipient) carries the surface, §3's connector contract admits Slack-channel, Slack-DM, and BetterStack as three connectors, §4's ledger gives per-recipient delivery state and send idempotency. The severity→surface *mapping* itself is template/config content (declared severity keys → channel identities), not a missing mechanism — L8 §§2–4 as written cover the delivery mechanics the tiers need.

**External tool boundary.** Behind P5: all 35+ check probes (cron inspection, spend CSV reads, container counts, backup age, heartbeat status), the threshold rules that define "judgment call" (2× trailing-7d etc. — deterministic provider-computed comparisons, 1406), the chown/reap remediation commands, table rendering and the Slack post, DM and BetterStack page delivery, and — in the realizable-today reading — the per-source cooldown state file itself. BetterStack's off-host paging is wholly external by design (1410).

**Verdict.** 🟡 — the body is expressible today as one instance with one batch action step (built L0a–L0d + LC3b), but the workflow does not start itself and its alert discipline straddles the kernel edge: the 09:00 trigger needs **L6 §§1–2**, which as written cover drift-free recurrence and CAS-claimed idempotent firing (the fire→create seam excepted — GAP-1); kernel-side severity routing needs **L8 §§2–4**, which as written cover addressed delivery, connectors, and per-recipient send idempotency (the tier mapping is config, not mechanism); and cross-run cooldown/dedup has **no home in either corpus as written** — the planned `policy_state` (L2 gates future §10) names rate-limit-shaped durable memory but is gate-scoped and silent on cross-instance reach, and L8 §4 dedupes sends, not conditions. Provider-side suppression keeps the workflow fully realizable today, so this is a boundary finding, not a blocker.

**Gaps.**
- **GAP-1 recurs:** the L6 fire→`CREATE_INSTANCE` seam — a re-claimed 09:00 fire after a crash between the create commit and the fire-row advance mints twin dashboard runs and double Slack posts.
- **GAP-2 recurs:** the batch-vs-kernel-grain boundary for the 35 checks and the per-remediation audit question are both the unwritten instance/step-weight-floor rule — the author decides "one errand or thirty-five" with no stated line.
- **Cross-run alert-suppression state has no kernel home (new):** cooldown + dedup per alert source is durable state consulted before firing that must survive across instances, but the transcript is per-run, the planned `policy_state` (L2 gates future §10) is gate-scoped and silent on cross-instance scope, and L8 §4's delivery ledger dedupes a single logical send, not a repeating condition — trigger scenario: a data source goes stale Monday and Monday's run DMs the warning; Tuesday's fresh instance re-detects the same condition and, with no kernel-readable record that the alert fired within its cooldown window, DMs again — precisely the spam the 1711 state file exists to prevent; harmless while suppression rides the provider, load-bearing the day L8 §4 owns delivery. → **GAP-6**

### S7. Cost Telemetry + MTD Throttle

**Facts (capture).** Context: "a single broken prompt that retries in a loop can rack up real money in a day" across twenty concurrent containers; cost self-awareness "has to be wired into the same surfaces that run the work" (1444). Three telemetry layers (1446): **per-API-call** — the credential proxy fronting every Anthropic request logs the response `usage` block (input / output / cache-read / cache-write tokens) plus model and the calling container's source IP to `logs/anthropic-cost-telemetry.jsonl`, computing `cost_usd` per call from a pricing table pinned in code (Haiku $0.80/$4, Sonnet $3/$15, Opus $15/$75 per million, cache modifiers); kill switch `ANTHROPIC_COST_TELEMETRY=0`. **Container-context join** — at every container spawn the runner writes `chat_jid`, `scheduled_task_id`, `group_folder`, `model_tier`, `started_at`, and the container IP to `logs/container-context.jsonl`; the two JSONLs join on `container_ip + time-window` so every dollar resolves to a skill or a chat thread. **Per-skill spend reports** — `scripts/cost-by-skill-report.py` aggregates by `scheduled_task_id`, then `chat_jid`, then `group_folder`; the daily digest surfaces top spenders. Three control loops on top (1448): the **MTD throttle** reads a CSV-driven monthly running total and runs three states — `normal` below 70% of the monthly target; `warning` at 70–90% (routes mid-tier traffic down a notch); `hard` at ≥90% (forces Haiku for everything except an explicit `use opus`); manual `use opus` always wins — "users self-escalate when they need it, the system does not silently downgrade a hard request"; `NANOCLAW_THROTTLE_OVERRIDE=1` bypasses the throttle entirely for incident response. The **Karpathy cost playbook** sets routing defaults — Haiku-first cascade, `HAIKU_BOUNDARY=0.05` widened, `OPUS_BOUNDARY=0.07` narrowed, classifier fallback Haiku instead of Sonnet; every routing decision lands in `logs/model-routing.jsonl` with its classifier score. The **dispatch budget governors** double as cost and rate-limit protection: per-host-session cap of 8 sub-agent dispatches, daily ARQ ceiling of 10, and a cross-source burst detector that pings admin when the sliding-15-minute count crosses threshold. A daily monitor at 08:00 UTC posts yesterday's spend by tier, cache-hit ratio, and MTD pacing with a linear month-end projection vs the trailing-7-day average, alerting on cache-hit <80%, daily spend ≥2× trailing, or MTD >90% of target by day 15 or earlier (1450); the alerts are cooldown-gated so a single bad day doesn't generate eight pings (1700).

**v3 decomposition.** By layer, because the layers land on opposite sides of the kernel edge.

*(a) The telemetry layers.* None of this is kernel territory, and the boundary argument is granularity: the proxy fronts individual Anthropic API calls (1446), and one P5 `DispatchIntent` is *performed* as many such calls — the per-call grain sits strictly below the kernel's smallest unit, on the performer's side of produce-not-perform. Capture, join, and report are runtime/observability work by design. What the corpus *does* claim is the coordination residue, and the "Operational observability, cost, and trace outputs" cross-level seam says it precisely: §1 — cost/trace/latency recorded as **durable facts** with source, timestamp, version, aggregation scope, and attribution (actor, definition version, model, runtime provider, child link), explicitly *not* masquerading as the workflow transcript; §2 — a cost ledger with roll-ups "across child workflows, retries, gates, and external providers while preserving per-source attribution," tied to the version/config that produced them. The structural observation worth recording: BitSafe's middle layer — joining two JSONLs on `container_ip + time-window` — is a heuristic reconstruction of an identity v3 owns natively. A runtime performing a `DispatchIntent` knows the instance/step/actor it performs for; the seam's attribution requirement makes the fuzzy IP-plus-clock join unnecessary. The seam as written covers the need (fact schema, attribution, roll-up, retention question), but it is topic-map only — no contract, no schema.

*(b) The MTD throttle.* Walk the candidate kernel homes and each one refuses it. **run_overrides:** snapshotted at creation (`run_overrides: snapshot(run_overrides)` — CREATE_INSTANCE) against a definition pinned by `RESOLVE_START`; per-instance and frozen by design, so it structurally cannot carry fleet state that must reach *already-created* instances' future dispatches — it is the right home for the opposite thing (see (c)). **L0c issued config:** `AgentConfig` is "an immutable portable run intent, *deterministically* resolved into the packet" — resolving it against a mutable fleet counter at dispatch time breaks the determinism/pin discipline unless throttle state were itself a versioned committed fact, and no fleet-scoped policy store exists in either corpus. **L2 policy_state (future §10):** the only named durable policy memory, explicitly for "budgets, rate limits" — but as written it is policy-local, gate-scoped, riding gated transitions; dispatch derivation is a post-commit projection, not a gated transition, so even a fleet-scoped `policy_state` has no written path to the model field of a `DispatchIntent` (the §9 typed transform outputs — effective priority, effective timing — are the nearest surface a routing transform could join, and they are listed as candidates only; MVP stays allow|warn|block). And GAP-6's finding recurs verbatim: `policy_state` is silent on cross-instance scope. **The runtime reading** is therefore not a concession but the design answer: produce-not-perform means the kernel produces the *ask*; which model serves each of the many API calls inside one performance belongs to the performer — and BitSafe's own throttle confirms the grain, acting per-call at the routing layer, where a kernel-side throttle could at best coarsely tier the whole dispatch. Fleet model-routing policy is runtime territory by design. The Karpathy playbook is the same verdict at rest: routing defaults and classifier boundaries are runtime configuration; `model-routing.jsonl` is runtime telemetry (its natural v3 home is a seam-§1 operational fact stream, attribution included). What the kernel *cannot* disown is the boundary contract the throttle must respect — (c).

*(c) Manual "use opus" + incident override.* The user-escalation half has a built kernel analog: a per-run pinned intent in `run_overrides` at CREATE, resolved into L0c's `issued_agent_config` provenance — exactly the capture's shape (self-escalation as explicit user intent, never silently downgraded). But the invariant crosses the kernel/runtime boundary and there it has no story: the kernel issues opus, the fleet is in `hard` forcing Haiku — *which wins*, and how would the transcript ever know? L0c §3 keeps issued-vs-applied explicit and names an executor/adapter **attestation** as future work ("issued_agent_config is provenance, not a runtime receipt"), but defines no contract; a *precedence* rule between kernel-issued run config and runtime fleet policy is written nowhere in either corpus. That is the genuinely new hole (gap below). The incident env var (`NANOCLAW_THROTTLE_OVERRIDE=1`) is the runtime overriding its own policy — no kernel analog needed; worth one note: it leaves no durable record, which v3's own discipline would route to a seam-§1 operational fact if realized.

*(d) Daily spend monitor.* S6-shaped, and S6's decomposition transfers wholesale: an L6 §§1–2 timer row (08:00 UTC, drift-free, CAS-claimed fire) mints one instance per tick whose body is one batch action step behind P5 — the spend math, cache-hit ratio, trailing average, and linear projection are all provider-computed thresholds, exactly S6's "judgment call" comparisons (1450). ### S8. Monthly Investor Update

**Facts (capture).** The thinnest capture base in the series so far, and that must be said plainly: the workflow itself is **one line** in the digest list — "monthly investor update drafted by sub-agent and reviewed by human" (1705), inside the digest family "fired on cadence regardless of state" (1705). No named reviewer, no draft location, no review channel, no publish destination, no rework mechanics appear anywhere. What the capture *does* supply is the governance frame the line sits in, and it is unusually well documented: [05] "Approval gates for anything that leaves the building" — "**Agents propose, people approve.**", "The newsletter agent drafts but never publishes", and the gates "sit exactly where a mistake would be public or hard to undo" (857–861); [10] "AI proposes, human disposes. The bot drafts; humans QA; the publish action is a deliberate gesture" (1746); and "Ask before X": "external-facing communications" require explicit human approval (1754). An investor update is external-facing by definition, so the human gate in 1705 is policy-mandated, not incidental. One honest nuance on the `PROPOSED —` page-title convention (1746): it is scoped to *policy pages awaiting debate*, and the same sentence explicitly says "a refreshed investor update" ships as a new version **without** the prefix — an evidence-based regeneration, not a proposal. So the S8 gate fact rests on 1705 + the drafts-never-publish frame, not on the title convention. Everything below about *how* the review loop works (approve/rework decision keys, what rework carries) is a modeling choice consistent with that frame, not a capture fact.

**v3 decomposition.** One `WorkflowInstance` per month; a three-step template — draft (agent step) → review (human_gate) → publish (auto action) → terminal — and this is the first simulation whose *core* is a genuinely built corpus mechanism: the L3 human-decision errand end to end.

- *Trigger.* An **L6 monthly cron series** (`series_id` recurring identity, durable row carrying `process_after` + recurrence, drift-free advance via cron parser, CAS-claimed firing per L6 §§1–2) mints `CREATE_INSTANCE` + `KICKOFF`. Monthly recurrence is squarely inside L6 §§1–2 as written; the fire→create seam is GAP-1 verbatim (a re-claimed fire after a crash between the create commit and the row advance drafts the same month's update twice).
- *Draft step* (L0b agent step): P5 **`DispatchIntent`** to the drafting actor — the capture's "sub-agent" (1705). Modeling choice: a bound actor behind one dispatch is the minimal faithful form; an L4 child spawn (`SpawnIntent` → child instance → `CHILD_LIFECYCLE` via the `wait_for` ChoicePoint) is equally expressible if per-round context isolation is wanted, but nothing in 1705 requires it. The actor assembles the update provider-side (metrics pulls, LLM drafting, the draft page write) and emits `drafted` — a P2 `transitions` principal-committed selection through the P3 ladder under its P4 warrant, the draft ref riding the payload into the gate's handoff.
- *The human gate — full built-corpus depth.* The `drafted` edge targets the human_gate; `apply_target_entry_effects` sees `is_human_gate` and `park_for_human_decision` runs **inside the arrival commit**: a fresh `request_ref` is minted, a **`DECISION_REQUEST`** transcript entry commits — `{request_ref, recipient: step.role, decisions: decision_keys(step), recommendation, recommendation_source, context_ref}` — and the instance parks `WAITING(human_decision)` with `resume_events = decision_keys(step)`. Post-commit, the P5 **`HumanDecisionRequest`** directive is projected to the bound operator: question, decision context, `allowed_decisions`, and `decision_requirements` — the per-decision required payload fields surfaced to the UI from the same declared map the submit path enforces. This is the full-form human-decision errand of the P1 table (`DECISION_REQUEST` + `WAITING(human_decision)` → operator → `SUBMIT_DECISION`, correlated by `request_ref`); its delivery is "local/manual … durable channel L8" per the unit's own note.
  - *The decisions map is the P2 ChoicePoint*, principal-committed by the bound operator; the kernel routes by declared key and does not know what "approve" means. Modeling choice for S8: `approve → publish_step`, `request_rework → draft_step`, with **`request_rework` declaring a required non-empty `instruction`** — exactly the corpus's own anchor case ("the anchor's request_rework requires a non-empty instruction", SUBMIT_DECISION.txt / `required_fields`): a rework verdict with an absent or empty instruction is `Rejected(missing_required_field)` at submit, before any commit.
  - *Recommendation/override:* the mechanism exists and is built — `incoming_recommendation` reads `recommends` off the firing edge; choosing against a recorded recommendation without `override: true` is `Rejected(override_required)`, and flagging override with nothing to override is `Rejected(override_not_applicable)` — but the honest S8 modeling choice is to declare **no** `recommends` on the `drafted` edge: the draft *is* the proposal ("AI proposes, human disposes", 1746), and a machine self-recommendation of "approve" on its own draft would invert the fiduciary point of the invariant. Absent recommendation ⇒ every decision is equal and override never applies.
  - *The human's submit — CAS/idempotency.* `SUBMIT_DECISION` carries `{instance_id, op_id, expected_version, request_ref, verdict, override?, payload, by}` and climbs `admit_input`'s operator rungs in order: **op_id idempotency** (a double-clicked or retried approve is `Duplicate`, not a second routing), **state** (`WAITING(human_decision)` else `not_awaiting_decision`), **correlation** (`wait.request_ref` must equal the submit's `request_ref` else `decision_request_mismatch` — a stale approval aimed at a *previous round's* request can never complete the current park), **version CAS** (`Stale`), **authority** (`by` must be `instance.binding[step.role]`, both missing and mismatch branches declared `operator_not_authorized`). Two reviewers racing: one commit wins at `expected_version`; the loser gets `Stale` — at-most-once decision routing is structural, not conventional.
  - *The rework loop and round hygiene.* On `request_rework`, `choice.target` is the draft step; the loop-back trips `advances_round`, so the same commit runs **`clear_stale_decision_context`** — the stale review/approval context is dropped, the fresh rework payload (the instruction + refs) survives as the handoff, and `instance.round` advances in `apply_target_entry_effects`. The re-arrived draft step resumes ACTIVE and the post-commit `DispatchIntent` carries the instruction to the drafter. When round 2's draft re-enters the gate, `park_for_human_decision` mints a **new** `request_ref` — the round-1 ask is dead by correlation, so a late round-1 approve cannot ship round 2's draft. This loop is the exact anchor shape the L3 units were built around; nothing here is planned-level.
- *Publish step* (LC3b auto action — "the publish action is a deliberate gesture" made kernel-visible): P1 errand claims `action_running(req, episode)` → P5 **`ActionIntent`** to a delivery runner → `ACTION_RESULT` classified through the P2 `outcomes` ChoicePoint (`sent | send_failed | infra_error`, infra re-parking under the episode retry budget) → terminal COMPLETE → LC teardown. Send-effect idempotency (crash after the provider sent but before `ACTION_RESULT` landed) is provider-side today; kernel-side durable send accounting is **L8 §4**'s delivery ledger — stable delivery id, retry-against-the-same-record, marker written only after a confirmed effect — which as written covers exactly this. A crash inside the window leaves the durable `action_running` marker for the L9 watchdog (GAP-4).
- *Levels:* built L0a–L3 + LC carry the entire body — draft, gate, rework loop, publish; planned **L6** carries the trigger, **L8 §4** the durable ask + publish delivery, **L9** the unanswered-review disposition (below).

**External tool boundary.** Behind P5: the metric/data pulls and LLM drafting of the update; the draft page write (Notion); delivery of the `HumanDecisionRequest` to the reviewer's surface (Slack/Notion — local/manual today, L8 later); the review UI that renders context, allowed decisions, per-decision requirements, and collects the verdict + instruction; and the outbound publish itself (email/page to investors) with provider-side send idempotency. The kernel coordinates only what it should: the park, the correlated decision record, the round-advancing rework loop, and the publish errand's claim/outcome.

**Verdict.** 🟡 — but with the emphasis inverted from every prior section: the *core* of this workflow, the human gate with its rework loop, is **fully built** — DECISION_REQUEST park, projected `HumanDecisionRequest`, the decisions ChoicePoint with per-decision required fields, the override invariant, round advancement with stale-context clearing, and the five-rung admission of the human's submit are all normative corpus today, and S8 exercises them without a single stretch. The 🟡 comes from the edges: the monthly trigger needs **L6 §§1–2**, which as written cover drift-free monthly recurrence and CAS-claimed firing (the fire→create seam excepted — GAP-1); durable delivery of the ask and the publish needs **L8 §4**, which as written covers the delivery ledger both need; and the unanswered-review case — the reviewer never submits — is an explicitly *declared* deferral (the P1 table's human-decision failure shape is "no timeout (L9)"; L3-future §2 already names the needed dispositions `deny | expired | escalated` and the park-durably-resume-through-ingress rule, but no mechanism is written). **Gaps.**

### S9. ARQ Dispatcher

**Facts (capture).** Trigger: `research-queue-dispatch.py --apply --min-priority P2 --include-surface-actions` runs every 15 minutes during business hours and hourly overnight; it reads the Active Research Queue — a Notion database with priority and status — enforces a daily cap of 10 dispatches, and spawns sub-agents for the eligible rows; P3 work runs on its own slower cadence (every 30 minutes during business hours) "so it does not starve P1/P2" (1404). The ARQ itself catalogs capability gaps and skill proposals; agents file ARQ entries rather than failing silently, and Aki performs weekly triage (1224). The dispatcher writes findings child pages back into Notion and auto-flips parent rows to `Findings ready` when a child page is detected — a 2026-05-13 *pre-dispatch guard*, added after one ARQ row accumulated **26 duplicate findings pages** because the dispatcher kept re-picking a row whose status was stuck at "In investigation" (1404). "The dispatcher is intentionally separate from the work; it is the planner, not the worker" (1404); "the dispatcher does not block; it queues" — short-lived ticks, no waiting (1412). Workers run in a concurrent container pool sized by `MAX_CONCURRENT_TASKS` (1430); Notion-only research agents run unisolated (1432). Three dispatch governors (1434): a per-host-session cap of 8 sub-agent dispatches (soft warning at 5; exceeding 8 returns exit 7 and refuses), the ARQ daily cap of 10 (`NANOCLAW_ARQ_DAILY_CAP`) — hitting it stops the dispatcher in apply mode and reports the queue depth to admin — and a cross-source burst detector (`scripts/dispatch-burst-detector.py`) that joins the per-host-session counter and the ARQ daily count and fires an admin ping when the union crosses a threshold. The cap-hit ping is a named escalation alert: "ARQ circuit breakers when the research-queue dispatcher hits its daily ceiling" (1709).

**v3 decomposition.** The planner-not-worker split (1404) is produce-not-perform speaking BitSafe's dialect: the dispatcher tick *selects and mints, never researches* — exactly what a kernel instance should be. But the minting is where the built corpus runs out.

- *(a) Planner/worker split.* The tick is an **L6-fired sweep instance**: a timer fire mints a short-lived instance whose single LC3b auto action (P1 inline/full errand: `action_running` claim → P5 `ActionIntent` to a selection runner → `ACTION_RESULT` through the P2 outcomes ChoicePoint) selects eligible rows and mints workers, then COMPLETEs — matching 1412's exit-don't-wait shape (and pricing ~55 mostly-empty tick instances/day against GAP-2's unwritten weight floor). The workers fork the design: **L4 children are the dishonest route.** `park_for_child` parks the parent `WAITING(child_event)` on exactly ONE `wait.link_id`, and `CHILD_LIFECYCLE` rejects `not_awaiting_this_child` whenever the parent is not parked on that precise link — so a dispatcher that spawns and exits (as 1412 requires) gets every child completion *rejected at delivery*; N>1 concurrent children are not built (static step list + singular wait slot — GAP-3's exact finding, here with runtime-sized N = the eligible-row set); and L4 future §2's parent-close "detach" names a close-time policy, not a spawn-time mode, while §4's N-child controls extend *awaited* fan-out. **Independent top-level instances are the honest route:** workers are full instances minted via `CREATE_INSTANCE` + `KICKOFF`, issued by the sweep's runner through ingress behind the P5 boundary. What carries the provenance once the kernel link is gone: convention on both transcripts — the worker's task payload carries `{arq_row_id, dispatcher_instance_id, fire_id}` (durable in its transcript from creation), and the sweep's `ACTION_RESULT` records the minted instance ids as T1 evidence. That is greppable provenance, not *routable* provenance: no lifecycle delivery, no cost roll-up (L4 future §1) — acceptable here precisely because nothing awaits, but the missing construct is real: `SpawnIntent` exists only as `park_for_child`'s post-commit output; the kernel has no **detached spawn** — mint-without-parking with a durable link (new gap below).
- *(b) The 26-duplicates bug.* BitSafe's "row is being worked on" state lived in the **Notion row status — mutable world state maintained by a side effect** — and when the flip didn't happen, every subsequent tick re-picked the row and minted another worker: read-check-act over world state with no claim. The three candidate homes, judged: the external status (what demonstrably failed — copying it into v3 fixes nothing); a kernel-side claim (the nearest construct, `park_for_child`'s idempotent-on-the-ACTIVE-link `ChildWorkflowLink`, is **per-parent-instance** — each tick is a *different* sweep instance, so no built claim registry spans ticks); and **GAP-1's creation-grain identity — the twin-proof answer**: key worker creation on the ARQ row id with active-uniqueness (the L8 §1 "auto-create over hijack" oracle shape: mint-or-return-existing), and tick N+1's mint attempt for a row with a live worker returns the existing instance — 26 duplicates become impossible *by construction, regardless of what the status field says*. The completed-but-unflipped case is covered too: the terminal worker instance keyed on the row id is committed, queryable kernel state — "has this row produced findings" becomes a transcript fact (findings page ref as T1 evidence), not child-page detective work. One deliberate deviation from the L4 precedent: `park_for_child` lets a terminal link *not* block a fresh attempt (retry-friendly); ARQ wants terminal-blocks-until-re-triage, so the uniqueness key needs an attempt/generation dimension that only Aki's weekly triage (1224) advances. The sharp finding: **v3-as-built would NOT have prevented the incident** — bare `CREATE_INSTANCE` carries no external-identity key (GAP-1's operator/API path), so the runner-mints form re-creates BitSafe's failure verbatim. The 26-findings incident is GAP-1's real-world casualty: empirical proof that the gap is load-bearing, not theoretical.
- *(c) Governors.* Read against **L6 §3** precisely: the `min(capacity, batch, ready)` rule and the governor/callback separation match the dispatcher's shape well (the governor decides, the mint callback performs — the planner split again), and §3's fourth bullet even covers dispatch-accounting failure posture ("count it as a dispatch failure unless… durable, recoverable state"). But §3 as written covers **per-tick capacity only**. The per-host-session cap of 8 (1434) *is* the `batch` term — covered. The **daily cap of 10 is a calendar-windowed quota**: durable counter state surviving across ~55 tick instances, reset at day boundary, shared across the P1/P2 and P3 series, with count-vs-mint atomicity under crashes — §3's "scheduling bookkeeping should live in scheduler-owned state" *names the home* but writes none of the window/reset/shared-across-series semantics. The **cross-source burst detector is covered nowhere**: it joins counters owned by two *independent* schedulers (the host-session loop's and the ARQ dispatcher's — 1434) in a third observer; §3 governs one scheduler's dispatch, and no section owns fleet-spanning counter state. Both are kin to GAP-6's finding (durable cross-run state consulted before firing), with one difference: GAP-6's suppression state had no named home, the daily quota has a home with no contract. The cap-hit circuit breaker (1434, 1709) needs no L9 machinery: it is a quota breaker, not a failure-count breaker (L9 §5's breakers and S17's 3-failure family are the latter) — decomposed, it is a declared sweep outcome (`cap_exhausted`, carrying queue depth) whose route `emits:` the admin alert directive — completion routing plus a fire-and-forget P5 ask, with the once-per-day ping suppression again GAP-6-shaped.
- *(d) Priority anti-starvation.* Expressible, and cleanly: **two (or three) L6 timer series over one queue** — series A binding `min_priority: P2` with the business-hours-15-min + overnight-hourly recurrence (standard multi-line cron; two rows sharing one logical series or two series minting the same template), series B binding the P3 filter at 30-minute business-hours cadence (1404). The filter is *not* kernel state — the de-vocabularized kernel routes by declared keys and never reads "P2"; each series' target binds the filter as an L0f slot in the sweep task, consumed by the selection runner behind P5. Anti-starvation emerges from series separation, not from any kernel priority scheduler — the right boundary. The one wrinkle: the daily cap of 10 spans both series (1434 states one `NANOCLAW_ARQ_DAILY_CAP`), which is exactly (c)'s shared cross-series counter.
- *(e) Findings write-back + status flip.* Inside the **worker** template, as completion routing: research step (P5 `DispatchIntent` to the research actor; Notion-only, unisolated per 1432) → findings-page write and status flip as declared LC3b action steps (P5 `ActionIntent`; outcomes `findings_written` / `flipped` / `infra_error` through the P2 outcomes ChoicePoint) → COMPLETE. `Findings ready` thereby becomes the projection of a *routed kernel fact*, not something the dispatcher must detect — which dissolves the pre-dispatch guard's primary job (that job moves to (b)'s creation-grain identity). A crash between the findings write and the flip leaves a durable `action_running` marker whose reconciliation is the named L9 deferral (GAP-4); until L9 lands, BitSafe's child-page-detection guard survives as provider-side belt-and-braces in the selection runner, reconciling world drift from workers that died mid-flip.

**External tool boundary.** Behind P5: the ARQ Notion reads (priority/status query) and eligibility filtering; the research work itself (LLM + sources); the findings child-page writes and the status flips with provider-side effect idempotency; the admin pings, queue-depth report, and burst-detector alerting surfaces; container-pool capacity (`MAX_CONCURRENT_TASKS`, 1430 — the runtime fact feeding §3's `capacity` term); worktree/no-worktree isolation (1432); and the env-var override surface (1434). The kernel coordinates only: tick firing, exactly-once worker minting, the quota decision, and the worker's step/outcome routing.

And the routing lesson, learned the hard way and load-bearing for v3's whole thesis (2028): handing "a long, many-step job to the side tuned for short, sharp tasks" yields "truncated, half-finished output. The fix was not a better model. It was a clearer rule about which side owns long-running, human-gated work. **'Orchestration that has to wait for approval belongs with the brain.'**" Ownership tiebreak: "If the inputs and the approval already sit in the workspace, the workspace owns it… We write that decision down" (2030). No trigger mechanism is stated beyond the weekly framing (2020).

**v3 decomposition.** One **weekly content-cycle instance** carrying the whole arc — surfacing action → topic gate → schedule → draft → design child → sign-off gate → publish — and the instance-boundary argument is the honest work here.

- *(a) Instance boundary.* Three candidate cuts, two rejected. **Approval-as-CREATE** (candidates are just rows; a human approving one mints the piece-instance via operator `CREATE_INSTANCE`): rejected as dishonest — it evicts the first gate from the kernel's audit horizon, and the capture's own thesis forbids that: "nothing advances to drafting on a machine's recommendation alone" (2020) and "the workspace holds… the approval state" (2022) demand the approval be a *committed workflow fact* — a `DECISION_MADE` under the P3 ladder — not a pre-kernel convention; 2028 says the waiting-for-approval itself is the brain's job. **Per-candidate instances**, each parked at its own gate: rejected — the capture's review is a 1-of-N selection ("approves *a topic*", singular, 2020), so N sibling gates mismodel it: approving one leaves N−1 instances parked `WAITING(human_decision)` forever (GAP-4 amplified), and no kernel construct couples sibling instances' gates for disposal. **The honest cut: one cycle instance.** The weekly trigger (modeling choice — the capture states only the cadence) is an L6 §§1–2 timer series; the fire mints the cycle instance whose *first step is the surfacing itself* — an LC3b auto action: `action_running` claim → P5 `ActionIntent` to the reach runner → the reach listens across Slack/web/transcripts and writes candidates **as structured records provider-side** (exactly 2012's permanence rule) → `ACTION_RESULT` through the P2 outcomes ChoicePoint (`candidates_found` / `nothing_found` / `infra_error`), candidate refs riding as evidence into the gate's `context_ref`. A standing continuous reach planner on its own cadence is an equally faithful variant (S9's decomposition transfers, coupling through the candidate rows as in S5); the weekly framing makes the in-template step the simpler honest form.
- *(b) The two human gates.* S8 §"The human gate — full built-corpus depth" transfers wholesale — `park_for_human_decision` inside the arrival commit, fresh `request_ref`, `DECISION_REQUEST` entry, projected `HumanDecisionRequest`, the five-rung admission of `SUBMIT_DECISION` — so only the deltas are argued. **Two gates in one template** is unremarkable by construction: a human_gate is just a step type; each park mints its *own* `request_ref`, and the correlation rung (`wait.request_ref = decision.request_ref` else `decision_request_mismatch`) makes cross-gate confusion structurally impossible — a stale topic-approval can never complete the sign-off park. **Different decision maps**, both de-vocabularized P2 `decisions` instances: gate 1 declares `{approve_topic (required non-empty field: topic_ref), no_topic_this_week → terminal skip}` — the 1-of-N selection rides the *decision payload* through `required_fields(choice)`, not N sibling gates; gate 2 is S8's exact anchor shape, `{approve → publish, request_rework → draft (required non-empty instruction)}` with the round-advancing loop and `clear_stale_decision_context`. One boundary noted as such: the built recommendation/override invariant operates at decision-*key* grain (`recommendation` is a verdict key), so the reach's candidate *ranking* cannot engage `override_required` — a human approving a lower-ranked topic is invisible to the override rule. The capture's stated invariant is the machine→advance direction, which the gate itself fully delivers; payload-grain recommendation is v3 territory beyond the capture, so noted, not registered.

A **detached request re-entering via ingress** is the worst fit: it trades the durable link for GAP-9's convention-grade provenance for no gain — unlike S9's dispatcher, the piece-instance *does* wait for the visuals (the sign-off gate needs them). The line: the kernel earns entry the moment the wait must **survive the performer** — a retrieval that outlives the actor session or needs independent audit is exactly the L5 help-ask, whose slots the corpus already holds reserved (the agent-emit opener in errand.txt; the *stay* route in choice_point.txt; paper-tested PASS in the primitives memo §8). Planned, and designed; not needed for 2010's stated shape.

Brief because it is a discipline match, not a mechanism question.
- *(f) The routing lesson (2028–2030).* This is v3's thesis in BitSafe's dialect, and the mapping deserves to be explicit. ### S11. Ship Pipeline (CI/CD)

**Facts (capture).** Trigger: "a push to any `feat/*` or `fix/*` branch triggers `dev-deploy.yml` on GitHub Actions"; the workflow builds the container, deploys to the dev VM, and runs a 30-minute smoke watch; the `auto-promote-listener.py` daemon "polls the dev VM's health endpoint and, if the watch passes clean, merges the branch to `main` automatically"; prod restarts shortly after — `pending-restart.sh` runs every 5 minutes, "waits for 0 active container agents, and obeys a 30-minute rate-limit gate to prevent thrash"; "the whole loop is hands-off: an agent pushes a feature branch, and the code lands on main without anyone clicking merge" (1418; the [07] restatement adds journalctl as the watched surface and "prod cron restarts within 5 minutes", 1295). **Hotfix lane:** any commit containing `[hotfix]` shortens the smoke watch 30→5 minutes, writes `data/restart-pending-hotfix` instead of `data/restart-pending`, and `pending-restart.sh` skips its rate-limit gate (still waits for 0 agents unless `NANOCLAW_HOTFIX_FORCE_RESTART=1`); lead time ~36→~11 minutes; the tag is "engineer judgment, not a default" (1420). **`[uat]` tier:** when a commit message contains `[uat]`, "auto-promote holds the branch until a human green-lights it via a Slack reaction"; the default is the opposite — clean dev run + 30-minute smoke suffices; hotfix shortens smoke but does not skip the uat gate (1750). **Exception-file gate:** "hard exceptions requiring human review" — Dockerfile/container changes, `src/db.ts` schema migrations, the egress-firewall script, package.json major bumps — "the automation refuses these; humans execute `promote-to-prod.sh` post-review" (1299). **Pre-commit hooks:** prettier auto-format, the encrypted-DB audit, and the worktree-mass-deletion guard (>20 files / >2000 net lines aborts; `ALLOW_MASS_DELETE=1` overrides) run on every commit (1422). **Build discipline:** `npm run build` auto-snapshots `dist/` and sets `data/restart-pending`; container builds auto-tag with release timestamps (1424). **Bottleneck:** "smoke watches serialize on `flock`; five branches in flight queue end-to-end for ~2.5 hours"; `promote-to-prod.sh --auto --hotfix <branch>` can inject a branch at the front of the queue; parallelizing the watch is roadmap (1438). "An agent can push a fix at 03:00 UTC and the fix ships before anyone wakes up" (1426).

**v3 decomposition.** One `WorkflowInstance` per branch-push — per **promotion attempt**, identity `(branch, head_sha)`. Template sketch (one static template, three declared paths): deploy step (LC3b auto action) → **smoke wait** (`type: wait`) → eligibility classifier (LC3b) → {merge step | uat gate | high-risk human path} → restart-marker handoff → COMPLETE. This is the series' first genuine timed wait, and its core is built.

- *(a) Instance boundary and ingress.* The push event enters as an **L8 message-source channel** (a GitHub webhook through the §3 connector contract, normalized per §§1–2), correlating exactly on `(branch, head_sha)` — §1's store-enforced `UNIQUE` oracle with auto-create is precisely "one promotion per push" and covers webhook redelivery **as written**; the bare operator/API ingress path dedups nothing at creation grain — GAP-1 verbatim (a redelivered push mints twin promotions: two watches on one deploy and a double merge attempt). Modeling choice on a *second* push to the same branch mid-flight: active-uniqueness on `branch` with supersede — the new push should CANCEL the stale attempt (the built `CANCEL` intent can kill it), but *who issues that CANCEL* is the same unowned-cancel-authority seam S4 recorded in GAP-5's family; without it, a stale promotion's late `smoke_clean` is only fenced by (b)'s stale-intent handling.
- *(b) The 30-minute smoke watch.* The deploy step's `ActionIntent` (P5) has the runner deploy **and arm the watcher**; its `deployed` outcome routes to the wait step, whose arrival parks `WAITING(smoke_watch)` with `resume_events: [smoke_clean, smoke_failed]` — the **open-door errand** of `errand.txt` exactly: marker only, no outbound directive, "the kernel waits for the world." **WHO detects:** the provider watcher (the `auto-promote-listener.py` role, 1418) observes journalctl/the health endpoint for the bound duration and issues `RESUME_WAIT(smoke_clean)` at T+30-clean or `RESUME_WAIT(smoke_failed)` at first error — the kernel never polls. The resume climbs `admit_input` (op_id → `not_waiting` state guard → `event.type ∈ wait.resume_events` → version CAS), and the **on_resume ChoicePoint** — kernel-classified: the event's validated-and-routed type is the key — routes `smoke_clean → classifier`, `smoke_failed → halt/notify` (or a re-deploy self-target). All built. **Where the 30-minute deadline lives — three homes, judged:** (i) *provider-owned clock* (BitSafe's reality): the watcher owns the timer and `smoke_clean` IS the deadline firing clean — expressible today and honest, since the verdict is genuinely the watcher's classification; (ii) *kernel-side L6 timer errand* (the primitives memo names the mapping: durable timer row → `TIMER_FIRED`, reload-and-discard-if-stale): a `timeout` key in `resume_events` fired at park+30min — the race against a watcher's `smoke_failed` is single-winner structurally (state guard + CAS; the losing fire discards per L6 §2, covered as written), but timeout-means-clean inverts the usual semantics, so its better use is a dead-watcher backstop, which is really L9 §5 territory; (iii) **L9 §2's WaitCondition-as-durable-checkpoint** names exactly this need as written — "correlation discriminators, deadline/escalation policy, and stale-intent" declared *in* the wait, wait state surviving crash with timeout/escalation auditable, "internal deterministic waits (child lifecycle, timers) are the simpler forms" — but names it only: the built wait slot has no deadline field, and the seam that materializes a WaitCondition deadline as an L6 row and obsoletes the row when a resume wins is written in neither section. **L9 §4 stale-intent** covers the late-event side as written (a late `smoke_clean` after supersede or re-park: evaluated against expected version and allowed intent window, recorded as related evidence rather than silently dropped); the built path already answers `Stale`/`Duplicate` via CAS + op_id, but note the correlation grain: the bare wait correlates by resume-event **class** (`resume_events`), not per-watch identity — there is no `request_ref` analog pinning a resume to *this* watch attempt; §2's declared correlation discriminators are the named fix. One more note: `RESUME_WAIT` carries **no authority rung today** (a declared later slice in the unit) — the resume that ships a merge to main is unauthenticated at the kernel; L8 §1's channel-authentication rule is where the watcher's identity belongs.
- *(c) The `[uat]` conditional human gate — routing, not a dynamic template, and not a machine-committed approve.* The dishonest option first: an always-present gate whose approve is machine-submitted when no `[uat]` tag. `SUBMIT_DECISION`'s authority rung requires `by = instance.binding[step.role]`, and the decisions ChoicePoint is **principal-committed** — "an authorized principal picks, and the commit is theirs." Binding a machine principal to the reviewer role is mechanically possible and semantically a fiction: the accountability the gate exists to record evaporates (a bot's `DECISION_MADE` on every routine promotion), and it prices a park + `HumanDecisionRequest` + submit round-trip of pure ceremony per push. The selector-authority taxonomy already names the honest home for machine selection — **kernel-classified** — and that is the outcomes ChoicePoint, not decisions. **So: routing.** One eligibility classifier action step (LC3b) after `smoke_clean`: its runner validates the commit message *and* the changed-file set behind P5 and returns `auto | uat_hold | high_risk` through the P2 outcomes ChoicePoint (kernel-classified on the validated result); three static template paths, kernel de-vocabularized throughout (`uat_hold` is an opaque key). The gate, when entered, is **S8's built human-gate machinery wholesale** — DECISION_REQUEST park, projected `HumanDecisionRequest`, decisions ChoicePoint, five-rung admission of the submit (cite S8; nothing to re-derive). The **Slack reaction** green-light is the operator's `SUBMIT_DECISION` delivered through an L8 connector, and **L8 §4a's correlation-by-stored-state covers it as written**: the reaction echoes only an opaque handle; routing authority is the durable request record — a reaction on the wrong message cannot ship the wrong branch. **The exception-file gate** is the same classifier's `high_risk` route (1299's file list is design-time classifier config, L0f-pinnable): it lands on a human_gate whose approve leads to an **LC3a operator-action step** — `WAITING(action_pending)` → `ActionRequest` → the human's `RUN_ACTION` runs the promote under the kernel's single-winner claim — the faithful in-kernel form of "humans execute `promote-to-prod.sh` post-review" (1299); a terminal `halted_for_human` with fully out-of-band execution is the degenerate alternative. **Pre-commit hooks** (1422) never touch the kernel: they run at commit time, before any push exists — repo/provider guards upstream of the trigger, out of scope by construction. **The hotfix lane is L0f as built**: one template, targets `standard`/`hotfix` binding `smoke_duration` (30m/5m) and the restart-marker variant as slots; `RESOLVE_START` pins the resolved view per run; the ingress connector selects the target from the validated tag at create time. The asymmetry — hotfix as resolve-time slots, uat as in-instance routing — is right, not accidental: hotfix varies *bindings* on the same path shape, uat varies the *path*, and 1750 says they compose (hotfix shortens smoke but keeps the uat gate) — slots × routing composes for free, where encoding both as targets or both as paths would square the variant count. The queue-front injection (1438) is provider queue policy — (e).
- *(d) Prod restart: downstream convergence, not instance coordination.* The instance's contract honestly ends at "merged + restart marker written" (the merge outcome's action writes `data/restart-pending[-hotfix]` behind P5 — the marker file is world state, 1424/1420). `pending-restart.sh` is a **level-triggered provider reconciler** (host cron, 5-minute period) whose admission conditions — 0 active container agents, ≥30 minutes since last restart — are fleet runtime state, and S7(b)'s produce-not-perform argument transfers verbatim: when and whether the fleet restarts belongs to the performer. If pulled kernel-side, both conditions land in known holes: the 30-minute rate-limit gate is **GAP-6's cross-run rate-limit state** verbatim (planned `policy_state` names "rate limits" but is gate-scoped with no cross-instance reach), and the agent-count is cross-scheduler runtime capacity — L6 §3's capacity-informed governor names the shape, GAP-10's cross-series counter silence applies. Provider-side by design is the verdict, not a concession.
- *(e) The flock — cross-instance mutual exclusion.* Five parked promotions cost the kernel nothing (parked instances are cheap; the ~2.5h is provider throughput, 1438) — but the **mutex itself has no kernel story**: no claim/lock construct spans instances in either corpus. Judged against the nearest constructs: the wait slot is per-instance; L4 links are per-parent; L6 §3's governor bounds *dispatch from a scheduler*, not mid-instance acquisition of a singleton external resource by already-running instances; GAP-10's scheduler-owned counters are quota, not exclusion. ### S12. Code Factory SDLC

**Facts (capture).** This is a **forward-looking spec, not a shipped system**: "Published 2026-05-25 · Type: forward-looking spec" (3080), a 4-week MVP plan (3177–3201) whose own open-questions list is still undecided — including the spec-approval policy itself (3213) and blocker escalation (3216); the simulation takes the spec as written. Vision: a 24x7 autonomous SDLC pipeline "patterned on NanoClaw's three-queue model" — "ideas flow in one side, shipped commits come out the other," humans approving at high-stakes gates (spec sign-off, prod promote) (3082, 3087); core thesis: "the bottleneck isn't agent capability — it's queue discipline, state visibility, and reversibility" (3090). **Research Queue**: a Notion DB (Topic, Why Relevant, Source URL, Priority P0–P3, Status, Owner — 3099); entry via agents auto-filing `suggest_research`, humans dropping links, weekly review promoting high-signal items (3102); a Triage agent "runs every N hours: dedups, scores, drafts a 1-page brief, flags decision-required items for admin" (3103); promotion gate: approved items become specs (move to Task Queue), rejected items archive with reason (3104). **Task Queue — the SDLC spine**: each task a Notion row with nine SDLC-step checkboxes from "Spec drafted (acceptance criteria + test plan)" through "Shipped (CHANGELOG trailer consolidated, ship-log entry posted)" (3111–3119); schema: Title, Spec relation, Tier (1–4), Status, Owner agent, Blocker, Worktree branch, PR URL, Acceptance criteria (3120). **Ship Queue**: dev VM auto-deploys every push, CI lint/typecheck/unit; 30-min journalctl smoke window, clean → auto-merge; exception-file gate refuses auto-promote on high-risk files (Dockerfile, DB schema, firewall, major dep bumps) (3126–3128). State machine: `idea → researching → spec_drafted → spec_approved → building → in_review → ci_green → on_dev → promoting → shipped`, plus "rejected at any gate → archived (with reason)" and "blocked → flagged-to-admin (ask-admin RPC)" (3134–3136). Spec approval is "human or auto-approve for Tier-4" (3112); the tier policy is open question #2 — "auto-approve Tier-4 (doc / refactor / housekeeping)? Human-only for Tier 1–3?" (3213). Six roles (3142–3147): Triage; Spec; Build — "claims a worktree, implements, writes tests, opens PR. Bounded turn budget; on overrun emits a rescope-handoff"; Review — "independent peer agent: checks acceptance criteria, runs tests, comments on PR"; Ship; Watchdog — "heartbeat alarms, stuck-agent detection (max-turns / wall-clock / livelock), budget tripwires." Safety rails (3151–3158): worktree isolation; file-claim locks — "claim_file / release_file prevent two agents racing on the same path; auto-expire after 25 min" (3152); exception-file gate (3153); CHANGELOG trailers — agents write structured commit trailers, "orchestrator consolidates on main (no merge conflicts on shared doc files)" (3155); bounded turn budgets — "agents that hit cap emit a rescope-handoff JSON for auto-redispatch (depth ≤ 2, spend cap $5/chain)" (3156). Observability: per-queue heartbeat tasks, daily ship log, budget tripwires at 80/95%, stuck-agent paging (3162–3165). Success metric relevant below: >90% of Tier-4 commits shipped with zero human intervention (3221).

**v3 decomposition.**

- *(a) The state machine — a composition, not one instance.* The honest cut is **one `WorkflowInstance` per Task row carrying the SDLC spine** (spec_drafted → shipped): the nine checkboxes (3111–3119) are literally a template's step list — spec draft (agent step, Spec actor) → tier route → spec gate → build → review → CI wait → dev/smoke/promote (S11's territory) → consolidate + ship-log (completion-routed action steps) → COMPLETE — and the Notion Status/checkbox columns become projections of routed kernel facts, exactly S9 (e)'s move; 3090's "state visibility" demand *is* the transcript. One instance for the whole `idea → shipped` chain is the wrong cut: RQ items massively outnumber tasks (dedup and rejection happen pre-promotion), the queues run independent cadences, and Triage's dedup/scoring is queue-scoped planner work, not per-item steps. So the prefix (`idea → researching → spec_drafted`) is **S9-shaped planner territory**: the every-N-hours Triage agent (3103) is the ARQ dispatcher verbatim — an L6 §§1–2 timer series minting a sweep instance whose single LC3b action (P5 `ActionIntent` to a selection runner) dedups, scores, and drafts behind the directive, with per-item RQ state world-side in the Notion row. The segments join at **promotion**: "approved items become Task rows" (3104, 3143) means the planner mints the task instance and exits — S9's finding twice over: exactly-once creation keyed on the RQ item id (GAP-1 — a redelivered approval or re-run sweep mints twin task instances for one idea) and mint-without-parking (GAP-9). Transition mapping across 3134: `researching → spec_drafted` and `building → in_review` are **actor emits** — P2 `transitions`, principal-committed by the bound Spec/Build actor through the P3 ladder under P4 warrants; `spec_approved` is the (b) gate; `in_review → ci_green` is a **machine completion**: the instance parks a bare wait (`WAITING(kind)`, resume_events `{ci_green, ci_failed}`) and the CI provider's webhook resumes it — today via harness-driven `RESUME_WAIT`, durably via the L8 §§1–3 connector correlating exactly on PR/branch id; `on_dev → promoting → shipped` is S11's ship pipeline (smoke watch, auto-merge, exception-file gate — that gate being the same deterministic path-class conditional-route family as (b); depth deferred to S11). **`rejected at any gate → archived`** is not `CANCEL` but a declared terminal route: each gate's ChoicePoint declares a reject key targeting one terminal archive step, and "with reason" rides the built `required_fields` mechanic — a reject with an absent/empty reason is `Rejected(missing_required_field)` before any commit (SUBMIT_DECISION's anchor rule); the reason is a transcript fact and LC archive is the literal "archived." `CANCEL` remains the out-of-band operator kill, not the in-template disposition. **`blocked → flagged-to-admin`**: the carrier is the **L3 human gate** — the Build/Review actor's declared `blocked` transition routes to a human_gate step whose `park_for_human_decision` commit mints the `DECISION_REQUEST` and projects the P5 **`HumanDecisionRequest`**; that projected ask *is* the "ask-admin RPC," with decisions `{unblock → resume, rescope → spec, archive}` (S8's mechanics wholesale, including round hygiene on the loop-back). S9's escalation-emit is the wrong carrier — a fire-and-forget alert would never resume the parked task — and the LC3a `ActionRequest` fits only if unblocking is an operator *action* rather than a judgment. The park is indefinite by declared design (the human-decision errand's failure shape is "no timeout (L9)"), so a blocker nobody answers is GAP-4/L9 §6 verbatim — and the spec's own open question #5 (ask-admin RPC vs. daily-review queue, 3216) is precisely L9 §6's escalation-policy choice, unwritten in both corpora.
- *(b) Tier-based auto-approve.* The same conditional-gate problem as S11's `[uat]`: the gate exists on some runs and not others, and the built corpus has no conditional step — the honest shape is an **upstream ChoicePoint routing by validated tier to gate-or-skip paths** (`tier4 → build`, `tier123 → spec_gate`, both edges through the shared arrival; the gate itself is S8's fully built human gate). Expressible today. The load-bearing question is **who committed the tier**: if the Spec agent's emit carries its own tier, the routing selection is principal-committed *by the agent whose work the gate exists to check* — the fox classifying the henhouse; a Spec agent that tags borderline work Tier-4 ships it with zero human touch, and the >90% zero-touch success metric (3221) actively rewards exactly that. The capture pins tier as a schema field (3120) and leaves the policy open (3213). v3 offers two honest mechanisms, both built. (1) **The tier as a separate principal-committed or kernel-classified decision**: a classification position whose selector is *not* the spec author — either a distinct principal's committed selection (the Triage agent already "scores," 3142, or the human at promotion), or an LC3b action step whose runner deterministically classifies the spec/diff into tier outcome keys — kernel-classified through the `outcomes` ChoicePoint, no self-interested selector at all. (2) **L2 gate verification of a claimed tier**: the tier-carrying emit passes an L2a process gate before the transition commits ("gate pipeline runs before commit" — the P2 transitions row); Tier-4's definition — "doc / refactor / housekeeping" (3213) — is substantially machine-checkable from touched-file classes, the same check family as the exception-file gate, so a claimed Tier-4 touching schema files blocks. The mechanics are built; the separation-of-duty *discipline* (the tier's committer must not be the gated actor) is template design — the kernel enforces it as authority bindings and records it as warrants, but no corpus rule states it.
- *(c) Six roles — bindings, one exception.* Roles are **actor bindings, not kernel constructs**: one task template whose steps bind Spec/Build/Review/Ship actors via the L0b binding map, plus Triage in its own sweep template. Review's independence is structural, not aspirational: the review step's transitions are principal-committed by `instance.binding[review_role]` and admitted through P3's authority rung — Build cannot commit Review's verdict; the warrant check rejects it. Whether Review is "peer Claude or a different model" (3214) is L0c run config — runtime territory; per-review context isolation, if wanted, is an L4 child spawn (S15's territory). **Watchdog is not a template role at all — it is the L9 supervision plane**: heartbeat alarms, max-turns/wall-clock/livelock stuck detection, and paging (3147, 3165) map point-for-point onto L9 §5's watchdog contract (workload-declared silence budgets, restart-first/work-durable recovery) — named in the planned corpus, unwritten (GAP-4). Budget tripwires (3164) are S7's runtime spend telemetry, out of kernel scope by that section's verdict.
- *(d) The rescope-handoff.* Decomposed against produce-not-perform. **The turn budget**: the kernel cannot count turns — the budget is *issued* as pinned run config (`run_overrides` snapshot / L0c `issued_agent_config`) and *enforced* by the runtime, and the overrun re-enters the kernel as a **classified outcome**: run Build as an LC3b auto action (P5 `ActionIntent` to the agent-harness runner) and `budget_exceeded` is a declared key on the `outcomes` ChoicePoint — kernel-classified, which is the honest authority (an actor-emitted transition would trust the overrunning agent to self-report cleanly). Whether the runtime actually *applied* the issued budget is L0c §3's issued-vs-applied attestation — GAP-8's exact territory: the transcript says max-N-turns was issued; nothing kernel-readable says it was enforced. **The redispatch is expressible today** as a declared outcome route: `budget_exceeded → rescope step` (an agent step consuming the rescope-handoff JSON riding the outcome payload, emitting a narrowed spec) `→ build` — a loop-back through the shared arrival, `advances_round` firing S8's round hygiene, the rescope JSON as the fresh round's handoff. **Chain state**: model the chain in-instance and the depth cap becomes instance-local round arithmetic over committed state — fine (the LC3b episode retry budget is the built bounded-retry precedent, though rescope is retry-*as-new-work* — transform then redispatch — so the declared-route form is the faithful one); cross-instance chain accounting is needed only if redispatch mints a *new* Task row, which lands on GAP-1 creation identity plus a GAP-10-shaped cross-instance counter — avoid it, the in-instance loop is both simpler and more faithful ("auto-redispatch" of the same task). The **$5/chain spend cap** is the harder half even in-instance: a route guard consulting accumulated spend needs kernel-readable cost facts, and those live in the operational-observability seam §§1–2 (durable cost facts, attribution, roll-ups) plus L4 future §1 (child cost roll-up) — topic map only, no contract. Today the runner meters chain spend itself (carried in the handoff JSON) and classifies `spend_cap_exceeded` as one more declared outcome — provider-enforced and coherent, but the cap's enforcement is invisible to the kernel whose routing it gates (GAP-8's family again).
- *(e) File-claim locks.* `claim_file`/`release_file` with 25-min auto-expire (3152) is **cross-instance mutual exclusion over external resources** — two *different* task instances racing on one path. Every nearby kernel construct refuses it: the `action_running` claim scopes one errand inside one instance; `ChildWorkflowLink` is per-parent; GAP-6/GAP-10's cross-instance state is consult-shaped (counters, suppression), not exclusion-shaped; and the auto-expire is a **lease** — vocabulary the primitives memo explicitly poisons ("`Lease` (implies TTL + renewal; the model has none)"): expiring claims are absent from v3 *by construction* (kernel claims never expire; their staleness is L9's problem). The boundary, argued honestly: at **task grain**, the kernel-native exclusion is GAP-1's creation identity — one live instance per Task row means no two instances ever work the same task; at **file grain the kernel is structurally blind** — de-vocabularized routing knows no paths, and which files a Build performance touches is discovered mid-performance, behind P5. So the locks are **provider territory by design**: the runtime's worktree manager owns the claim registry (worktree isolation, 3151, already absorbs most of the race; the locks guard the residual shared-path contention), the same family as S11's serialization mutex. The residue worth registering: mutual exclusion is the oldest coordination primitive there is, and if BitSafe ever wants the coordination kernel to own it, no construct exists and the lease shape is deliberately unbuilt — a boundary to ratify, not an accident (→ GAP-11, extended).
- *(f) CHANGELOG trailer consolidation.* "Orchestrator consolidates on main" post-merge (3155) is S9 (e)-shaped completion routing: a declared LC3b action step on the ship tail (P5 `ActionIntent` to a consolidation runner; outcomes `consolidated | infra_error`), the structured trailers riding as evidence. The *serial* discipline across concurrently-shipping tasks is the runner's own — a single consolidator principal serializes by construction, provider-side, kin to (e). Brief by design; the surrounding merge/ship mechanics are S11's.

**External tool boundary.** Behind P5: all LLM work (triage scoring and briefs, spec drafting, implementation, tests, review comments); git/GitHub — worktree create/claim, branches, PR open, CI runs, merges; the Notion reads/writes for all three queues (rows, checkboxes, statuses as projections of kernel facts); the dev-VM deploy, journalctl smoke watch, and prod promote (S11); the file-claim lock registry with its 25-min expiry; turn counting and per-chain spend metering plus the rescope JSON's contents; CHANGELOG consolidation on main; Slack/admin delivery of asks, ship logs, and pages; the §7 knowledge layer — SQLite caches, FTS5, Notion→disk skill sync (3170–3173 — S16's territory). The kernel coordinates: the per-task state machine (steps, gates, waits, terminal dispositions with reasons), the tier route and its verification, the blocked-park and its correlated decision, round-bounded rescope loops, sweep firing and exactly-once task minting, and per-step role authority.

**Verdict.**
- **SDLC spine (per-task template):** 🟡 — the body is largely built (agent steps, S8's human gate with rework/round mechanics, declared terminal reject routes with required reasons, the LC3b action tail); the CI/dev machine completions need **L8 §§1–3**, which as written cover connector normalization and exact correlation on PR identity; the ship tail defers to S11; blocked-park liveness is the named L9 deferral.
- **Queues (planners feeding the spine):** S9's verdict transfers verbatim — the Triage/Spec sweeps are 🟡 **L6 §§1–2** (covered as written); the promotion mint is 🔴 — exactly-once task creation keyed on RQ item identity plus mint-without-parking has no story in either corpus (GAP-1 + GAP-9).
- **Tier gate:** ✅ — gate-or-skip routing, the human gate, a non-self-interested tier classification (kernel-classified LC3b outcomes or a separate principal's committed decision), and L2a verification of a claimed tier are all built mechanics; the separation-of-duty rule itself (the tier's committer must not be the gated actor) is unstated template discipline, noted, not a missing mechanism.
- **Rescope:** 🟡 — the overrun-as-classified-outcome and the declared rescope loop with instance-local round-bounded depth are expressible today; the issued-budget attestation is 🔴 (GAP-8), and a kernel-readable spend-cap guard needs the observability seam §§1–2 + L4 §1, which exist as topic map only — provider-enforced today.
- **Locks:** ✅ as *not a kernel workload — provider territory by design* at file grain (kernel-native exclusion exists only at task grain, via creation identity); a kernel-side lock registry would be 🔴 — no construct, and lease/expiry semantics are deliberately absent.
- **Watchdog:** 🟡 **L9 §§5–6** — the planned sections name precisely the needed contract (silence budgets, restart-first recovery, unanswered-human-wait escalation) and none of it is written (GAP-4); the spec schedules as MVP Week-3 work (3195) what v3 holds only as a topic map.

**Gaps.**
- **GAP-1 recurs (the factory's front door):** a redelivered "approved" promotion or a re-run Triage sweep mints twin task instances for one RQ item — S9's 26-findings failure shape transplanted to the SDLC spine; row-keyed creation identity is also the kernel's only native duplicate-work exclusion at task grain.
- **GAP-9 recurs:** Triage and Spec are planners that must mint task instances and exit; `SpawnIntent` exists only inside `park_for_child`, so the factory's entire feed runs on convention-grade ingress minting with no routable provenance link.
- **GAP-4 recurs, twice:** the Watchdog role *is* the unwritten L9 §5 contract — max-turns/wall-clock/livelock/heartbeat detection (3147, 3165) maps point-for-point onto silence-budget/restart-first text that exists only as topic map; and every blocked task parked on the ask-admin gate carries the human-decision errand's declared "no timeout (L9)" — the spec's own open question #5 (3216) is L9 §6's unwritten escalation policy.
- **GAP-8 recurs:** the turn budget is issued as pinned run config and enforced by the runtime, with `budget_exceeded` returning as a classified outcome — but nothing attests the budget was applied; a runtime that ignores the cap ships a 200-turn run whose transcript says max-40 was issued, and the $5/chain cap's provider-side enforcement is likewise invisible to the routing it gates.
- **GAP-11 recurs, extended to data grain:** `claim_file`/`release_file` with 25-min auto-expire (3152) is acquire/block/release/expire coordination *between* instances over world resources; the lease/TTL shape is deliberately poisoned vocabulary in the primitives memo, so expiring claims are absent by construction. To ratify alongside S11's resource-grain mutex: is file-grain exclusion below the kernel's line by design (de-vocabularized routing knows no paths), with the kernel's contribution capped at task-grain creation identity?

### S13. Propose–Approve–Apply Change Control

**Facts (capture).** The governance meta-loop that makes the fleet's scale argument work. **Registry:** "Every agent is a row in one database" — each row documents the owner, purpose, category, agent type, a status progressing In development → Active → Retired, the agent's scope, triggers, tool access, a link to its instructions documentation, and a connection to its change history (811); the law is "if an agent is not in the registry, it does not run", against the shadow-agent failure mode (813); the registry keeps the fleet questions cheap — "Which agents are running right now? … Who approves a change to one of them?" (803). **Change control:** "No agent can edit its own instructions" (837); three stages — Propose: changes documented in a dedicated database with the proposed wording, source of the suggestion, and current status (841); Approve: "the proposal goes to the agent's human owner listed in the registry" — the owner, not a centralized administrator (843); Apply: "a dedicated tuning agent applies the change, which is its sole function" (845); the output is "always a written record of what changed, who asked for it, and who approved it" (847). **Governing agents:** the tuning agent "never decides what should change and never approves anything"; a separate read-only oversight agent "cannot edit any agent, and its job is to watch" — it "posts a weekly digest of every change across the fleet and raises an alert whenever a change is actually applied"; the audit trail exists "as a database, queryable like everything else in the workspace" (851–853). The maxim: "The agent that can act cannot approve, and the agent that watches cannot act" (855). The payoff: the 61st agent "inherits the same propose, approve, apply loop" at low marginal cost (865).

**v3 decomposition.**

- *(a) The change-control loop as a workflow.* One `WorkflowInstance` per proposed change, and the template is S8's three-step shape with the draft replaced by a proposal: **propose** (the task payload carries `{target_agent_ref, proposed_wording, source}` — the "dedicated database" row of 841 becomes the instance + transcript, its `status` field a projection of kernel state exactly as S9 dissolved `Findings ready`) → **approve** (L3 human_gate — S8's built machinery transfers wholesale and is not re-derived; decisions map, modeling choice: `{approve → apply, reject → terminal, request_revision → propose (required non-empty instruction)}`) → **apply** (LC3b auto action, below) → terminal. Ingress is GAP-1 verbatim: a proposal filed twice (redelivered event, retried filing agent) mints twin change instances and the owner gets two approve asks for one change. **The owner-from-registry binding:** the built corpus supports this *natively but existence-grade only*. Binding is per-instance and resolved pre-kernel (`RESOLVE_START`: `project_binding` is "its OWN cascade, not a slot"; `CREATE_INSTANCE`: "binding resolved pre-kernel; the kernel only validates coverage"), so the ingress connector reads the target agent's registry row behind P5 and binds `owner_approver → that human` at CREATE — data-dependent per-change binding needs zero new mechanism. But the coverage rule validates *presence* (every reachable role bound), never *provenance*: the capture's requirement is correctness-grade — the approver must be THE owner listed in the registry (843) — and the kernel cannot see that the bound principal matches the registry; the transcript records who held the gate, not that the lookup was right. Second consequence: the binding snapshots at CREATE, so an ownership handoff while the proposal parks leaves the *old* owner holding the gate, with no rebind construct (compounding GAP-4 when the old owner is gone). **Against L12:** the planned corpus does own this loop, as written — §3: "Promotion should produce a proposal, not mutate the definition directly"; the proposal travels through the definition-PR channel with author, rationale, source evidence, and affected scope; acceptance runs the relevant gates/evals before the definition becomes active; and the state ladder (remembered / candidate lesson / proposed definition change / accepted definition) subsumes 841's status field. §4: "Record the reviewer decision and evidence separately from the author's proposal" — which the built corpus already delivers structurally (`DECISION_MADE` is a separate committed entry from the proposal payload) — and for agent/org definitions, independent review should be the default. §8 goes *further than BitSafe*: "Lifecycle operations on definitions must be deterministic host operations, not LLM-run prose" — the tuning agent's sole function (845) is exactly what §8 says should not be an LLM at all, so in v3 the apply step is a P5 `ActionIntent` to a deterministic apply runner (`ACTION_RESULT` classified `applied | apply_failed | infra_error` through the outcomes ChoicePoint) and the tuning *agent* dissolves into a *runner*; §8's boot-time tripwire (refuses to run on an out-of-band change until the sanctioned flow stamps it) is 837's no-self-edit rule made structural rather than policed. Coverage judgment: L12 as written names every element of the loop — proposal artifact, independent review gate, deterministic apply, anti-self-edit tripwire — but is topic map only: no proposal schema, no definition-store write contract, no owner-routing note (the last needs nothing beyond built binding).
- *(b) Separation of powers as BINDING/AUTHORITY facts.* Per input path, the separation is **built and structural**: the approve gate's `SUBMIT_DECISION` admits only `by = instance.binding[step.role]` (both missing and mismatch branches declared `operator_not_authorized`) — the applier *cannot* approve because its completions enter as `ACTION_RESULT` correlated to its claim, and the outcomes ChoicePoint is kernel-classified ("no accountable selector") — the applier classifies results, it never selects with authority; a proposing actor's emit can only turn declared transition keys. "The agent that can act cannot approve" holds rung-for-rung. **What is not enforced anywhere: that the three roles are three principals.** Nothing validates `binding[proposer] ≠ binding[approver] ≠ binding[applier]`, and CREATE's validator family — binding coverage, `validate_gate_config`, `validate_context_refs`, `validate_decision_gates` — is precisely where a binding-disjointness `REQUIRE` would live and is absent: one principal bound to both approver and applier passes coverage silently and ships self-approved changes over a formally clean transcript. Worse for 837 specifically: the *target* agent's identity rides in the opaque task payload the de-vocabularized kernel cannot read, so "no agent can edit its own instructions" cannot even be *stated* as a kernel invariant without lifting the target ref into a kernel-visible field. A discipline-grade fallback is expressible today — an L2a process gate on the approve→apply transition whose runner checks disjointness and non-self-targeting provider-side — but that is template-author vigilance, exactly what the capture's structure-over-vigilance ethos (855, 865) exists to replace. Judged a gap, not discipline → GAP-14.
- *(c) The registry.* Split it, because v3 answers the two halves oppositely. **Template registry — structural, built:** "if it is not in the registry, it does not run" is v3's law for *definitions* verbatim — `RESOLVE_START` rejects `workflow_definition_unavailable` when `select_source` cannot load the pinned template, and CREATE loads only pinned definitions; a template outside the store cannot run, by construction, and L0c's `issued_agent_config` pins what config was issued per dispatch. **Agent registry — absent:** binding principals are opaque ids resolved pre-kernel; nothing checks that a principal exists, is Active rather than Retired, or matches its declared scope/tools — a Retired agent's principal left in a binding passes coverage and keeps receiving `DispatchIntent`s, which is 813's shadow-agent failure mode reproduced inside v3. The planned corpus holds fragments: the identity seam names a durable actor record in one bullet; L13 §4's BAD_BINARY-style quarantine (a durable blocklist for agent definition versions that should stop receiving work) is the Retired-blocks-work shape but per-*version* and framed as failure response, not lifecycle status. No fleet-level actor registry — owner, status, scope as kernel-consultable facts — exists in either corpus, and S13 is the workflow that makes it load-bearing: the approver *lookup* (a) and the status gate both read it → GAP-15. Part of an agent's row does dissolve into existing v3 homes: instructions link = the definition store (e), triggers = L6 series, tools = L0c/L7 issued capability — the row is partly a join over things v3 already owns, which sharpens rather than softens the finding: the missing piece is the *actor-principal* store and its status gating, not the metadata.
- *(d) The oversight agent.* **Weekly digest:** an S6-shaped L6 §§1–2 scheduled sweep — one instance per week, one batch action step behind P5 — and its data source is v3's home ground: 853's "audit trail … as a database, queryable" is *native*, because the change-control transcripts ARE the change history, committed queryable state (what changed = proposal payload, who asked = source + creating principal, who approved = `DECISION_MADE.by` — 847 field-for-field). GAP-1 at the fire→create seam; GAP-2's weight floor trivially. **Read-only-ness:** kernel-side, near-structural — an actor's entire kernel surface is emitting declared keys on its own bound steps; there is no cross-instance write path through an emit, so the oversight actor bound only to a read-and-post template *cannot* edit any agent through the kernel. Provider-side, its read-only toolset is L0c issued config + planned L7 grants — and proving the runtime honored it is L0c §3's issued-vs-applied attestation, named without a contract (GAP-8's family). **Alert-on-apply:** the event-driven half, and the honest answer is two shapes. In-template (expressible today, S9's `cap_exhausted` precedent): the apply step's `applied` outcome routes through a step that emits the alert directive — but then the *watched* template announces itself, and an author who omits the emit silences oversight, inverting 855. Independent subscription: the only built cross-instance subscription is L4's `wait_for` (per-parent, per-child); the **observe seam §1** names the needed primitive as written — a `history_plus_stream()`-style primitive that atomically snapshots history plus live tail with durable replay offsets — but frames it per-run ("an observer should be able to join *a run*"); a fleet-wide event-class subscription ("every apply commit across all change instances") is written nowhere, and L8's task inbox is delivery, not subscription. The saving structure is S5(b)'s convergence argument: the weekly digest re-scans committed state, so a missed alert is latency, not lost audit — noted as a boundary finding, not registered.
- *(e) Instructions as mutable external definition — GAP-7's fate.* Forked by where the instructions live. **Kernel-resident (the v3-native shape): GAP-7 dissolves architecturally.** If the agent's instructions are a pinned definition in the store, apply is a deterministic host operation landing version N+1; every run's transcript pins `template_ref` = which version ran; the change history (811) is the version sequence joined to change-instance transcripts — the exact provenance BitSafe maintains by convention falls out of the pin discipline. Residual: the definition store's *write path* (how apply lands a new version, the versioning contract) is unwritten — `select_source` is "MVP: local; central store is L11+" — so the dissolution is architectural, not contractual; specifying that write path is precisely L12's definition-PR channel, named not written. **External-resident (BitSafe's actual shape): GAP-7 recurs verbatim.** The registry row links instructions documentation in Notion (811) — S5's finding transfers: behavior identity escapes the pin (the actor fetches the page at run time; the transcript cannot say which instruction text ran), and the no-self-edit invariant between kernel commits is only as strong as the Notion ACL, outside the kernel's audit horizon. The apply runner's page-write effect idempotency is provider-side.

**Gaps.**
- **GAP-1 recurs:** a redelivered "review this contract" utterance on the bare ingress path mints twin review instances — two full two-round reviews and two redlines for one contract; L8 §1's correlation store covers the channel path as written.

### S16. Skill Reconciler

**Facts (capture).** `/etc/cron.d/skills-sync` fires `scripts/sync-skills-from-notion.py` every hour at :00 (1408). One pass does two jobs. **Mirror:** the script reads the Notion Skills DB and writes each row to disk at three paths — `/root/nanoclaw-skills/<name>/SKILL.md`, `container/skills/<name>/SKILL.md`, `marketing-ai-system/design_system/skills/<name>/SKILL.md` (1408); the Skills DB holds 74 skills as Notion pages syncing hourly to `/workspace/skills/<name>/SKILL.md`, the on-disk cache is read-only, and "edits in Notion propagate globally to future agent invocations without requiring deployment" (1228) — "skills as config": updating a skill means editing a Notion page, no deployment or code change (1035). **Reconcile:** the script parses each SKILL.md's frontmatter for a `scheduled_tasks:` block; "any tasks declared in frontmatter that are not yet present in `store/messages.db` get inserted; tasks that have been removed from frontmatter get marked inactive" (1408). The payoff, verbatim: "the reconciler is the reason a new skill ships with its scheduled cron declaratively in one place — author the SKILL.md row in Notion, and within the hour the on-disk copies update and the schedule is live" (1408). Like the other standing loops it is a short-lived tick that acts and exits — it never waits (1412). And the drift it exists to close is a documented paid lesson: `feedback_skill-built-but-not-scheduled.md` — "shipping skill code isn't enough — the `scheduled_tasks` row is a separate insert" (1722).

**v3 decomposition.** Split where the capture's own sentence splits — the run, the mirror, and the reconciliation — because they land on three different verdicts.

- *(a) The run.* S6-shaped, and S6's decomposition transfers wholesale (cite, not re-derived): one hourly **L6 §§1–2 timer series** whose CAS-claimed fire mints a short-lived instance carrying a single LC3b batch action — P1 errand (`action_running` claim + episode) → P5 `ActionIntent` to the reconciler runner → `ACTION_RESULT` classified through the P2 outcomes ChoicePoint (`reconciled | nothing_changed | infra_error`, the infra route re-parking under the episode retry budget) → COMPLETE → LC teardown; P3 Admission + P4 Warrant on every entry. The fire→create seam is GAP-1 verbatim; ~24 mostly-no-op tick instances/day price GAP-2's unwritten weight floor. Nothing new on this half.
- *(b) The interesting half — declarative `scheduled_tasks:` driving durable schedule state.* The frontmatter block is desired-state config: the set of live timer series must be a **projection of the declared config** — insert what is declared and missing, deactivate what is present and no longer declared. Walk the corpus for an owner. **L6 as written owns individual row mechanics only:** durable rows carrying `process_after` + recurrence, status bits (*not fired / claimed / completed / obsolete*, §1), CAS-claimed exactly-once firing with reload-and-discard-if-stale (§2), the adopted `series_id` recurring-identity model, and the §3 dispatch governor. No sentence states that the series *set* is derived from anything — no desired-state reconciliation contract, and in fact **no written ingress provisions or retires a series at all**: every prior simulation (S5's four check series, S8's monthly cron, S9's dual-cadence pair) presumed its L6 series existed; S16 is the workflow that *creates* them, and the corpus has no series-creation story to hand it. The deactivate half at least has vocabulary — the *obsolete* status bit — but, exactly as S4 found at occurrence grain, it is vocabulary awaiting a writer. **Where does v3 declare a workflow's own trigger?** Nowhere in its definition: an L0f definition is template + slots + targets + binding (`RESOLVE_START`/`slot_scope` — no trigger field); L5 §1's package shape (frontmatter Markdown + machine-readable metadata — literally the SKILL.md shape) names metadata for "indexing, validation, and UI" but no schedule; so a template's schedule is external scheduler state, full stop. Both are topic map; no seam between the definition store and the L6 series store is written anywhere. One structural point sharpens the verdict: this half cannot be waved off as provider territory, because L6 §3 places scheduling bookkeeping in *scheduler-owned* state — the moment v3 owns timers, the reconciliation's write target sits on v3's side of the P5 boundary, and the contract must be written there.
- *(c) The mirror — GAP-7's workaround made into a workflow.* S5(c) named it prospectively: a methodology living in a mutable Notion page "needs an unspecified snapshot/sync step to become resolvable — BitSafe's own S16 Skill Reconciler (Notion → disk sync) is precisely the workaround." Its fate follows S13's split exactly (cite, not re-derived). **Kernel-resident residence dissolves the mirror entirely:** skills as pinned definitions in the store (`select_source` — "MVP: local(.pairflow/); central store is L11+"), each run resolving and pinning that hour's version at `RESOLVE_START`, editing routed through L12 §3's proposal channel with a deterministic apply (§8: lifecycle operations on definitions are host operations, not LLM prose). The three-path disk fan-out becomes one store; 1228's "read-only cache, edits propagate to future invocations without deployment" is the pin-per-run discipline delivered natively, plus what BitSafe lacks — a transcript recording *which* skill version each run executed; the caching concern itself has a named home in L5 §2's deterministically-refreshed, audited prompt index. While skills stay Notion-resident, GAP-7 recurs verbatim (behavior identity escapes the pin between hourly syncs; a redelivered fire may resolve a different definition than the first attempt).
- *(d) Idempotency of the reconciliation.* Insert-if-missing / deactivate-if-removed is level-triggered against current declaration + current store, so a crash mid-reconcile leaving half-applied desired state converges on the next hourly run — *provided every operation is keyed on stable series identity*, and that key is exactly where the writing runs out. The identity must derive deterministically from the declaration — `(skill, task name)` → `series_id` (the adopted recurring-identity model gives the row shape, not the derivation rule; note a rename becomes deactivate+insert, silently severing the series' fire history). The insert itself is then **GAP-1's family at series grain**: "not yet present … get inserted" (1408) is check-then-insert over the store, the 26-findings shape one level up — two overlapping reconciler runs (hour N stalls, hour N+1 fires) double-insert unless series identity is store-enforced UNIQUE with mint-or-return-existing (the L8 §1 "auto-create over hijack" oracle shape). And to answer the question directly: **L6 §1's dedup-by-status-bits does not cover series-grain convergence as written** — it dedupes "equivalent pending wake-ups" with status bits so *recovery* can classify occurrence rows (not-fired/claimed/completed/obsolete); it is occurrence-grain bookkeeping inside timer state, and says nothing about the series set converging against a declared identity. The deactivate half has the mirrored race: marking a series inactive while one of its fires is mid-CAS-claim is GAP-5's fire-claim-vs-concurrent-obsolete arbitration, recurring at series grain.

**External tool boundary.** In BitSafe's shape, everything is behind (or below) the kernel: the Notion Skills DB read, the frontmatter parse, the three disk writes, and the `store/messages.db` upserts are all one script under host cron. In the v3 reading, behind P5 remain: the Notion read (or, natively, Notion as authoring surface feeding L12's proposal channel), the deterministic frontmatter parse, and any residual content caching (L5 §2's index refresh). Deliberately *not* behind P5: the L6 series store writes — scheduler-owned coordination state (L6 §3) — and the definition-store write path (L12's channel). The kernel coordinates: the hourly fire, one batch errand, and — in the native shape — the series-set reconciliation itself, which is the half with no written contract to coordinate under.

### S17. Liveness Family

**Facts (capture).** Four mechanisms, all born from or hardened by the 2026-05-13 incident (1470: three OOM kills in 44 minutes — a python3 accumulator ate 19 GB, the 32 GB host had zero swap, the third kill rebooted the box). **(1) Dead-man's switch:** a cron drop-in at `/etc/cron.d/dead-mans-heartbeat` fires every minute and POSTs to a BetterStack heartbeat endpoint; the monitor has a 5-minute period plus a 10-minute grace window, so the 1-minute cadence tolerates five consecutive misses; "the reason the monitor itself lives off-host (BetterStack, not an on-host cron) is that every on-host monitor would die simultaneously in a kernel panic or networking failure. If NanoClaw goes silent for >15 minutes, a separate piece of infrastructure pages the team. RECOVERED on resume" (1410); listed under security alarms as "if NanoClaw stops checking in, BetterStack pages Aki out-of-band" (1701); wired during the incident's four-hour recovery (1478). **(2) Failure circuit breakers, two grains:** "Scheduled-task failures: three consecutive runs trip a circuit breaker and ping admin with the failure category" (1703); and "Container retry-budget exhausted when one thread fails three same-category times in 30 minutes" (1709). **(3) Stuck-agent / silent-drop detection:** the "Autoflow silent-drop detector when a triggering @-mention never gets a cursor written — the class we hit and fixed on 2026-05-14" (1709); the underlying cursor-bootstrap gap: "a thread's first @-mention queued past `MAX_CONCURRENT_INTERACTIVE=3` would never get processed because the cursor never got written; 16 stuck production threads on the day of the fix" (1480). **(4) OOM-backoff sentinel:** "at `/tmp/host-session-last-oom`: if a tick exits with rc=137, the next tick within 1800s skips the claude call and pings admin instead of thundering-retrying" (1477). The family's stated philosophy: "the failure mode of an autonomous system is a stuck process — a daemon that thinks it is doing something but is not. Short-lived ticks with state files are easier to reason about than long-running daemons" (1412). Adjacent kin, noted for the family portrait only: the push watchdog (unpushed commits >6h fire an admin ping, 1702).

**v3 decomposition.** Mechanism by mechanism, then the synthesis this section exists to deliver.

- *(1) Dead-man's switch — mostly not kernel territory, and saying precisely why is the finding.* The kernel is storage plus commits; it never executes, so "NanoClaw went silent" is a claim about the *runtime plane* — schedulers, runners, the watchdog itself — and produce-not-perform puts fleet self-supervision on the performer's side by construction. Minting kernel instances for the heartbeat would be GAP-2's reductio ad absurdum (1,440 one-step instances/day of pure ceremony); the heartbeat emitter is runtime machinery below the kernel's floor. What the kernel *does* contribute, natively and today: durable committed state makes "silent" **queryable evidence** — last-commit timestamps per instance, ages of open `action_running` markers, parked-wait durations — the staleness facts BitSafe's monitors reconstruct from state files are v3 transcript queries (S6's dashboard already consumes this shape). And "RECOVERED on resume" (1410) is structural, not aspirational: commit-based durability means a >15-minute total outage loses no coordination state — every instance reloads from its committed position, which is L9 §5's "global stop … preserving durable state" delivered by the storage model itself. But the *paging* cannot be: queryable evidence dies with the host that would query it — BitSafe's off-host argument (1410) transfers to v3 unchanged and **bounds the L9 contract from outside**: L9 §5's watchdog is on-host runtime machinery, so the contract must require the watchdog to *push* externally observable liveness evidence (a heartbeat) to a monitor outside the failure domain, and the pager stays external by the same argument BitSafe gives. Who watches the watcher is answered the same way at every level of the tower — one level out — and the outermost level is not v3's to own. L9 §5 as written says nothing about the watchdog's own observability; that becomes requirement R8 below.
- *(2) The failure circuit breakers — one grain built, one grain homeless.* **Per-thread retry budget (1709):** if the thread's retries live inside one instance, this is the **built LC3b episode retry budget** verbatim — `ACTION_RESULT` retries only outcomes that *declare* a retry policy, `attempt_count_in_episode` bounds it, and "same-category" is native: the category IS the classified outcome key on the kernel-classified P2 outcomes ChoicePoint, so "three same-category failures" is three same-key `ACTION_RESULT`s in one episode, and `retry.on_exhausted` routes to a step whose route `emits:` the admin alert with the category riding as payload — S9's `cap_exhausted` pattern. One honest delta: the built budget counts *attempts*, not a 30-minute *window* — the time dimension of 1709 has no field in the episode contract (a slow-burn flake that fails three times over three hours trips v3's counter but not BitSafe's window). **Per-series breaker (1703) — cross-run, and this is the hard one:** "three consecutive runs" spans three *instances* of one L6 `series_id`, and "trip" must stop the *series* from firing — durable failure history consulted at fire time, which is GAP-6/GAP-10's exact shape (cross-run state consulted before firing; scheduler-owned counters with no written contract). Who owns "this series is sick, stop firing it"? Walk the candidates: the LC3b episode budget is per-errand-within-one-instance — refuses; **L6 §3 names the consumption point as written** — "capacity informed by system health and **circuit breakers**" — so the governor consulting breaker state before dispatch is planned text, but §3 writes nothing about where breaker state lives, how it accumulates per series, what trips or resets it; **L9 §5's "startup circuit breaker" is a different animal** — the runtime respawn-thrash guard paired with the typed self-exit, not a per-series scheduled-work breaker; and nothing else in either corpus mentions it. So the answer to "is that written anywhere?" is **no** — L6 §3 holds the enforcement seam, L9 holds the diagnosis mandate, and the breaker's state contract (accumulate classified-outcome keys per `series_id` across runs, consecutive-N trip, category-carrying escalation, reset/half-open authority) falls between them. What v3 has that BitSafe lacks: the failure *evidence* is already native — classified `ACTION_RESULT` outcomes on instances carrying series provenance are committed, queryable facts, where BitSafe must maintain a category counter in a state file; v3 has the ledger and no contract that reads it. → requirement R5.
- *(3) Stuck-agent / silent-drop — the flagship question.* Anatomy of the incident first: a triggering @-mention **arrived**; the capacity gate (`MAX_CONCURRENT_INTERACTIVE=3`) deferred it; the cursor — the durable "we owe this thread work" marker — was written only by the *processing* path, never the *queuing* path; so the deferred arrival left no durable claim, the system's own bookkeeping said "nothing owed," and no later tick ever picked it up — 16 threads, silently, in production (1480). The root pattern: **arrival and claim were separate acts, and the claim rode the wrong side of the capacity gate.** Map onto v3: under **GAP-1's creation identity as L8 §1 writes it** — the store-enforced exact correlation oracle, "auto-create over hijack" — the arrival IS the claim: the correlation lookup either finds the instance or mints it in the same committed move, so "arrived but no cursor" is structurally inexpressible; and capacity is **L6 §3's dispatch governor**, which throttles the dispatch of already-committed work and can never gate the *recording* of arrival — the ordering BitSafe got wrong is fixed in v3's architecture, not in its vigilance. The 16 threads would each have been a created instance parked awaiting dispatch: visible, aged, queryable. The *detector* (1709's escalation alert) has an equally exact planned home: **L8 §4b's inbound non-delivery ledger** — "a message arrived and was *not* processed is an auditable fact, not silence," structural drops recorded with reason codes — covers the audit mirror as written. The residual L9 duty is the reconciliation sweep: cross-check arrival evidence (channel log / §4b ledger) against the correlation store and alert on any triggering arrival with neither an instance nor a recorded drop — belt-and-braces for paths that bypass the oracle (→ R6). **The flagship judgment, S9-style:** v3 *with L8 §1* would have **prevented** the 16-stuck-threads incident by construction — but L8 §1 is topic map, and **v3-as-built would reproduce it**: on the bare ingress path the harness is the cursor-writer, and a harness that defers creation past a capacity check re-creates BitSafe's failure verbatim. This makes the incident **GAP-1's second documented real-world casualty, and its dual**: S9's 26 duplicates are the too-many-instances face, the 16 stuck threads are the zero-instances face — mint-or-return-existing kills both ends of the same hole, which is the strongest possible evidence that creation identity is one mechanism, not two patches.
- *(4) OOM-backoff sentinel — GAP-6's shape wearing L9 §5's semantics.* Decompose the sentinel: a **death signal** (rc=137, reported by the supervisor because the performer cannot report its own death), a **durable suppression marker** (`/tmp/host-session-last-oom`), and a **consult-before-fire rule** (next tick within 1800s skips the claude call and pings admin). The consult-before-fire half is GAP-6 verbatim — durable cross-run state consulted before firing, living today in a provider-side file the kernel cannot read — landing at L6 §3's health-informed capacity seam (capacity = 0 for this work class while the breaker is open). The semantics half is covered by **L9 §5's nanoclaw bullets as written, and strikingly precisely**: "recovery must consume its own evidence" (the sentinel is exactly evidence-consuming backoff — the marker is read and honored by the next tick, and expires rather than re-triggering forever; note the 1800s window is TTL-shaped state that must stay *runtime-side*, since `Lease` is deliberately poisoned kernel vocabulary — kernel claims never expire, their staleness is L9's problem); "executor self-exit on unhealable local fault" (rc=137 is the *involuntary* sibling of the typed "I am poisoned" exit); and the startup circuit breaker is the sentinel's exact job description in the field. Two kernel touchpoints remain. First, the death itself: if the host-session tick runs as an LC3b auto action, an OOM kill means the `ACTION_RESULT` **never arrives** — a durable `action_running` marker with a dead performer, which is GAP-4's named deferral verbatim (RUN_ACTION: "a crash here leaves a durable `action_running` the L9 watchdog reconciles"); the watchdog must be able to consume the supervisor's rc=137 as proof-of-death evidence and route the declared failure path (→ R2). Second, the suppressed fire must be a *recorded fact*: "a fire was claimed and deliberately not dispatched (breaker open)" deserves a first-class scheduler-ledger entry — the outbound kin of L8 §4b's inbound mirror — or the skip is exactly the silence the family exists to abolish (→ R4).

**The GAP-4 synthesis — what the L9 contract must minimally own.** Eight prior sections each threw an instance onto the same unwritten contract: S3 (a crash between action claim and result leaves durable `action_running`; undeclared outcomes park "recovered at L9"), S8 (the reviewer never submits — the human-decision errand's declared "no timeout (L9)"), S9 (worker dies between findings-write and status flip — marker drift against world state), S10 (two unanswered gates plus a design child that never completes — the child await's "L9 reconciliation edge"), S11 (the watcher daemon dies mid-smoke and `RESUME_WAIT` is the wait's only exit), S12 (the Watchdog *role* — heartbeats, max-turns/wall-clock/livelock, paging — and the blocked-park's unanswered ask-admin), S13 (the owner never answers; softened only by a workload-level weekly sweep), S14 (the helper never replies and `help_pending` parks forever). S17 adds the four mechanisms above. Synthesized into concrete requirements — each derived from a real incident or a real parked-forever shape, together the deliverable that feeds GAP-4's disposition:

- **R1 — Deadline-bearing waits.** Every wait class (`human_decision`, bare wait, `child_event`, `help_pending`, `action_pending`) must accept a declared deadline/escalation policy *in the wait itself* (L9 §2's WaitCondition), materialized as an L6 timer row and obsoleted when a real resume wins; expiry routes to a declared disposition (`deny`/`expired`/`escalated` per L3-future §2; promote-to-another-approver/ops-inbox per L9 §6) — park-forever must become impossible to declare accidentally. [S8, S10 ×3, S11, S12, S13, S14]
- **R2 — In-flight marker reconciliation with proof-of-death.** The watchdog owns every durable `action_running`/`spawning` marker: on silence beyond budget or a supervisor-reported death signal (rc=137), commit a kernel-readable death fact and route the step's declared retry/failure path — never leave marked-forever, and never kill on suspicion (merely-slow routes to the judgment tier, L9 §5). [S3, S9, S17-OOM]
- **R3 — Workload-declared silence budgets on a cheap channel.** Tolerance = `max(floor, declared_timeout)`; the performer publishes what it is doing and how long silence is legitimate, via heartbeat mtime off the contended data plane (L9 §5's nanoclaw bullet, generalized past Bash). [S12's max-turns/wall-clock/livelock detection]
- **R4 — Recovery consumes its own evidence, and suppression is a recorded fact.** A recovery action must consume the stale marker that triggered it (one-tick grace) or the next pass kills the fresh replacement (L9 §5); repeated same-class deaths within a declared window open a post-crash backoff that suppresses redispatch and alerts instead of thundering-retrying — the suppression state durable and kernel-readable (GAP-6's missing home), and every suppressed fire logged as a first-class entry, mirroring L8 §4b. [S17-OOM, 1477]
- **R5 — Cross-run per-series failure breaker.** N same-category classified failures across consecutive runs of one `series_id` trip a breaker the L6 §3 governor consults before firing; the contract must write the state home (scheduler-owned, per L6 §3), the category dimension (= classified outcome keys), trip/reset/half-open authority, and the category-carrying escalation — jointly an L6 §3/L9 seam that today belongs to neither. [S17, 1703/1709; GAP-6/GAP-10]
- **R6 — Arrival-without-claim sweep.** Periodically reconcile ingress arrival evidence (channel logs, the L8 §4b inbound ledger) against the correlation store; any triggering arrival with neither an instance nor a recorded non-delivery entry is an alert. Prevention is L8 §1's creation identity; the sweep is the audit backstop for paths that bypass it. [S17, the 16 stuck threads, 1480]
- **R7 — Stale-intent disposition for late completions.** Late resumes/results after expiry or supersede are evaluated against expected version, state fingerprint, and allowed intent window, recorded as related evidence with a configurable response (ignore/attach/confirm/reopen/escalate) — never silently applied, never silently dropped (L9 §4 as written). [S11's late `smoke_clean`, S9's late findings]
- **R8 — The watchdog is itself watchable, off-host.** The supervision plane must push externally observable liveness evidence (a heartbeat) to a monitor outside the host's failure domain, because every on-host monitor dies simultaneously (1410); the pager is external *by design*, the kernel's contribution capped at durable, queryable silence evidence (last-commit timestamps, marker ages) plus a global estop that preserves committed state. [S17-dead-man, S11's dead watcher]

**External tool boundary.** Behind (or entirely outside) P5: BetterStack's off-host heartbeat monitor and paging — external by the model's own R8 argument, not merely by convenience; the host cron emitting the minute-cadence POST; the systemd-run memory scopes, swap provisioning, and the supervisor that observes rc=137 (1474–1477); `ping-aki.sh` and the Slack/DM alert surfaces with their per-source cooldown files (GAP-6, provider-side today); the failure-category classification logic inside runners (feeding kernel-classified outcome keys); and the watchdog *process* itself — the kernel stores its evidence and the L9 contract governs its duties, but the thing that walks markers and kills runtimes is a runtime-plane performer.

**Verdict.**
- **Dead-man's switch:** ✅ as *not a kernel workload — runtime self-supervision with an off-host pager, external by design*; the kernel's native contribution (committed state as queryable silence evidence; nothing-lost recovery on resume) is **built**, and the one contract residue — the watchdog must export its own liveness — is unwritten in L9 §5 (→ R8, feeds GAP-4).
- **Circuit breakers:** split — the per-thread same-category retry budget is ✅ **built** (LC3b episode budget + kernel-classified outcome keys + `on_exhausted` escalation route), minus the 30-minute window dimension the episode contract lacks; the per-series cross-run breaker is 🔴 — **L6 §3** names only the governor's *consultation* of breakers and **L9 §5**'s breaker is the startup-thrash guard, a different mechanism; the breaker's state/trip/reset contract is written nowhere in either corpus (GAP-6/GAP-10 family, → R5).
- **Silent-drop detection:** 🟡 **L8 §1 + §4b** — creation identity ("auto-create over hijack") prevents the class and the inbound non-delivery ledger names the audit, and both **cover the need as written** — but both are topic map only, and the flagship judgment cuts both ways: v3-with-L8 §1 would have prevented the 16-stuck-threads incident by construction; v3-as-built reproduces it on the bare ingress path. The reconciliation sweep is the unwritten L9 duty (→ R6).
- **OOM-backoff sentinel:** 🟡 **L9 §5** — the nanoclaw bullets (evidence-consuming recovery, typed self-exit, startup circuit breaker) cover the sentinel's semantics as written, with the suppression state itself GAP-6-shaped and the dead-performer's unreturned `ACTION_RESULT` landing on GAP-4's named `action_running` deferral (→ R2, R4).

**Gaps.**
- **GAP-4 — this section is its disposition-feeder, not another recurrence entry:** the R1–R8 list above concretizes the unwritten L9 contract from nine sections' accumulated instances (S3, S8, S9, S10, S11, S12, S13, S14, S17); the proposed disposition is "write L9 §§2/4/5/6 as contracts satisfying R1–R8," with R5's breaker-state seam settled jointly with L6 §3 and R8's off-host boundary stated as a design limit, not a deferral.
- **GAP-1 recurs — second documented real-world casualty, and the dual of the first:** the autoflow cursor-bootstrap gap (1480, 16 stuck production threads) is the zero-instances face of the same hole whose too-many-instances face was S9's 26 duplicate findings pages — a triggering arrival that mints no durable claim on the bare ingress path; L8 §1's mint-or-return-existing oracle kills both failure modes with one mechanism.
- **GAP-6 recurs, twice:** the OOM sentinel's 1800s suppression window and the per-series breaker's failure history are both durable cross-run state consulted before firing with no kernel home — provider-side files today, load-bearing the day L6 owns firing.
- **GAP-10 recurs:** the per-series breaker's counter is scheduler-owned windowed state across ~1,440 tick fires/day, kin to the ARQ daily quota — L6 §3 names the home and writes none of the semantics.
- **GAP-2 recurs, boundary-confirming:** the minute-cadence heartbeat is the clearest below-the-floor case in the series — 1,440 daily one-step instances of pure ceremony — reinforcing that the weight-floor rule, when written, should name runtime self-supervision as canonically provider-native.
- Nothing genuinely outside L9's named scope surfaced: all four mechanisms land inside L9 §§2/4/5/6 plus already-registered gaps — the section's finding is that the L9 topic map has the right *shape* and lacks every *contract*.

## Synthesis

**The headline: the model held.** None of the 17 workflows was unrealizable on v3 + external tools — every one decomposed into kernel coordination plus provider performance without distorting either side. The strongest single result is external and unsolicited: BitSafe's hardest-won operational lesson — "Orchestration that has to wait for approval belongs with the brain" (S10, capture 2028) — is the v3 kernel's existence claim, derived independently by a company that has never seen this model. The exercise also produced two incident-grade validations: v3's creation identity (planned) would have prevented both the 26-duplicate-findings incident (S9) and the 16-stuck-threads incident (S17) *by construction* — and v3-as-built would have reproduced both.

**Verdict topology across 17 simulations.**

- **Built and stretch-free where it claims to be.** Every human gate in the fleet (S8, S10, S11, S12, S13) ran on the L3 machinery with zero strain — including rework loops, round hygiene, per-decision required fields, and cross-gate correlation safety. The smoke watch (S11) is a built open-door wait. The two-round independent review (S15) found that produce-not-perform makes BitSafe's load-bearing isolation pattern the *structural default*. The L5 reserved slots met their first real-world witness (S14) and carried four of six declarations as-is.
- **"Not a kernel workload" is a coherent, repeatedly-confirmed boundary.** S1's lookup, S7's telemetry and model routing, S11's prod-restart reconciler, S12's file-grain locks, S14's 90-second exchange, S17's dead-man heartbeat — six independent judgments drew the same line from different directions (per-call grain below the dispatch; supervision on the performer's side; the wait doesn't survive the performer). The design rule distilled in S14(e) and S10(d) is canon material: *the kernel earns entry when the wait must survive the performer or the ask needs independent audit.*
- **The planned levels are well-aimed.** Where verdicts were 🟡, the named L6/L8 sections almost always **cover the need as written** — timer rows + CAS-claimed firing, the exact correlation oracle, the delivery ledger, correlation-by-stored-state. The topic map's shape survived contact with a real fleet.
- **The 🔴s concentrate at the seams, not inside levels.** The unwritten places are consistently *between* well-scoped territories: the L6 fire → `CREATE_INSTANCE` binding (GAP-1's scheduler face), the L8-event-maintains-L6-row seam (GAP-5), the L6 §3 ↔ L9 breaker-state seam (S17 R5), the definition-store ↔ series-store seam (GAP-16), the produce/perform attestation seam (GAP-8, GAP-13). Levels are owned; seams are orphaned.

**Gap ranking by demonstrated load.**

- **Tier 1 — structural, casualty-proven, highest priority:** **GAP-1** (16/16 simulations; two documented incidents as dual failure faces; also the kernel's native duplicate-work exclusion at task grain per S9/S12) and **GAP-4** (9 sections; S17's R1–R8 list is a ready-made requirements input for writing the L9 contract).
- **Tier 2 — recurring design pressure needing a written rule or construct:** **GAP-2** (9 sections; the answer may well be "by design, stay provider-native below the line" — but the line must be written, with S17's heartbeat as the canonical below-floor case and S14's stopwatch as the marginal one); **GAP-9** (detached spawn — every queue-feeding planner in a real fleet hits it; S9, S12); **GAP-6 + GAP-10** (the cross-run consulted-state family: suppression, quotas, breakers — one design decision should settle all three).
- **Tier 3 — sharp but single-witness; several are boundary-ratifications rather than build items:** GAP-5 (externally-derived deadlines), GAP-7 (external definition source — with the S13/S16 finding that v3-native residence *dissolves* it, leaving the store write contract), GAP-8 (issued-vs-applied precedence/attestation), GAP-11 (cross-instance mutex — candidate for "below the line by design"), GAP-12 (the L5 agent-addressed helper leg), GAP-13 (declarable step isolation), GAP-14 (binding-disjointness validation), GAP-15 (actor registry / principal status gating), GAP-16 (declared-trigger ↔ scheduler-state seam).

**Reusable design canon minted by the exercise** (candidates for promotion into the corpus): conditional gates are *routing, not dynamic templates* — an upstream kernel-classified classifier with gate-or-skip paths (S11 `[uat]`, S12 tiers); resolve-time slots × in-instance routing compose freely and should not be conflated (S11 hotfix × uat); external status fields become *projections of routed kernel facts*, dissolving detect-and-flip guards (S9, S12, S13); peer workflows may couple *through the world* when convergence comes from idempotent re-detection (S5); a self-interested selector must never classify its own gate condition — separate principal or kernel-classified outcome (S12); and the P5-entry rule (S10/S14) above.
