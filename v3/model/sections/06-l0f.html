L0f Project/repository configuration & definition resolution

A repository declares which workflow templates it runs and supplies repo-scoped values for the typed slots a template declares. This is a pre-kernel resolution layer: it runs before CREATE_INSTANCE and produces its inputs — it adds no kernel handler.

L0e let a template declare a runtime-context requirement with a config block of literal values (base_branch, branch_pattern). But those belong to the repo where you deploy, not to the portable definition. The same split surfaces for v1's bootstrap / test commands — repo toolchain values the workflow references but cannot define. L0f separates the two responsibilities: (J1) definition resolution — pick and pin the template (explicit or repo default, from a source) — and (J2) slot/value resolution — fill the template's typed slots from a repo-local ProjectConfig through a cascade. The fields with a meaningful universal default may stay template defaults; the cascade resolves the rest.

Not the kernel. The kernel still knows only Template + Instance. L0f is a function RESOLVE_START(command, project_config) → ResolvedStartRequest | Rejected that runs ahead of the kernel and hands a resolved bundle to CREATE_INSTANCE; later START and provider provisioning read the applied values from the pinned resolved definition through normal template loading. No instance, transcript, or version exists during the pass — a rejection means nothing was created.

5b

The whole pass is pre-kernel: it assembles inputs and validates them, but touches no instance state. v1 already does exactly this merge for one hard-wired workflow (repoValidationProfileResolver); L0f generalizes it to any template's declared slots.

Pseudocode The resolution module — not a kernel handler

A standalone function (empty baseline — it is not diffed against the kernel, because it is not part of it). It produces the bundle CREATE_INSTANCE consumes:

One entry point, no kernel coupling: RESOLVE_START returns a ResolvedStartRequest (or rejects). slot_scope fixes what the selected run consults — the per-workflow section, its target, and the CLI overrides are strict (a non-declared key is a typo → unknown_slot); the shared project_global and unrelated workflows' sections stay lenient. resolve_slot is the 5-tier cascade, explicit CLI on top. apply_slots then bakes the resolved values into a resolved definition — a pinned, immutable Template view — so the kernel and L0e keep reading runtime_context from a pinned template, never from a mutable slot map. The role → actor binding keeps its own cascade (L0c), it is not a slot.

ResolvedDefinition (value)
the pinned Template with its slot values applied (apply_slots); an immutable definition view the kernel loads exactly like a Template — the slot values live in the pinned definition, not in runtime state
ResolvedStartRequest (output)
{ resolved_template_ref (pinned ResolvedDefinition), binding } — the handoff to CREATE_INSTANCE; L0e reads runtime_context from the pinned view, no separate slot map
New rejections — all pre-kernel, no state change
Rejected(no_workflow_selected)
neither command.template_id nor default_workflow present
Rejected(workflow_definition_unavailable)
the source cannot load the selected template
Rejected(unknown_target(t))
an explicitly-selected target the workflow does not define — an intentional selection, so it rejects (unlike a lenient global slot)
Rejected(unknown_slot(key))
a non-declared key in the workflow / target / CLI scope (typo guard)
Rejected(unbound_required_slot(id))
a required slot resolves to no value
Rejected(slot_type_mismatch(id))
a resolved value fails its slot's declared type (minimal check)
L0f is the deployment-scope sibling of L0c's step-scope cascade: L0c resolved an AgentConfig through role/step/run scopes inside the template; L0f resolves slot values through project/workflow/target/CLI scopes outside it. The role → actor binding and agent/model config keep their own cascades — the project is merely a new tier in those, never a scalar slot.

Then the repo-local ProjectConfig (a new file — empty baseline) fills those slots with the values only the repo knows:

default_workflow is optional convenience — a StartCommand may name template_id explicitly; with neither present, resolution rejects with no_workflow_selected. Global defaults serve every workflow; a workflows[id] section scopes values (and the strict typo check) to one template, and targets are the highest config tier — only an explicit CLI override outranks them.

Evidence Why we accept L0f for now

  • Scenario coverage: a repo selects its default workflow, pins it from a local source, and resolves the template's slots — global test, a ui target override, a workflow-specific bootstrap, a CLI base_branch override — into a ResolvedStartRequest. Typos in scoped sections, unbound required slots, and a missing workflow selection all reject before any instance exists.
  • The layer is real, not invented (v11 verified): v1 already stores these in pairflow.toml [validation.commands] — bootstrap (optional, no default), test (required, default "pnpm test"), typecheck, lint (commandConfigTypes.ts, repoConfig.ts) — plus per-target [validation.targets.<id>.commands] and CLI --bootstrap-command / --test-command.
  • The cascade order is grounded: resolveRepoValidationProfileCommands merges legacy/default → repoValidation.commands → selected target → then applyExplicitValidationCommands (explicit CLI) — i.e. default < repo config < target < explicit CLI, exactly the L0f tier order. repoValidationProfileResolver.ts is the L0f cascade, hard-wired to one workflow; L0f generalizes it to any template's declared slots. An explicitly-selected but undefined target rejects (unknown_target) rather than silently proceeding, matching v1's handling of a missing configured target.
  • Execution points grounded: bootstrap runs after worktree creation (startCommandDefaults.ts); test runs in the PASS validation gate (passValidationGate.ts). Both are repo-specific values the workflow references but cannot define — the J2 case.
  • Known gaps (intended): no central store/registry (L11+), definition PRs (L12), trust (L13); no full schema; per-step/dynamic resolution and slot interpolation deferred; global-slot typo leniency accepted. All captured in Absent.
  • Decision: accepted as the L0f baseline (light evidence per playbook §2.1); roadmap block already in approach.md.
