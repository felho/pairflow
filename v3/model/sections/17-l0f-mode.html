L0g Run-scoped mode / variants

A single workflow can run in more than one mode (v1's code | doc) — the same step graph, but different gates and context. This is not a runtime kernel branch: a start-fixed, run-scoped mode that L0f resolution normalizes into a pinned, mode-specific ResolvedDefinition, so the kernel runs a mode-agnostic template and never sees the mode at runtime. One mechanism — the modes: membership tag — on two carriers: a gate binding and a context ref. An L0f-family extension, living entirely in the pre-kernel resolution pass.

Why two surfaces, not three. An earlier draft added a third surface — a run-level mode_profiles policy-ref map. It was dropped: in this kernel a policy is only ever applied at a gate (uses: = the policy, config: = its parameters) — there is no global run-level policy engine, so a free-floating policy map had no consumer. Mode-specific policy instead rides a gate binding: a transition point may declare a [code] binding and a [doc] binding (same uses with different config, or a different uses); resolution keeps the mode's. The consumer is the surviving gate's evaluator — visible, not a dangling map. An L0f delta kept off the L0f / LC3b baselines (the lenses diff against them and leave them untouched); L2 (gates) and L2b (context) are the pure consumers.

Pseudocode RESOLVE_START gains a J3 step (diff vs L0f)

The mode extension adds a third resolution responsibility to RESOLVE_START and two helpers; every other line is the L0f baseline, unchanged:

valid_mode_declaration is a load-time / authoring consistency check (fail-closed, the slot discipline applied to modes): default_mode names a declared mode, and every modes: tag sits on one of the two supported surfaces (a gate binding or a *_ref — elsewhere is mode_tag_on_unsupported_surface) and names a declared mode; a mono-mode template carries no mode surface at all. apply_mode then prunes the gate bindings and context refs into a pinned, mode-specific definition — so the variant is fixed at start, never branched on at runtime. The kernel passes no mode to a gate evaluator: a gate runs because its binding survived resolution, and any mode-specific behavior rides the binding's own config — one source of truth, not a runtime mode check inside the policy.

Evidence Why this cut is v1-faithful

A v1 reality check on review_artifact_type ∈ { code, document } (bubble.toml, --review-artifact-type, create-time immutable) shows every mode behavior maps onto the two surfaces:

  • Gate surface (presence + per-mode config): the runtime PASS validation gate runs only in code (passValidationGate.ts:407); the doc-contract reviewer gate is document-only (docContractGates.ts); the reviewer finding-priority demotion and the meta-review approve "docs-only null policy" (docContractReviewerGatePolicy.ts, metaReviewApproveValidationPolicy.ts) are the same gate with a [doc] binding / config.
  • Context surface: the docs-only edit guard ("refine only docs/task/spec; source code forbidden", documentBubbleSourceEditGuard.ts, rolePromptImplementerScope.ts), the reviewer doc-scope guidance, and the "runtime checks not required" wording (roleActionGuidance.ts) are mode-tagged context refs.
  • The one not-a-transition-gate piece: v1's doc default test directive — skip_full_rerun: true, verification_status: trusted, "docs-only scope, runtime checks not required" (reviewerTestDirectiveResolver.ts:80), plus the guard that a skip-claim with runtime log refs is a conflict (docsOnlyRuntimeSkipGuard.ts). This is evidence production, not a boolean check — so it is the docs_only_runtime_evidence gate whose allow result produces that durable evidence and records its ref on the GateDecision (LC1 INV-3 — no inline blob). It stays on the gate surface with a visible consumer.

Why mode_profiles was dropped: the model has no free-floating run-level policy consumer (a policy always runs at a gate), so a policy_refs map had nowhere to land. Folding it into mode-tagged gate bindings keeps the "explicit policy, not gate-absence" insight while making the consumer visible.
