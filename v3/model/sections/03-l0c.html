L0c Agent run configuration

Resolves how the assigned actor is run — the effective AgentConfig — so the right kind of agent does the work, not a vanilla one.

L0b decides who acts and hands them a packet, but carries agent_config raw. L0c answers how: it resolves the effective config by cascade (role default → step override → run override), puts the resolved config in the packet, and records which config the kernel issued in the transcript. This closes the v1 gap where "use sub-agent X" was implicit and merely assumed. It stays a portable run intent — actual provisioning, skill loading, and attestation are later layers.

Runtime A concrete trace

One round, showing the cascade resolving and the issued config recorded:

1
START_INSTANCE → DispatchIntent { actor: codex, … }
packet effective_agent_config = resolve(implement) = role { mode: builder } ⊕ step { approach: systematic } → { mode: builder, approach: systematic }
2
codex (builder/systematic) emits PASS (version=1)
kernel re-resolves issued_config for implement = same { mode: builder, approach: systematic } → commit implement → review, transcript records issued_agent_config; next DispatchIntent { claude, effective_agent_config: resolve(review) = { mode: critic, approach: thorough, skill_refs: [test-runner] } }
3
claude (critic/thorough) emits CONVERGED (version=2)
kernel re-resolves issued_config for review = { mode: critic, … } → commit review → done, transcript records it; terminal — no dispatch
The config the actor was issued is recomputed at commit from the same deterministic sources the packet used — so the transcript's provenance always matches what was dispatched, without the dispatch having to store anything.

Pseudocode The rule behind the trace

A new resolver, a changed packet field, and a provenance line — the rest of L0b is untouched:

The resolver is pure and deterministic, so the kernel recomputes the issued config at commit rather than the dispatch storing it — which keeps DispatchIntent a stateless kernel output (the L0b commit ≠ deliver rule holds). Note the cascade is the same shape as ActorBinding and model selection (§14.2): one resolution pattern, three uses.

Domain What L0c adds

Template aggregate — gains the run profile
Role
… + default_agent_config (the base run profile)
Step
agent_config now an override input (no longer raw pass-through)
AgentConfig (value)
inline: mode, approach, persona/profile, execution_hints; refs: model_ref/model_hint, prompt_profile_refs, prompt_concern_refs, skill_refs, tool_refs, tool_policy_ref (e.g. MCP) — all portable run intent
Instance aggregate — gains run overrides
WorkflowInstance
… + run_overrides (per-step, snapshotted at start)
TranscriptEntry
… + issued_agent_config (provenance — what the kernel issued)
Kernel output — derived, not stored
effective_agent_config
resolve(role default ⊕ step ⊕ run override); computed at dispatch and recomputed at commit
The effective config is never stored as instance state — it is recomputed from immutable sources both when the packet is built and when provenance is recorded. issued_agent_config says what the kernel issued, not that the actor-runtime ran exactly so — that proof is a later executor/attestation concern.

Config The template grows

Roles gain default_agent_config (base profile); steps' agent_config now overrides/extends it. The *_refs fields (model_ref, prompt_*_refs, skill_refs, tool_policy_ref) are declared references — run intent, not a guarantee the target is installed; ActorAdapter resolves the runtime refs later, ContextAssembly first resolves the prompt refs at L2b.

[[@absent l0c]]

Evidence Why we accept L0c for now

  • Scenario coverage: a step declaring mode: builder or a specific reviewer profile gets that resolved config in its packet — the v1 "assumed sub-agent" gap is closed at the declaration level. The transcript shows which config each emit was issued (provenance for later eval/metacognition §16/§17).
  • Invariant coverage: deterministic kernel-resolved provenance ✓; config sources immutable per dispatched step ✓; DispatchIntent stays a stateless output (commit ≠ deliver holds) ✓; all L0a/L0b invariants still hold.
  • Known gaps (intended): no actor-runtime adaptation; no prompt/context assembly; no provisioning/attestation; no skill-doc/memory (§11.4); no model routing (§14.2); no authorization (L1). Each is in Absent.
  • Decision: accepted as the L0c baseline (light evidence per playbook §2.1).
