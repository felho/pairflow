L1 Capability matrix — role/state authorization

Before any commit, the kernel decides whether an emit is legitimate for the current position — the role acting, and the action it may take. The first real "the workflow is the boss" rule.

By now the kernel has its full L0 foundation — lifecycle (L0d) and runtime context (L0e). L0f prepares the resolved start input before the kernel (pre-kernel, outside the handler chain); L1 is the authorization layer that sits on top of the kernel. L0b exposes which transitions exist from a step (navigation); L1 enforces which of them this actor/role may actually use. The envelope gains expected_role — the role dimension of the authority snapshot (expected_version → + expected_role) — and the kernel checks, before the transition commits, that the claimed role is the position's active role and that a CapabilityProfile allows the action. The profile is derived from the step graph by default, so no new config is needed yet. L1 is not identity authentication and not a gate/policy.

Runtime A concrete trace

The happy path plus a wrong-role emit rejected before any state change:

1
codex emits PASS on implement (version=1)
envelope { expected_version: 1, expected_role: implementer, type: PASS } → role implementer = implement.role ✓ · PASS is a transition ✓ · capability(implementer, implement) = {PASS} allows ✓ → commit implement → review
2
a stray emit on review claims expected_role: implementer (version=2)
review.role is reviewer → expected_role ≠ step.role → Rejected(role_not_authorized); no transcript append, version stays 2
3
claude emits CONVERGED on review { expected_role: reviewer } (version=2)
role reviewer = review.role ✓ · CONVERGED is a transition ✓ · capability allows ✓ → commit review → done; terminal — no dispatch
With the default-derived profile, capability equals the step's transitions, so not_authorized stays dormant. The live teeth here is role authority: an emit claiming the wrong role is rejected before the kernel touches state.

Pseudocode The rule behind the trace

A derived-capability helper and two authorization gates in HANDLE — issued config now resolves only on the commit path; the packet hands out the role to echo back:

On top of the full lifecycle + runtime-context kernel, L1 adds two authorization gates around the existing no_transition check: role authority first (are you even the active role?), then — once the action is confirmed to exist as a transition — action authorization. It also adds capability and begins handing the dispatched role out in the packet to be echoed back as expected_role. The CapabilityProfile is default-derived from the step graph, so no new config is needed; explicit authored restrictions enter the same profile later. The role check is the birth of the Warrant (kernel-primitives rebaseline, wave 2): with expected_role joining expected_version, the act-from fields an input carries become a named contract — operation identity · context authority · request correlation — and the Admission ladder gains its authority rung at the slot L0d reserved (after staleness). The step lookup hoists above the ladder as a positional read — infallible by load-time validation, so it cannot reject or mask a rung. Behavior is unchanged.

The role dimension matures the L0b authority seed: expected_version answered "on which state version do I act"; expected_role answers "as which role". The kernel verifies the claim against the position's active role — it does not prove the actor's identity (no token), exactly as v11 derives authority from context match, not a credential.

Config The template — unchanged at L1

# L1 adds no template config — the CapabilityProfile is derived from the step graph:
#   capability(role, step) = the step's transition keys, when role = step.role

# a later explicit restriction would enter the SAME profile (not in the baseline), e.g.:
capability_profile:
  - { role: reviewer, step: review, allow: [converged] }   # narrows: reviewer may converge, not pass back
The whole point of default-derivation: the simple pair loop needs zero authorization config, yet the kernel still enforces who-may-do-what. Config appears only when a real restriction or a multi-role action (e.g. human_question from either role) is introduced.

Absent Still not here

[[@absent l1]]

Evidence Why we accept L1 for now

  • Scenario coverage: a wrong-role emit is rejected before any state change; only the position's active role can drive it. The pair loop runs unchanged with expected_role now mandatory, and the kernel — not the actor's goodwill — decides legitimacy.
  • Invariant coverage: role authority + capability gate before commit ✓; idempotency, lifecycle guard, and stale precede authorization ✓; all L0a–L0f invariants still hold.
  • Known gaps (intended): not_authorized dormant under default-derived; no lifecycle authorization (L3); no identity authentication (L7/L10); no gate/policy (L2). Each is in Absent.
  • Rebaseline (wave 2): the Warrant (P4) is born here and the Admission ladder gains its authority rung — see the kernel-primitives memo (§6/§9); behavior unchanged, the rejection/invariant registries are identical before and after.
  • Decision: accepted as the L1 baseline (light evidence per playbook §2.1).
